# ТЕСТ-ПЛАН C — доступ, группы, участники, протокол, история

**Агент:** C · **Проект:** SplitPay · **Оракул:** `SPEC.md` v1.2 (138 требований) · **Заказ:** `order/ORDER.md`

## Статус документа (правило Р3)

**Это план, а не набор.** Все ожидания записаны **ДО прогона** и выведены **только из `SPEC.md`**;
поведение приложения при составлении плана не наблюдалось, код приложения не читался.
**По правилу Р3 проекта кейс без зафиксированного результата прогона в сдаточный набор не входит.**
Поле «Результат прогона» у всех кейсов ниже — `не прогнано — сессия прогона`; кейсы войдут
в сдаточный набор только после отдельной сессии прогона, где это поле будет заполнено фактом.

## Зона агента C

`SP-001`–`SP-007` (модель данных, переживание перезапуска), `SP-030`–`SP-035` (группы),
`SP-040`–`SP-047` (участники), `SP-100`–`SP-117` (протокол и ошибки), `SP-120`–`SP-121` (пути),
`SP-140`–`SP-148` (идентификация и доступ), `SP-180`–`SP-184` (история операций).

Вне зоны C: алгоритмы распределения и валидация суммы (агент A), балансы, долги, погашения
и пересчёт (агент B). История здесь проверяется **как список операций и его сверка** со сводками,
а не как арифметика долгов.

## Соглашения

- Все запросы к `/api/`, кроме `GET /api/health`, несут заголовок `X-User-Id` (`SP-140`).
- Денежные величины в ожиданиях даны в двух видах (`SP-020`, `SP-021`): целое число копеек
  (`...Minor`) и строка с ровно двумя знаками (`...Formatted`), плюс код валюты (`SP-028`).
- Идентификаторы групп, участников и расходов — фактические значения, полученные при подготовке
  предусловия; в шагах они обозначены как `{G1}`, `{p1}`, `{eB1}` и подставляются буквально.
- «Тело ошибки» всюду означает форму `SP-101`: `{"error": {"code": "...", "message": "..."}}`.
- Два статуса находки не смешиваются: **дефект против заказа** — нарушено то, что автору
  сказано в `ORDER.md`; **расхождение с оракулом** — в `ORDER.md` этого не было, автор решил иначе.

## Общие фикстуры

Готовятся один раз перед блоком кейсов; в предусловиях кейсов ссылка — «фикстура F1/F2».

**F1 — своя группа (владелец `u-alice`)**

| Что | Значение |
|---|---|
| Группа | `{G1}`, название `Поездка`, валюта `RUB`, владелец `u-alice` |
| Участники в порядке добавления | `{p1}` `Аня`, `{p2}` `Борис`, `{p3}` `Виктор` |
| Расход | `{e1}`: плательщик `{p1}`, сумма `"300.00"` (`30000` копеек), категория `food`, описание `Бензин`, способ `equal`, состав `[{p1},{p2},{p3}]` |
| Начисления по `{e1}` | по `100.00` (`10000`) каждому — `SP-061`, `SP-063` |
| Погашение | долг `{p2}`→`{p1}` отмечен оплаченным на `"100.00"` (`10000`) |

**F2 — чужая группа (владелец `u-bob`)** — маркеры утечки подобраны так, чтобы ни одна строка
из F2 не встречалась в данных `u-alice`:

| Что | Значение |
|---|---|
| Группа | `{G2}`, название `Дача`, валюта `EUR`, владелец `u-bob` |
| Участники | `{pB1}` `Женя`, `{pB2}` `Зоя` |
| Расход | `{eB1}`: плательщик `{pB1}`, сумма `"150.00"` (`15000`), категория `housing`, описание `Дрова`, способ `equal`, состав `[{pB1},{pB2}]` → по `75.00` (`7500`) |
| Погашение | долг `{pB2}`→`{pB1}` отмечен оплаченным на `"75.00"` (`7500`) |

**Набор запрещённых строк утечки F2** (`SP-117`) — далее «список L». Наличие любой из этих строк
в теле отказа (в любом поле, включая `message`), а также в заголовках ответа, считается провалом:

```
"Дача"  "Женя"  "Зоя"  "Дрова"  "EUR"
"150.00"  15000  "75.00"  7500
{G2}-производные названия, {pB1}, {pB2}, {eB1}
```

Значение `{G2}` в теле допустимо только как эхо идентификатора из запроса; **имена, суммы,
валюта и идентификаторы участников/расходов чужой группы — недопустимы**.

# I. Доступ и идентификация

### C-01 · чужая группа по прямому идентификатору — корень группы
- **Требования:** SP-145, SP-116, SP-117, SP-101, SP-102, SP-100
- **Уровень:** API
- **Предусловие:** фикстуры F1 и F2 созданы. `u-alice` владеет `{G1}`, `u-bob` владеет `{G2}`.
  Идентификатор `{G2}` известен обращающемуся (он получен при подготовке F2 под `u-bob`).
- **Шаги:**
  1. `GET /api/groups/{G2}`, заголовок `X-User-Id: u-alice`, тела нет.
- **Ожидаемый результат:**
  - Статус `403`, тело `{"error":{"code":"FORBIDDEN","message":"..."}}` — код ровно `FORBIDDEN`
    из набора `SP-102`; `NOT_FOUND`, `UNAUTHORIZED`, `VALIDATION_ERROR` здесь — провал.
  - `Content-Type: application/json; charset=utf-8` (`SP-100`).
  - `message` непустой и называет причину — отказ по владению (`SP-108`).
  - **Чего в теле быть не должно (`SP-117`):** ни одной строки из списка L — конкретно
    `Дача`, `Женя`, `Зоя`, `Дрова`, `EUR`, `150.00`, `15000`, `75.00`, `7500`, `{pB1}`, `{pB2}`,
    `{eB1}`. Наличие любой — провал кейса.
  - Тело не содержит полей `name`, `participants`, `currency`, `expenses`, `balances`, `debts`
    ни на верхнем уровне, ни внутри `error`.
- **Статус возможной находки:** **дефект против заказа**, если вернулись данные группы —
  заказ прямо говорит «Пользователь видит только свои группы». Если данные не вернулись,
  но код/статус иной (например `404`), — **расхождение с оракулом**: конкретный код заказом не задан.
- **Результат прогона:** `не прогнано — сессия прогона`

### C-02 · чужая группа — все вложенные ЧИТАЮЩИЕ пути (SP-146)
- **Требования:** SP-146, SP-116, SP-117, SP-120
- **Уровень:** API
- **Предусловие:** F1, F2. Все запросы — с `X-User-Id: u-alice`, все пути — по `{G2}`.
- **Шаги:** каждый пункт — отдельный запрос, все пять обязаны быть выполнены:
  1. `GET /api/groups/{G2}/expenses`
  2. `GET /api/groups/{G2}/balances`
  3. `GET /api/groups/{G2}/debts`
  4. `GET /api/groups/{G2}/transactions`
  5. `GET /api/groups/{G2}` (корень — повторяется здесь как контроль, что отказ единообразен)
- **Ожидаемый результат:**
  - Каждый из пяти ответов: статус `403`, код `FORBIDDEN`, `Content-Type: application/json; charset=utf-8`.
  - Ни один ответ не содержит строк из списка L. Отдельно: в ответе шага 1 не должно быть
    `Дрова`, `15000`, `"150.00"`, `housing`, `{eB1}`; в ответе шага 2 — `Женя`, `Зоя`, `7500`;
    в ответе шага 3 — `{pB1}`, `{pB2}`, `"75.00"`; в ответе шага 4 — `settlement`, `expense`
    в качестве значений записей, `Дрова`, `"75.00"`.
  - Ни один ответ не содержит массива записей: поля `items`, `expenses`, `balances`, `debts`,
    `transactions` отсутствуют либо запрос вообще не дошёл до данных.
  - Пустой массив `[]` со статусом `200` на любом из пяти путей — **провал**: `SP-146` требует
    отказа, а не «пустого чужого».
- **Статус возможной находки:** **дефект против заказа** — «видит только свои группы» относится
  ко всем данным группы, а не к её корню; вложенный путь, отдающий данные, нарушает сказанное автору.
- **Результат прогона:** `не прогнано — сессия прогона`

### C-03 · чужая группа — все вложенные ИЗМЕНЯЮЩИЕ пути (SP-146)
- **Требования:** SP-146, SP-116, SP-117, SP-120
- **Уровень:** API
- **Предусловие:** F1, F2. Все запросы — с `X-User-Id: u-alice`, пути — по `{G2}`.
- **Шаги:**
  1. `POST /api/groups/{G2}/participants`, тело `{"name":"Ляля"}`
  2. `DELETE /api/groups/{G2}/participants/{pB2}`
  3. `POST /api/groups/{G2}/expenses`, тело
     `{"payerId":"{pB1}","amount":"10.00","currency":"EUR","category":"food","description":"взлом","split":{"method":"equal","participants":["{pB1}","{pB2}"]}}`
  4. `PUT /api/groups/{G2}/expenses/{eB1}`, тело
     `{"payerId":"{pB1}","amount":"1.00","currency":"EUR","category":"other","description":"подмена","split":{"method":"equal","participants":["{pB1}","{pB2}"]}}`
  5. `DELETE /api/groups/{G2}/expenses/{eB1}`
  6. `POST /api/groups/{G2}/debts/{pB1}/{pB2}/pay`, тело `{}`
  7. Контроль от владельца: `GET /api/groups/{G2}` с `X-User-Id: u-bob`
  8. Контроль от владельца: `GET /api/groups/{G2}/expenses` с `X-User-Id: u-bob`
  9. Контроль от владельца: `GET /api/groups/{G2}/transactions` с `X-User-Id: u-bob`
- **Ожидаемый результат:**
  - Шаги 1–6: каждый ответ — статус `403`, код `FORBIDDEN`, `Content-Type: application/json; charset=utf-8`,
    без строк списка L. Статусы `201`, `200`, `204` на любом из шагов 1–6 — провал.
  - Шаг 7: `200`, группа `{G2}` содержит ровно двух участников `Женя`, `Зоя` в этом порядке;
    участника `Ляля` нет; `Зоя` на месте.
  - Шаг 8: `200`, ровно один расход `{eB1}`, сумма `amountMinor: 15000`, `amountFormatted: "150.00"`,
    `currency: "EUR"`, `category: "housing"`, `description: "Дрова"` — то есть шаги 4 и 5 ничего не изменили.
  - Шаг 9: `200`, ровно две записи истории (расход `{eB1}` и погашение `{pB2}`→`{pB1}` на `7500` /
    `"75.00"`); третьей записи (погашения от шага 6) нет.
- **Статус возможной находки:** **дефект против заказа**, если хотя бы один изменяющий запрос
  прошёл: чужая группа изменена посторонним — прямое нарушение «видит только свои группы»
  в его сильной форме. Отказ с иным кодом при неизменённых данных — **расхождение с оракулом**.
- **Результат прогона:** `не прогнано — сессия прогона`

### C-04 · содержимое отказа по чужой группе не раскрывает данные (SP-117 подробно)
- **Требования:** SP-117, SP-116, SP-101, SP-108
- **Уровень:** API
- **Предусловие:** F2 создана. `u-alice` не владеет `{G2}`.
- **Шаги:**
  1. `GET /api/groups/{G2}/transactions`, `X-User-Id: u-alice`.
  2. Полное тело ответа сохранить как текст и проверить на вхождение подстрок.
- **Ожидаемый результат:**
  - Статус `403`, код `FORBIDDEN`.
  - Тело состоит **ровно** из объекта `error` с полями `code` и `message`; иных полей верхнего
    уровня нет.
  - Проверка подстрок — провал при наличии любой: `Дача`, `Женя`, `Зоя`, `Дрова`, `EUR`,
    `150.00`, `75.00`, `15000`, `7500`, `{pB1}`, `{pB2}`, `{eB1}`, `u-bob`.
  - Отдельно: идентификатор владельца `u-bob` не раскрывается — сообщение вида
    «группа принадлежит u-bob» — провал (`SP-117` запрещает раскрывать содержимое чужой группы,
    а владелец — её содержимое по `SP-001`).
  - Заголовки ответа не содержат ни одной из этих строк (в частности, нет `X-Owner`, `Location`
    с чужими данными).
  - При этом `message` обязан называть причину (`SP-108`): «доступ к чужой группе запрещён»
    или эквивалент. Пустой `message` либо `"error"` — провал.
- **Статус возможной находки:** **дефект против заказа** — утечка содержимого чужой группы
  прямо противоречит абзацу заказа о видимости только своих групп.
- **Результат прогона:** `не прогнано — сессия прогона`

### C-05 · 403 против 404: чужая существующая против несуществующей (SP-116 vs SP-104)
- **Требования:** SP-116, SP-104, SP-121, SP-102
- **Уровень:** API
- **Предусловие:** F1, F2. Строка `grp-does-not-exist-0000` заведомо не является идентификатором
  ни одной группы.
- **Шаги:**
  1. `GET /api/groups/{G2}`, `X-User-Id: u-alice` — чужая **существующая** группа.
  2. `GET /api/groups/grp-does-not-exist-0000`, `X-User-Id: u-alice` — **несуществующая** группа.
  3. `GET /api/groups/{G2}/balances`, `X-User-Id: u-alice`.
  4. `GET /api/groups/grp-does-not-exist-0000/balances`, `X-User-Id: u-alice`.
- **Ожидаемый результат:**
  - Шаги 1 и 3: статус `403`, код `FORBIDDEN` (`SP-116`).
  - Шаги 2 и 4: статус `404`, код `NOT_FOUND` (`SP-104`).
  - Ответы шагов 1 и 2 обязаны различаться статусом — одинаковый ответ на оба (например `404`
    в обоих случаях) считается расхождением с оракулом, несмотря на то, что он безопаснее.
  - Тела шагов 1 и 3 — без строк списка L.
- **Спорное место, отметить в отчёте:** `SP-116` заставляет приложение отвечать `403` на чужую
  существующую группу и `404` на несуществующую — то есть **отказ сообщает обратившемуся, что
  группа с таким идентификатором существует**. Это перечислимая утечка факта существования,
  формально не запрещённая `SP-117` (там речь о содержимом). Спека выбрала `403`; ожидание
  зафиксировано по спеке, а сам выбор выносится в отчёт как спорное решение оракула.
  Если автор ответил `404` в обоих случаях — это **расхождение с оракулом**, но с обоснованием
  в пользу автора: заказ такого различения не требовал.
- **Статус возможной находки:** **расхождение с оракулом** — заказ не задаёт различения кодов;
  утечкой данных ни один из вариантов не является.
- **Результат прогона:** `не прогнано — сессия прогона`

### C-06 · идентификатор участника в X-User-Id не даёт доступа (SP-148)
- **Требования:** SP-148, SP-116, SP-146, SP-147, SP-144
- **Уровень:** API
- **Предусловие:** F2 создана. `{pB1}` — **реальный** идентификатор участника `Женя` из чужой
  группы `{G2}`, полученный из ответа на создание участника под `u-bob`. Выдуманные строки
  в этом кейсе не используются: подстановка несуществующего идентификатора проверяла бы
  «неизвестный пользователь», а не `SP-148`.
- **Шаги:**
  1. `GET /api/groups/{G2}`, заголовок `X-User-Id: {pB1}`.
  2. `GET /api/groups/{G2}/transactions`, заголовок `X-User-Id: {pB1}`.
  3. `POST /api/groups/{G2}/participants`, заголовок `X-User-Id: {pB1}`, тело `{"name":"Тест"}`.
  4. `GET /api/groups`, заголовок `X-User-Id: {pB1}`.
  5. То же для второго участника: `GET /api/groups/{G2}`, заголовок `X-User-Id: {pB2}`.
- **Ожидаемый результат:**
  - Шаги 1, 2, 3, 5: статус `403`, код `FORBIDDEN`; в теле нет строк списка L.
    Статус `200` с данными группы — провал и есть содержательная находка `SP-148`.
  - Шаг 4: статус `200`, тело — **пустой массив** `[]` (`SP-147`: ранее не встречавшийся
    идентификатор обслуживается как обычный, у него просто нет групп). `{G2}` в списке — провал (`SP-144`).
    Статус `401`/`403` на шаге 4 — расхождение: участник как пользователь не запрещён, он просто чужой.
- **Статус возможной находки:** **расхождение с оракулом** — заказ не разделяет понятия
  «участник» и «пользователь» вовсе, автор мог отождествить их сам; но если отождествление даёт
  доступ к чужой группе, находка переклассифицируется в **дефект против заказа** (видимость чужих данных).
- **Результат прогона:** `не прогнано — сессия прогона`

### C-07 · список групп: изоляция владельцев и новый пользователь
- **Требования:** SP-035, SP-144, SP-147, SP-143, SP-109
- **Уровень:** API
- **Предусловие:** F1 (владелец `u-alice`), F2 (владелец `u-bob`). Пользователь `u-carol` ранее
  не встречался ни в одном запросе.
- **Шаги:**
  1. `GET /api/groups`, `X-User-Id: u-alice`.
  2. `GET /api/groups`, `X-User-Id: u-bob`.
  3. `GET /api/groups`, `X-User-Id: u-carol`.
  4. `POST /api/groups`, `X-User-Id: u-carol`, тело `{"name":"Обед","currency":"RUB"}`.
  5. `GET /api/groups`, `X-User-Id: u-carol`.
  6. `GET /api/groups`, `X-User-Id: u-alice`.
- **Ожидаемый результат:**
  - Шаг 1: `200`, ровно один элемент — `{G1}` с названием `Поездка`; `{G2}` и название `Дача`
    отсутствуют.
  - Шаг 2: `200`, ровно один элемент — `{G2}` с названием `Дача`; `Поездка` отсутствует.
  - Шаг 3: `200`, тело — ровно `[]`. Ответ `401`, `403` или `404` — провал (`SP-147`).
  - Шаг 4: `201`, в теле группа с `ownerId`/владельцем `u-carol` (`SP-143`) и пустым списком участников.
  - Шаг 5: `200`, ровно один элемент — `Обед`.
  - Шаг 6: `200`, по-прежнему ровно один элемент `Поездка` — появление `Обед` или `Дача` в списке
    `u-alice` — провал.
- **Статус возможной находки:** **дефект против заказа** — «Пользователь видит только свои группы»
  сказано автору дословно; чужая группа в списке нарушает именно это.
- **Результат прогона:** `не прогнано — сессия прогона`

### C-08 · заголовок X-User-Id: отсутствует, пустой, из пробелов; health без идентификации
- **Требования:** SP-140, SP-141, SP-142, SP-115, SP-114, SP-102, SP-113

### C-11 · название группы: длина, пробелы, обрезка

### C-16 · уникальность имён участников БЕЗ УЧЁТА РЕГИСТРА

- **Уровень:** API
- **Предусловие:** пустая группа `{G}` пользователя `u-alice`.

    что учитывается число когда-либо созданных, а не текущих участников, — это провал.

### C-19 · удаление свободного участника
- **Требования:** SP-044, SP-109, SP-006, SP-047
- **Уровень:** API
- **Предусловие:** группа `{G}` пользователя `u-alice`, участники в порядке: `{p1}` `Аня`,
  `{p2}` `Борис`, `{p3}` `Виктор`, `{p4}` `Галя`. Расход `{e}`: плательщик `{p1}`, сумма `"300.00"`
  (`30000`), `equal` на `[{p1},{p2},{p3}]`. Участник `{p4}` не участвует ни в расходе, ни в погашении.
- **Шаги:**
  1. `DELETE /api/groups/{G}/participants/{p4}`, `X-User-Id: u-alice`.
  2. `GET /api/groups/{G}`, `X-User-Id: u-alice`.
  3. `DELETE /api/groups/{G}/participants/{p4}`, `X-User-Id: u-alice` — повторное удаление.
  4. `GET /api/groups/{G}/expenses`, `X-User-Id: u-alice`.
  5. `DELETE /api/groups/{G}/expenses/{e}`, `X-User-Id: u-alice` — удалить расход,
     после которого `{p2}` перестаёт быть занятым (**правка D-07**).
  6. `DELETE /api/groups/{G}/participants/{p2}`, `X-User-Id: u-alice`.
- **Ожидаемый результат:**
  - Шаг 1: статус ровно `204`, **тело пустое** (`SP-109`); `200` с телом участника — расхождение.
  - Шаг 2: `200`, ровно три участника в порядке `Аня`, `Борис`, `Виктор`; порядок оставшихся
    не изменился (`SP-006`).
  - Шаг 3: `404`, код `NOT_FOUND` (`SP-047`); повторное `204` — расхождение.
  - Шаг 4: `200`, расход `{e}` на месте: `amountMinor: 30000`, `amountFormatted: "300.00"`,
    состав распределения — те же три участника; удаление свободного участника расход не тронуло.
  - Шаг 5: `204` (`SP-057`).
  - Шаг 6: `204` (**правка D-07**). `SP-044` формулирует условие как состояние («не участвует
    ни в одном расходе и ни в одном погашении»), а не как историю: после удаления
    единственного расхода `{p2}` этому условию удовлетворяет. Ответ `409 CONFLICT` здесь —
    находка: реализация ведёт у участника несбрасываемый флаг «использован», и пользователь,
    удаливший ошибочный расход, уже никогда не сможет удалить участника. Ни один из 125
    кейсов этот переход раньше не проверял: были проверены только два статических состояния
    — свободен изначально (`C-19`, `C-18`) и занят (`C-20`, `C-21`).
- **Статус возможной находки:** **расхождение с оракулом** — удаление участников в заказе
  не упомянуто вовсе.
- **Результат прогона:** `не прогнано — сессия прогона`

### C-20 · удаление участника с непогашенными долгами: плательщик и член состава распределения
- **Требования:** SP-045, SP-105, SP-102, SP-108, SP-113
- **Уровень:** API
- **Предусловие:** фикстура F1 **без погашения** — группа `{G1}`, участники `{p1}` `Аня`,
  `{p2}` `Борис`, `{p3}` `Виктор`; расход `{e1}`: плательщик `{p1}`, сумма `"300.00"` (`30000`),
  `equal` на всех трёх → по `100.00` (`10000`). Ни одного погашения не проведено, долги
  `{p2}`→`{p1}` `"100.00"` и `{p3}`→`{p1}` `"100.00"` в статусе `pending`.
- **Шаги:**
  1. `DELETE /api/groups/{G1}/participants/{p1}`, `X-User-Id: u-alice` — плательщик.
  2. `DELETE /api/groups/{G1}/participants/{p2}`, `X-User-Id: u-alice` — член состава распределения,
     должник с непогашенным долгом.
  3. `DELETE /api/groups/{G1}/participants/{p3}`, `X-User-Id: u-alice` — второй член состава.
  4. `GET /api/groups/{G1}`, `X-User-Id: u-alice`.
  5. `GET /api/groups/{G1}/expenses`, `X-User-Id: u-alice`.
  6. Контроль живучести: `POST /api/groups/{G1}/participants`, `X-User-Id: u-alice`,
     тело `{"name":"Галя"}`.
- **Ожидаемый результат:**
  - Шаги 1, 2, 3: статус `409`, код ровно `CONFLICT` (`SP-045`, `SP-105`); `message` называет
    причину — участие в расходе (`SP-108`). Статус `204` на любом из трёх — провал: участник
    с непогашенным долгом удалён.
  - Шаг 4: `200`, ровно три участника `Аня`, `Борис`, `Виктор` в исходном порядке.
  - Шаг 5: `200`, расход `{e1}` цел: `amountMinor: 30000`, `amountFormatted: "300.00"`,
    `currency: "RUB"`, состав распределения — ровно `[{p1},{p2},{p3}]`. Молчаливое исключение
    удаляемого участника из состава распределения (состав из двух) — провал.
  - Шаг 6: `201` — процесс жив и обслуживает корректные запросы (`SP-113`).
- **Статус возможной находки:** **расхождение с оракулом** — заказ не описывает удаление
  участников и не задаёт запрета; автор мог решить иначе. Однако удаление участника, на котором

  переклассифицировать в **дефект против заказа**, если после удаления сумма долгов перестала
  сходиться (проверяется совместно с зоной B).
- **Результат прогона:** `не прогнано — сессия прогона`

# IV. Краевые составы группы

### C-23 · пустая группа: пустой список против нулевых значений
- **Требования:** SP-030, SP-083, SP-082, SP-096, SP-180, SP-146
- **Уровень:** API
- **Предусловие:** группа `{Ge}` создана `u-alice` (`POST /api/groups`, тело
  `{"name":"Пустая","currency":"RUB"}`), участников **ноль**, расходов ноль, погашений ноль.
- **Шаги:**
  1. `GET /api/groups/{Ge}`, `X-User-Id: u-alice`.
  2. `GET /api/groups/{Ge}/participants` — путь вне таблицы `SP-120`; ожидание см. ниже.
  3. `GET /api/groups/{Ge}/expenses`, `X-User-Id: u-alice`.
  4. `GET /api/groups/{Ge}/balances`, `X-User-Id: u-alice`.
  5. `GET /api/groups/{Ge}/debts`, `X-User-Id: u-alice`.
  6. `GET /api/groups/{Ge}/transactions`, `X-User-Id: u-alice`.
- **Ожидаемый результат:**
  - Шаг 1: `200`, список участников — `[]`.
  - Шаг 2 (**правка D-13**): ожидание берётся из спеки, а не «любой из трёх исходов».
    Пути `/participants` в таблице `SP-120` нет, `SP-121` требует под `/api/` ответа `404`
    с кодом `NOT_FOUND` в форме `SP-101`. Поэтому: `404 NOT_FOUND` — успех; `405
    METHOD_NOT_ALLOWED` — допустимо (путь существует как корень для `DELETE`), фиксируется;
    **`200` с данными — расхождение с `SP-120`/`SP-121` и провал шага**, а не «фиксируется,
    но не дефект». Прежняя редакция объявляла приемлемыми все три взаимоисключающих исхода:
    шаг не мог провалиться иначе как падением процесса и занимал место проверки, не будучи ею.
  - Шаг 3: `200`, тело — ровно `[]`.
  - Шаг 4: `200`, тело — ровно `[]`. **Здесь `[]` правильный ответ именно потому, что участников
    ноль**: `SP-083` требует нулевых балансов «для всех участников», а всех — ноль. Ответ
    `404` — провал; ответ вида `{"total": 0}` без списка — расхождение (`SP-082` требует список
    по участникам).
  - Шаг 5: `200`, тело — ровно `[]`; долгов со статусом `pending` нет (`SP-096`).
  - Шаг 6: `200`, тело — ровно `[]` (`SP-180`: история есть, но пуста).
  - Ни один из шагов 3–6 не должен вернуть `500` или разрыв соединения.
- **Статус возможной находки:** **расхождение с оракулом** — поведение на пустой группе заказом
  не описано; падение процесса на пустой группе — **дефект против заказа** (заказано работающее API).
- **Результат прогона:** `не прогнано — сессия прогона`

### C-33 · данные переживают перезапуск процесса, включая погашения
- **Требования:** SP-007, SP-001, SP-003, SP-004, SP-005, SP-006, SP-143, SP-180
- **Уровень:** API
- **Предусловие:** чистый запуск `node app/server.js`. Создаются **обе** фикстуры: F1 (владелец
  `u-alice`, группа `Поездка`, участники `Аня`, `Борис`, `Виктор`, расход `{e1}` `"300.00"`
  категории `food` с описанием `Бензин`, погашение `{p2}`→`{p1}` на `"100.00"`) и F2 (владелец

    не изменились.

    **в том же порядке** (`SP-006`).
  - Расход `{e1}`: тот же идентификатор, `amountMinor: 30000`, `amountFormatted: "300.00"`,
    `currency: "RUB"`, `category: "food"`, `description: "Бензин"`, способ `equal`, состав
    распределения — те же три участника, момент создания тот же (`SP-004`).
  - **Погашение сохранилось:** в `GET /api/groups/{G1}/debts` пара `{p2}`→`{p1}` в статусе `paid`
    на `10000` / `"100.00"`; пара `{p3}`→`{p1}` в статусе `pending` на `10000` / `"100.00"`.
    Возврат пары `{p2}`→`{p1}` в `pending` после перезапуска — **провал** `SP-007` (именно этот
    пункт добавлен в редакции 1.1).
  - История `{G1}`: ровно две записи — те же, что до перезапуска, в том же порядке.
  - Данные `u-bob` также целы: группа `Дача`, участники `Женя`, `Зоя`, расход `15000` / `"150.00"`
    в `EUR`, погашение `7500` / `"75.00"` в статусе `paid`.

    существующими (проверяется созданием одной новой группы после шага 4).
- **Статус возможной находки:** **дефект против заказа** — заказ требует «Данные в JSON-файле»;
  потеря данных при перезапуске означает, что данные фактически не сохранялись. Потеря **только
  погашений** при сохранности остального — тоже дефект против заказа, поскольку отметка долга
  оплаченным заказана дословно.
- **Результат прогона:** `не прогнано — сессия прогона`

### C-35 · порядок истории: от новых к старым, поимённо
- **Требования:** SP-182, SP-180, SP-056
- **Уровень:** API
- **Предусловие:** группа `{Gh}` пользователя `u-alice`, валюта `RUB`, участники в порядке
  `{h1}` `Аня`, `{h2}` `Борис`, `{h3}` `Виктор`. Далее операции выполняются строго последовательно,
  с паузой не менее 1 секунды между ними, чтобы моменты различались:
  - T1: расход `{x1}` — плательщик `{h1}`, `"30.00"` (`3000`), `equal` на `[{h1},{h2},{h3}]`, описание `Первый`.
  - T2: расход `{x2}` — плательщик `{h2}`, `"60.00"` (`6000`), `equal` на `[{h1},{h2},{h3}]`, описание `Второй`.
  - T3: погашение `{h3}`→`{h2}` отмечено оплаченным (**правка D-19/D-27/D-41**: пары
    `{h3}`→`{h1}` при этих балансах не существует, см. пересчёт в «Обосновании T3» ниже).
  - T4: расход `{x3}` — плательщик `{h3}`, `"90.00"` (`9000`), `equal` на `[{h1},{h2},{h3}]`, описание `Третий`.
- **Шаги:**
  1. `GET /api/groups/{Gh}/transactions`, `X-User-Id: u-alice`.
  2. `GET /api/groups/{Gh}/expenses`, `X-User-Id: u-alice`.
- **Ожидаемый результат:**
  - Шаг 1: `200`, ровно четыре записи, в этом и только этом порядке:
    1. `expense` `{x3}` — `Третий`, `amountMinor: 9000`, `amountFormatted: "90.00"`;
    2. `settlement` `{h3}`→`{h2}` — `amountMinor: 3000`, `amountFormatted: "30.00"`
       (**правка D-19**; обоснование от балансов, а не от пер-расходной раскладки);
    3. `expense` `{x2}` — `Второй`, `amountMinor: 6000`, `amountFormatted: "60.00"`;
    4. `expense` `{x1}` — `Первый`, `amountMinor: 3000`, `amountFormatted: "30.00"`.
    Порядок «от старых к новым» (`Первый`, `Второй`, погашение, `Третий`) — провал `SP-182`.
    Раздельные блоки (сначала все расходы, потом все погашения) — тоже провал.
  - Шаг 2: `200`, расходы **от старых к новым**: `{x1}` `Первый`, `{x2}` `Второй`, `{x3}` `Третий`
    (`SP-056`) — то есть порядок в `/expenses` и в `/transactions` обязан быть противоположным.
    Одинаковый порядок в обоих — провал одного из двух требований, в отчёте указывается какого.
- **Обоснование T3 (внесено правкой D-19, было ошибкой плана).** Перед T3: начислено каждому
  `1000 + 2000 = 3000`; `{h1}` заплатил `3000` → баланс `0`; `{h2}` заплатил `6000` → `+3000`;
  `{h3}` заплатил `0` → `−3000`. По `SP-161` долг вычисляется **из балансов**, поэтому
  единственная пара — `{h3}`→`{h2}` на `3000`. Пары `{h3}`→`{h1}` не существует: у `{h1}`
  баланс ноль, и `POST .../debts/{h3}/{h1}/pay` обязан вернуть `404` по `SP-167`. Прежняя
  редакция кейса требовала именно этого вызова и получала сумму `1000` пер-расходной
  раскладкой — способом, который `plan-B.md` (`B-06`, `B-07`) квалифицирует как дефект.
  Кейс был неисполним: на спека-корректном приложении он не дошёл бы до шагов и занёс бы
  в отчёт несуществующий дефект зоны B.
- **Спорное место:** по `SP-165` погашение создаётся «на полную сумму текущего остатка»,
  то есть сумма `3000` не задаётся запросом, а вычисляется приложением. Если приложение
  принимает сумму погашения параметром, кейс фиксирует фактически проведённую сумму
  и сверяет её с `3000`; расхождение — находка зоны B, ожидание **порядка** записей при этом
  остаётся в силе и проверяется независимо.
- **Статус возможной находки:** **расхождение с оракулом** — направление сортировки заказом
  не задано.
- **Результат прогона:** `не прогнано — сессия прогона`

### C-38 · сверка истории с балансами и долгами
- **Требования:** SP-180, SP-181, SP-182, SP-056, SP-020, SP-028
- **Уровень:** API
- **Предусловие:** группа `{Gr}` пользователя `u-alice`, валюта `RUB`, участники в порядке
  `{r1}` `Аня`, `{r2}` `Борис`, `{r3}` `Виктор`. Операции строго последовательно:
  - расход `{z1}`: плательщик `{r1}`, `"300.00"` (`30000`), `equal` на всех троих → по `10000`;
  - расход `{z2}`: плательщик `{r2}`, `"60.00"` (`6000`), `equal` на всех троих → по `2000`;
  - погашение: долг `{r3}`→`{r1}` отмечен оплаченным.
- **Шаги:**
  1. `GET /api/groups/{Gr}/transactions`, `X-User-Id: u-alice`.
  2. `GET /api/groups/{Gr}/expenses`, `X-User-Id: u-alice`.
  3. `GET /api/groups/{Gr}/balances`, `X-User-Id: u-alice`.
  4. `GET /api/groups/{Gr}/debts`, `X-User-Id: u-alice`.
- **Ожидаемый результат — четыре сверки, каждая с точными числами:**
  - **Сверка 1 (история ↔ список расходов).** Записи типа `expense` в истории — ровно две,
    их идентификаторы и суммы совпадают со списком расходов один в один: `{z1}` `30000` /
    `"300.00"` и `{z2}` `6000` / `"60.00"`. Сумма расходов в истории — `36000` копеек /
    `"360.00"`. Запись в истории без соответствия в `/expenses` (или наоборот) — провал.
  - **Сверка 2 (история ↔ проведённые погашения).** Записи типа `settlement` — ровно одна,
    на `12000` копеек / `"120.00"`: до погашения баланс `{r3}` равен `−12000` (начислено
    `10000`+`2000`, заплатил `0`), и весь этот остаток причитается `{r1}`, чей баланс
    **`+18000`** (`30000 − 12000`; **правка D-21**, прежнее `+20000` нарушало `SP-081`
    внутри самого плана: сумма трёх балансов дала бы `+2000`). Сумма всех записей
    `settlement` в истории обязана равняться сумме **фактически проведённых погашений**
    — `12000` копеек / `"120.00"` (**правка D-26**: прежняя редакция сверяла её с полем суммы
    у долгов со статусом `paid`, чем возводила спорную трактовку в инвариант; при трактовке
    плана B, где у `paid` записан остаток `0`, эта сверка провалилась бы на любой реализации,
    следующей букве `SP-163`).
  - **Сверка 3 (история ↔ балансы).** Из истории выводится: заплачено `{r1}` = `30000`,
    `{r2}` = `6000`, `{r3}` = `0`; отдано погашениями `{r3}` = `12000`; получено погашениями
    `{r1}` = `12000`; начислено каждому `12000`. Отсюда балансы обязаны быть ровно:
    `{r1}` = `30000 − 12000 − 12000` = `+6000` / `"60.00"`; `{r2}` = `6000 − 12000` = `−6000` /
    `"-60.00"`; `{r3}` = `0 + 12000 − 12000` = `0` / `"0.00"`. Сумма трёх балансов — `0`.
    Расхождение хотя бы в одну копейку — провал сверки.
  - **Сверка 4 (история ↔ долги).** В `/debts` обязаны присутствовать ровно две пары:
    `{r3}`→`{r1}` со статусом `paid` и `{r2}`→`{r1}` со статусом `pending` на `6000` /
    `"60.00"`. **Величина у записи `paid` (правка D-26) — объявленная неоднозначность Н-3-А:**
    `0` / `"0.00"` (остаток, трактовка плана B, ближе к букве `SP-163` и `SP-092`) и
    `12000` / `"120.00"` (погашенная сумма) обе защитимы; фактическое значение фиксируется,
    кейса не проваливает. Несущие проверки — наличие записи, её статус и направление. Сумма долгов `pending` (`6000`) равна сумме положительных
    балансов (`6000`). Пары `{r3}`→`{r2}` в списке быть не должно.
  - У всех величин в трёх ответах `currency: "RUB"` (`SP-028`) и парные поля `...Minor` /
    `...Formatted` (`SP-020`).
- **Разграничение зон:** арифметика балансов и долгов — зона агента B. Этот кейс проверяет
  **согласованность списка операций со сводками**: расхождение фиксируется как «история
  и сводки говорят разное», с указанием, какая из четырёх сверок не сошлась, и передаётся
  агенту B для квалификации, если не сходится именно расчёт.
- **Статус возможной находки:** **дефект против заказа** — заказ требует и «автоматический расчёт
  долгов», и «историю операций»; если эти две вещи противоречат друг другу, пользователь не может
  доверять ни одной.
- **Результат прогона:** `не прогнано — сессия прогона`

# XI. Спорные места для отчёта

1. **`403` против `404` (C-05).** `SP-116` предписывает `403 FORBIDDEN` на чужую существующую
   группу и `SP-104` — `404 NOT_FOUND` на несуществующую. Различие статусов сообщает
   обратившемуся факт существования группы с данным идентификатором. `SP-117` закрывает только
   содержимое, не факт существования. Ожидание зафиксировано по спеке (`403`), но выбор оракула
   выносится в отчёт: реализация, отвечающая `404` в обоих случаях, безопаснее и заказу
   не противоречит.
2. **Код отказа при нарушении уникальности имён (C-16, C-17) и при превышении предела
   в 20 участников (C-18).** `SP-042` и `SP-043` называют это ошибкой, но не называют код;
   `409 CONFLICT` и `400 VALIDATION_ERROR` оба принадлежат набору `SP-102`. Фиксируется выбор
   автора; несовпадение кодов между C-16 и C-17 отмечается как внутренняя непоследовательность.
3. **Приоритет проверки владения и проверки существования на вложенных путях.** Для запроса
   к чужой группе с несуществующим вложенным идентификатором спека не говорит, что проверяется
   первым. См. раздел X.
4. **Форма ответа на `POST .../pay` (C-31, шаг 13).** `SP-165` требует, чтобы отметка
   выполнялась отдельным вызовом, но статуса успеха не называет; `SP-109` допускает и `200`
   (изменение), и `201` (создание погашения). Фиксируется без квалификации как дефект.
5. **Путь `GET /api/groups/{gid}/participants` (C-23, шаг 2).** В таблице `SP-120` его нет,
   но интерфейсу список участников нужен; он доступен через `GET /api/groups/{gid}`.
   Реализация отдельного пути — расхождение с таблицей путей, а не дефект.

## С-C1. Именование полей и фактический контракт (закрывает `D-23`, `D-24`)

**Чего не хватало.** План C во всех запросах на создание и изменение расхода посылал
`"split":{"method":"equal","participants":[…]}` — вложенный объект, которого спека не задаёт,
— и, в отличие от планов A и B, **не объявлял соглашения об именовании**. На прогоне это
дало бы не пропуск дефекта, а его выдумывание: приложение с любым другим именованием
вернуло бы `400` там, где план ждёт `201`, и исполнитель записал бы «расход не создаётся»
как дефект. От этой схемы зависят фикстуры F1 и F2, то есть **все** кейсы
`C-01`…`C-06`, `C-20`…`C-22`, `C-33`…`C-38`.

**Соглашение, дословно повторяющее `С-1` плана A.** Схема имён в кейсах — рабочая. Перед
прогоном она сверяется с фактическим контрактом приложения; запрос переписывается,
кейс исполняется. **Несовпадение имён само по себе находкой не является** — спека имён
не задаёт. Находкой является поведение: какой статус, какой код ошибки, какие числа.
Исключение — требования, где спека называет имя прямо: `SP-020` (суффиксы `Minor`
и `Formatted`) и `SP-028` (поле `currency`); они проверяются буквально.

**Сверка выполнена в сессии 3** по `app/README.md` (раздел «API») и по ответам приложения;
исходники не читались. Единая таблица соответствия — `tests/plan-A.md`, § XII, соглашение
С-5, общая для трёх планов (`D-24`: до правки три автора независимо выдумали три
несовместимые схемы одного тела расхода, и фикстуры B и C, описывающие «одно и то же»
состояние, строились бы разными запросами). Существенное для зоны C:

- идентификация — `Authorization: Bearer <token>`, а не `X-User-Id`. Всюду, где в кейсах
  стоит `X-User-Id: u-alice`, при прогоне подставляется токен пользователя `u-alice`,
  полученный регистрацией. Кейс `C-08` (отсутствующий / пустой / пробельный заголовок)
  исполняется **и** над `X-User-Id`, **и** над фактическим заголовком: отсутствие
  `X-User-Id` как механизма — самостоятельное расхождение с `SP-140`, фиксируется один раз;
- участники — зарегистрированные пользователи, добавляются по email
  (`POST /api/groups/{id}/members`), а не заводятся именем. Кейсы `C-14`…`C-22` исполняются
  над `members`; отсутствие пути `/participants` — расхождение с `SP-120`, одна запись;
- истории по пути `/transactions` нет — есть `GET /api/groups/{id}/activity`;
- отдельного `/debts` нет — долги приходят полем `debts[]` внутри `/balances`, без статуса.

## Правка `D-36`: правило разворачивания фикстур

**Что было.** Общие фикстуры F1 и F2 объявлены как «готовятся один раз перед блоком кейсов»,
но далее мутируются: `C-21` удаляет участника из `{G1}`, `C-26` создаёт его заново и ждёт
состава из четырёх, `C-31` создаёт и удаляет участника и расход и проводит погашение,
`C-09`, `C-10`, `C-11`, `C-28` создают дополнительные группы тому же `u-alice`. Порядок
исполнения кейсов не задан нигде, правила отката между кейсами нет. Следствие: `C-07`
ждёт «ровно один элемент» и на корректном приложении провалится; `C-26` шаг 8 провалится,
если раньше отработал `C-21`, и наоборот; `C-29` невыполним в принципе. Исход доброй
половины плана определялся порядком запуска, а не поведением приложения.

**Правило, вводимое здесь (заимствовано у плана B, где оно выдержано во всех 31 кейсе):**

1. **Каждый кейс разворачивает собственную фикстуру в свежесозданной группе.** F1 и F2
   остаются описанием формы начального состояния, а не единственным экземпляром: кейс,
   ссылающийся на «фикстуру F1», создаёт свой экземпляр F1 и работает только с ним.
2. **Кейс, которому нужен свой пользователь, заводит своего пользователя.** `u-alice`
   и `u-bob` — роли, а не единственные учётные записи. Абсолютные счётчики групп
   допустимы только внутри собственного пользователя кейса.
3. **Абсолютные количества запрещены там, где считается общий для нескольких кейсов
   ресурс.** Счёт ведётся относительно зафиксированного перед шагами значения (`K`, `N`),
   как в плане A. Правка `D-38` в `C-11` — применение этого правила.
4. Кейсы, требующие чистого запуска процесса (`C-32`, `C-33`), исполняются на отдельном
   файле данных, задаваемом переменной окружения приложения, и останавливают процесс сами.
   Это не правка объекта: файл данных задаётся штатной переменной, `app/` не меняется.

## Правка `D-04` и `D-16`: `C-40`, история операций на странице

**Что было.** Шаг 6 `C-40` открывает раздел истории на группе, где нет ни расходов,
ни погашений, и ожидает «пустое состояние (текст вида «нет операций» **либо пустой
список**)». «Пустой список» в DOM ничем не отличается от отсутствия списка: и то и другое
даёт ноль найденных строк. Кейс засчитал бы страницу, где вкладка «История» есть,
а обработчик не реализован — клик не делает ничего. При этом историю **с записями**
не смотрит ни один UI-кейс ни в одном из трёх планов. Вместе это обнуляло проверку одного
из одиннадцати действий `SP-131`.

**Новая редакция шага 6 и продолжение кейса:**

- Шаг 6 требует **положительного признака** того, что раздел отработал: заголовок раздела
  по роли — `getByRole('heading', {name: /истори|операц/i})` — либо явный текст пустого
  состояния `getByText(/нет операций|пусто|операций пока нет/i)`. Ноль найденных строк
  без положительного признака — **провал**, а не «пустой список».
- Шаг 7 (новый): добавить через интерфейс один расход и провести одно погашение.
- Шаг 8 (новый): открыть историю. Ожидание: **две видимые строки**; каждая содержит текстом
  сумму с двумя знаками после точки и код валюты (`SP-133`); **новая — сверху** (`SP-182`:
  запись о погашении стоит выше записи о расходе). Одна строка вместо двух — расход
  и погашение не попадают в историю совместно (`SP-180`); обратный порядок — `SP-182`;
  строки без сумм или без валюты — `SP-133`.

## Правка `D-18`: `C-41`, редуцированный вид не отменяет проверку утечки

**Что было.** Оговорка «если интерфейс не позволяет обратиться к группе по произвольному
идентификатору вовсе, кейс выполняется в редуцированном виде: проверяется показ текста
ошибки на шаге 4» отменяла единственную UI-проверку `SP-117` решением, принимаемым по ходу
прогона. Утечка в другой форме — страница запрашивает `GET /api/groups` и рисует всё
полученное, а сервер по ошибке отдаёт чужое — при редуцированном виде не искалась бы вовсе.

**Новая редакция.** В редуцированном виде **остаётся обязательной** проверка списка
запрещённых строк L по **всему видимому тексту страницы** под `u-alice`: она не требует
обращения к чужой группе и потому исполнима всегда. Редуцируется только шаг 2
(обращение по произвольному идентификатору) — и его невозможность фиксируется как
ограничение интерфейса. Проверка `SP-117` не редуцируется ни при каких условиях.

## Правка `D-11`: `SP-100` и ответы `204` — объявленное сужение

`C-29` сужает проверку `Content-Type` до ответов `200`/`201`, исключая `204`, и нигде
этого сужения не объявляет. `SP-100` исключений не делает. Сужение остаётся в силе как
осознанное — у ответа `204` тела нет, — но объявляется здесь и вносится в § XI:
**`SP-100` против `SP-109`: у ответов `204` заголовок `Content-Type` не проверяется;
фактическое значение фиксируется наблюдением. Неоднозначность Н-3-Б.**

## Правка `D-35`: единая доктрина повышения статуса находки

Три плана применяли три несравнимые доктрины: A — от текста заказа, B — от тяжести
последствий, C — **условно и задним числом**, по исходу прогона (`C-06`: «если отождествление
даёт доступ к чужой группе, находка переклассифицируется»; `C-20`: «переклассифицировать,
**если** после удаления сумма долгов перестала сходиться»; `C-09`: «но если владелец
сменился, это дефект против заказа»). При сведении трёх отчётов в один список «дефектов
против заказа» попали бы находки, отобранные по трём несравнимым признакам.

**Принята доктрина плана A** (соглашение С-3) как единственная, опирающаяся на текст,
а не на оценку: дефект против заказа — только там, где отсутствует или неработоспособна
функция, названная в `ORDER.md` дословно; всякая характеристика её результата —
расхождение с оракулом. **Условная переклассификация допустима, когда условие
сформулировано через текст заказа, и запрещена, когда через тяжесть последствий:**
`C-06` («видит только свои группы» — дословно из заказа) остаётся как есть; `C-20`
(«сумма долгов перестала сходиться» — тяжесть) переводится в безусловное расхождение
с оракулом; `C-09` — остаётся: владение группой следует из «видит только свои группы».

## Правки `D-29`, `D-31`, `D-32`: чей вердикт по дублированным требованиям

Дублирование само по себе не порок — порок в двух вердиктах по одному требованию.
Отнесение фиксируется здесь и действует при сведении отчёта:

| Требование | Вердикт даёт | Контроль |
|---|---|---|
| `SP-058` (повторное удаление расхода) | `A-37` — расходы это зона A | `C-36` |
| `SP-095` (долг самому себе) | `B-10`, `B-11` | `C-24` шаг 5 |
| `SP-083`, `SP-082`, `SP-096` (нулевые балансы, пустые долги) | `B-02`, `B-24` | `C-23`, `C-24` — краевые составы, которых у B нет |
| доступность интерфейса (`A-46`, `B-37`, `C-42`) | одна сводная находка с перечнем элементов | три кейса — три наблюдения, не три находки |

`D-30` и `D-33` **отклонены как находки**: дублирование там объявлено авторами и полезно
(`C-23`/`C-24` дают краевые составы, которых нет у B; пять кейсов на `SP-133` различаются
валютой, копейками и знаком минуса). Правок в планы не вносится, правило сведения — выше.
