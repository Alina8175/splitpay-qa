# PLAN A — расход и распределение

**Агент:** A · **Зона:** `SP-010`–`SP-028` (деньги и валюта), `SP-050`–`SP-059` (расходы),
`SP-060`–`SP-076` (способы распределения и категория).
**Основание:** `SPEC.md` версия 1.2 (оракул) и `ORDER.md` (заказ).

> **Правило Р3.** Это **план**, а не отчёт. Всё, что записано в поле «Ожидаемый результат»,
> выведено из `SPEC.md` **до прогона** и ни одним символом не списано с поведения приложения.
> Кейс входит в сдаточный набор **только после сессии прогона**, когда поле «Результат прогона»
> заполнено фактом. Сейчас у всех кейсов там стоит `не прогнано — сессия прогона`, и это
> означает: набор ещё не сдан.

**Что при составлении плана не делалось:** код приложения не читался и не искался, приложение
не запускалось, HTTP-запросы не выполнялись, `.git` не трогался (ограничение О-1). Ожидания
получены арифметикой из требований.

## Соглашения

### С-1. Имена полей тела запроса и ответа

`SP-050` перечисляет **состав** полей расхода (плательщик, сумма, валюта, категория, описание,
способ распределения, состав распределения), но **не задаёт их идентификаторы**. `SP-020`
фиксирует только суффиксы `Minor`/`Formatted`, `SP-028` — имя `currency`. Поэтому в плане
используется каноническое именование:

| Смысл | Поле в плане |
|---|---|
| плательщик | `payerId` |
| сумма расхода | `amount` (строка, `SP-011`) |
| валюта | `currency` |
| категория | `category` |
| описание | `description` |
| способ распределения | `splitType` (`equal` / `percent` / `manual`) |
| состав, `equal` | `splitWith`: массив идентификаторов участников |
| состав, `percent` | `split`: массив `{participantId, percent}` |
| состав, `manual` | `split`: массив `{participantId, amount}` |
| начисление в ответе | `split[i].amountMinor`, `split[i].amountFormatted`, `split[i].currency` |

Перед прогоном каноническое именование сверяется с фактическим контрактом приложения
(страница `/` и README в поставке) и фиксируется таблицей соответствия в отчёте о прогоне.
**Несовпадение имён само по себе находкой не является** — спека имён не задаёт. Находкой
является поведение: какой статус, какой код ошибки, какие числа.

### С-2. Идентификаторы фикстур

`P1`, `Q1`, `G1` и т. п. — метки плана. Фактические значения подставляются из ответов на
запросы создания в фикстуре. Это связывание, а не плейсхолдер: числовые ожидания кейсов
от фактических идентификаторов не зависят.

### С-3. Два статуса находки

`ORDER.md` — единственное, что видел автор. Дословно в нём о моей зоне сказано: расход
распределяется **поровну / по процентам / вручную**, у расхода есть **сумма, валюта,
плательщик, категория, участники**, есть HTTP-API и HTML-страница. **Бизнес-правил заказчика
(округление, совпадение суммы распределения с суммой расхода, запрет нуля и отрицательной
суммы) в заказе НЕТ** — они есть только в оракуле, `SPEC.md` § 0.1.

Отсюда жёсткое деление:

- **Дефект против заказа** — только там, где нарушено перечисленное выше: отсутствует один из
  трёх способов распределения, отсутствует поле расхода из списка, страница не позволяет
  добавить расход.
- **Расхождение с оракулом** — всё остальное в этой зоне: адресность копейки, метод наибольшего
  остатка, `Minor`/`Formatted`, набор валют, коды ошибок, отказ по нулю и минусу, отказ по
  чужому участнику, значения по умолчанию.

Смешивать нельзя: первое — вина автора, второе — цена того, что автору оракул не передавали.

### С-4. Заголовки

Все запросы: `X-User-Id: qa-agent-a`, `Content-Type: application/json`.
Все группы плана принадлежат **одному** пользователю `qa-agent-a` — намеренно: иначе
обращение к «чужой» группе дало бы `403` (`SP-116`) и подменило бы проверяемую причину отказа.

## Фикстуры

Каждая фикстура — последовательность запросов. Порядок добавления участников значим
(`SP-006`, `SP-062`, `SP-067`) и в кейсах используется как есть.

**Ф1 — `G1`, RUB, трое.**
1. `POST /api/groups` `{"name":"Поездка","currency":"RUB"}` → `G1`
2. `POST /api/groups/{G1}/participants` `{"name":"Аня"}` → `P1`
3. `POST /api/groups/{G1}/participants` `{"name":"Борис"}` → `P2`
4. `POST /api/groups/{G1}/participants` `{"name":"Вера"}` → `P3`

Порядок добавления: **Аня (P1) → Борис (P2) → Вера (P3)**.

**Ф2 — `G2`, USD, двое.**
`POST /api/groups` `{"name":"Trip USD","currency":"USD"}` → `G2`; участники `{"name":"Ann"}` → `Q1`,
`{"name":"Bob"}` → `Q2`.

**Ф3 — `G3`, без поля валюты при создании, двое.**
`POST /api/groups` `{"name":"Без валюты"}` → `G3`; участники `{"name":"Дима"}` → `R1`,
`{"name":"Егор"}` → `R2`.

**Ф4 — `G4`, RUB, четверо.**
`POST /api/groups` `{"name":"Квартира","currency":"RUB"}` → `G4`; участники по порядку:
`Ася` → `S1`, `Боря` → `S2`, `Витя` → `S3`, `Гена` → `S4`.

**Ф5 — `G5`, RUB, семеро.**
`POST /api/groups` `{"name":"Семеро","currency":"RUB"}` → `G5`; участники по порядку:
`Уч1` → `M1`, `Уч2` → `M2`, `Уч3` → `M3`, `Уч4` → `M4`, `Уч5` → `M5`, `Уч6` → `M6`, `Уч7` → `M7`.

Фикстуры Ф1, Ф2, Ф4, Ф5 предполагают, что группа создаётся с валютой без ошибки; отказ на
шаге фикстуры сам по себе — находка соседней зоны, кейс в этом случае помечается
заблокированным, а не проваленным. Ф3 — не только фикстура, но и часть кейса **A-28**.

# I. Распределение поровну и адресность копейки

### A-01 · 100,00 на троих поровну: копейка достаётся первому добавленному
- **Требования:** SP-062, SP-063, SP-061, SP-076, SP-050, SP-020, SP-021, SP-028, SP-010
- **Уровень:** API
- **Предусловие:** Ф1. Группа `G1`, валюта `RUB`, участники в порядке добавления: Аня (`P1`),
  Борис (`P2`), Вера (`P3`). Расходов в группе нет.
- **Шаги:**
  1. `POST /api/groups/{G1}/expenses`, `X-User-Id: qa-agent-a`, тело:
     `{"payerId":"P1","amount":"100.00","currency":"RUB","category":"food","description":"Ужин","splitType":"equal","splitWith":["P1","P2","P3"]}`
  2. `GET /api/groups/{G1}/expenses`, `X-User-Id: qa-agent-a`
- **Ожидаемый результат:**
  Шаг 1 — `201`. В теле: `amountMinor: 10000`, `amountFormatted: "100.00"`, `currency: "RUB"`,
  `category: "food"`, `splitType: "equal"`. Состав распределения — ровно три начисления:
  - Аня `P1` — `3334` / `"33.34"` / `"RUB"`
  - Борис `P2` — `3333` / `"33.33"` / `"RUB"`
  - Вера `P3` — `3333` / `"33.33"` / `"RUB"`

  Сумма начислений `3334 + 3333 + 3333 = 10000` = `"100.00"` ровно (`SP-063`, `SP-076`).
  Лишняя копейка — **у Ани**, первой добавленной, а не у Бориса, не у Веры и не у плательщика
  как такового (`SP-062`). Все `*Minor` — целые числа без дробной части (`SP-010`).
  Шаг 2 — `200`, те же числа.
  Отсекается: `33.33/33.33/33.33` (итог `99.99`), `33.34` всем (`100.02`),
  `33.33/33.33/33.34` (копейка последнему), `33.33/33.34/33.33` (копейка среднему),
  `amountFormatted: "100"` или `"100.0"` (`SP-021`), отсутствие `currency` у начислений (`SP-028`).
- **Статус возможной находки:** **расхождение с оракулом** — про адрес остатка и про пару
  `Minor`/`Formatted` в заказе нет ни слова, автор выбирал сам.
- **Результат прогона:** `не прогнано — сессия прогона`

### A-02 · Повторяемость: тот же расход дважды даёт то же распределение
- **Требования:** SP-062, SP-063, SP-076
- **Уровень:** API
- **Предусловие:** Ф1, после **A-01** (в группе один расход на `"100.00"`).
- **Шаги:**
  1. `POST /api/groups/{G1}/expenses` с телом, **побайтово тем же**, что в A-01 шаг 1.
  2. `GET /api/groups/{G1}/expenses`
- **Ожидаемый результат:**
  Шаг 1 — `201`, распределение второго расхода: `P1` `3334` / `"33.34"`, `P2` `3333` / `"33.33"`,
  `P3` `3333` / `"33.33"`. Шаг 2 — два расхода, у обоих **идентичный** состав начислений
  по участникам и суммам; идентификаторы расходов при этом различны.
  Отсекается: чередование получателя остатка («в этот раз копейку следующему»), раздача
  остатка по случайному участнику, привязка остатка к времени создания или к порядку в хеш-таблице.
- **Статус возможной находки:** **расхождение с оракулом** — воспроизводимость раздачи остатка
  в заказе не оговорена.
- **Результат прогона:** `не прогнано — сессия прогона`

### A-03 · Повторяемость через перезапуск процесса
- **Требования:** SP-062, SP-063 (контекст `SP-007`)
- **Уровень:** API
- **Предусловие:** Ф1, после **A-01** и **A-02** (два расхода по `"100.00"`).
- **Шаги:**
  1. `GET /api/groups/{G1}/expenses` — зафиксировать оба состава начислений.
  2. Остановить процесс сервера; запустить заново `node app/server.js`.
  3. `GET /api/groups/{G1}/expenses` — сравнить с шагом 1.
- **Ожидаемый результат:**
  После перезапуска оба расхода на месте, у каждого начисления `3334` / `3333` / `3333`
  на `P1` / `P2` / `P3` соответственно, `amountFormatted` `"33.34"` / `"33.33"` / `"33.33"`,
  итог по каждому расходу `10000` = `"100.00"`. Состав побайтово совпадает с шагом 1
  (за исключением полей, которые спека не фиксирует, — они сравниваются по значению, а не по
  форме сериализации).
  Отсекается: пересчёт распределения при чтении из файла с другим адресом копейки, потеря
  состава распределения при сериализации, хранение долей как чисел с плавающей точкой
  с восстановлением `33.333333` (`SP-010`).
- **Статус возможной находки:** **расхождение с оракулом** — заказ требует лишь хранения
  в JSON-файле, а неизменность распределения через перезапуск — требование оракула.
- **Результат прогона:** `не прогнано — сессия прогона`

### A-04 · Порядок в запросе обратный порядку добавления — копейка всё равно первому добавленному
- **Требования:** SP-062 (контекст `SP-006`)
- **Уровень:** API
- **Предусловие:** Ф1. Порядок добавления: `P1` → `P2` → `P3`.
- **Шаги:**
  1. `POST /api/groups/{G1}/expenses`
     `{"payerId":"P3","amount":"100.00","currency":"RUB","category":"other","description":"","splitType":"equal","splitWith":["P3","P2","P1"]}`
- **Ожидаемый результат:**
  `201`. Начисления: `P1` — `3334` / `"33.34"`, `P2` — `3333` / `"33.33"`, `P3` — `3333` / `"33.33"`.
  Итог `10000` = `"100.00"`. Копейка у Ани (`P1`), **несмотря на то что в запросе она названа
  последней и плательщик — Вера**.
  Отсекается: раздача остатка по порядку массива `splitWith` (дала бы копейку `P3`), раздача
  остатка плательщику (`P3`), сортировка состава по идентификатору или по имени.
- **Статус возможной находки:** **расхождение с оракулом** — «порядок добавления в группу»
  задан только оракулом (`SP-062`).
- **Результат прогона:** `не прогнано — сессия прогона`

### A-05 · Одна копейка на троих
- **Требования:** SP-064, SP-019, SP-062, SP-063
- **Уровень:** API
- **Предусловие:** Ф1.
- **Шаги:**
  1. `POST /api/groups/{G1}/expenses`
     `{"payerId":"P1","amount":"0.01","currency":"RUB","category":"other","description":"копейка","splitType":"equal","splitWith":["P1","P2","P3"]}`
- **Ожидаемый результат:**
  `201` (минимальная сумма `"0.01"` принимается, `SP-019`). `amountMinor: 1`,
  `amountFormatted: "0.01"`. Начисления — **три записи**, ни одна не выброшена:
  `P1` — `1` / `"0.01"`, `P2` — `0` / `"0.00"`, `P3` — `0` / `"0.00"`. Итог `1` = `"0.01"`.
  Отсекается: отказ `400` на «слишком маленькой» сумме, возврат состава из одного участника
  с ненулевой долей, `"0.00"` у всех троих (итог `0`), `"0.01"` каждому (итог `"0.03"`),
  `amountFormatted: "0"` вместо `"0.00"` (`SP-021`).
- **Статус возможной находки:** **расхождение с оракулом** — граница в одну копейку и
  требование сохранять нулевые доли в составе — из оракула.
- **Результат прогона:** `не прогнано — сессия прогона`

### A-06 · Остаток больше единицы раздаётся по одной, а не целиком первому
- **Требования:** SP-062, SP-063, SP-076
- **Уровень:** API
- **Предусловие:** Ф1 (для шага 1) и Ф5 (для шага 2). В `G5` порядок добавления
  `M1` → `M2` → `M3` → `M4` → `M5` → `M6` → `M7`.
- **Шаги:**
  1. `POST /api/groups/{G1}/expenses`
     `{"payerId":"P1","amount":"0.05","currency":"RUB","category":"other","description":"пять копеек","splitType":"equal","splitWith":["P1","P2","P3"]}`
  2. `POST /api/groups/{G5}/expenses`
     `{"payerId":"M1","amount":"10.00","currency":"RUB","category":"transport","description":"такси","splitType":"equal","splitWith":["M1","M2","M3","M4","M5","M6","M7"]}`
- **Ожидаемый результат:**
  Шаг 1 — `201`. `5 ÷ 3 = 1`, остаток `2`, две копейки уходят первым двум по порядку добавления:
  `P1` — `2` / `"0.02"`, `P2` — `2` / `"0.02"`, `P3` — `1` / `"0.01"`. Итог `5` = `"0.05"`.
  Шаг 2 — `201`. `1000 ÷ 7 = 142`, остаток `6`, шесть копеек — первым шести:
  `M1`…`M6` — по `143` / `"1.43"`, `M7` — `142` / `"1.42"`. Итог
  `143 × 6 + 142 = 1000` = `"10.00"`.
  Отсекается: выдача всего остатка первому (`P1` `3`/`"0.03"`; `M1` `148`/`"1.48"`), выдача
  остатка последнему, отбрасывание остатка (итог `0.03` и `9.94`), округление вверх для всех
  (итог `0.06` и `10.01`).
- **Статус возможной находки:** **расхождение с оракулом** — алгоритм раздачи остатка задан
  только `SP-062`.
- **Результат прогона:** `не прогнано — сессия прогона`

### A-07 · Состав — подмножество группы: порядок считается по группе, а не по составу
- **Требования:** SP-052, SP-062, SP-063
- **Уровень:** API
- **Предусловие:** Ф1. Порядок добавления `P1` → `P2` → `P3`; в составе только `P2` и `P3`.
- **Шаги:**
  1. `POST /api/groups/{G1}/expenses`
     `{"payerId":"P1","amount":"0.05","currency":"RUB","category":"other","description":"двое из троих","splitType":"equal","splitWith":["P3","P2"]}`
- **Ожидаемый результат:**
  `201`. Состав распределения — ровно две записи, `P1` в нём отсутствует.
  `5 ÷ 2 = 2`, остаток `1`, копейка — **Борису (`P2`)**, потому что из двоих он добавлен в группу
  раньше: `P2` — `3` / `"0.03"`, `P3` — `2` / `"0.02"`. Итог `5` = `"0.05"`.
  Отсекается: копейка `P3` (порядок массива запроса), копейка `P1` (первый в группе, но не в
  составе — начислять ему нечего), включение `P1` в состав с нулевой долей.
- **Статус возможной находки:** **расхождение с оракулом** — что «порядок добавления»
  применяется к подмножеству состава, следует из `SP-062` + `SP-052`, в заказе этого нет.
- **Результат прогона:** `не прогнано — сессия прогона`

# II. Сумма расхода: формат и границы

### A-08 · Нулевая сумма
- **Требования:** SP-016
- **Уровень:** API
- **Предусловие:** Ф1, число расходов в группе зафиксировано перед шагами (`N`).
- **Шаги:**
  1. `POST /api/groups/{G1}/expenses`
     `{"payerId":"P1","amount":"0","currency":"RUB","category":"other","description":"ноль","splitType":"equal","splitWith":["P1","P2","P3"]}`
  2. `POST /api/groups/{G1}/expenses`
     `{"payerId":"P1","amount":"0.00","currency":"RUB","category":"other","description":"ноль с копейками","splitType":"equal","splitWith":["P1","P2","P3"]}`
  3. `GET /api/groups/{G1}/expenses`
- **Ожидаемый результат:**
  Шаги 1 и 2 — `400`, тело `{"error":{"code":"VALIDATION_ERROR","message":"…"}}`, сообщение
  называет поле суммы (`"amount"`) или причину «сумма должна быть больше нуля».
  Шаг 3 — расходов по-прежнему `N`: ни один из отклонённых расходов не создан.
  Отсекается: `201` с `amountMinor: 0` и тремя нулевыми начислениями; `400` с кодом вне набора
  `SP-102`; `500`.
- **Статус возможной находки:** **расхождение с оракулом** — правило «нельзя создать расход
  с нулевой суммой» есть в постановке заказчика (`SPEC.md` § 0.1), но в `ORDER.md` его нет,
  автору его не передавали.
- **Результат прогона:** `не прогнано — сессия прогона`

### A-09 · Отрицательная сумма
- **Требования:** SP-017
- **Уровень:** API
- **Предусловие:** Ф1, число расходов `N` зафиксировано.
- **Шаги:**
  1. `POST /api/groups/{G1}/expenses`
     `{"payerId":"P1","amount":"-1.00","currency":"RUB","category":"other","description":"минус","splitType":"equal","splitWith":["P1","P2","P3"]}`

### A-15 · Целочисленность арифметики: три ловушки плавающей точки
- **Требования:** SP-010, SP-071, SP-066
- **Уровень:** API
- **Предусловие:** Ф1.
- **Шаги:**
  1. `POST /api/groups/{G1}/expenses`
     `{"payerId":"P1","amount":"0.30","currency":"RUB","category":"other","description":"десятая и пятая","splitType":"manual","split":[{"participantId":"P1","amount":"0.10"},{"participantId":"P2","amount":"0.20"}]}`
  2. `POST /api/groups/{G1}/expenses`
     `{"payerId":"P1","amount":"1.00","currency":"RUB","category":"other","description":"семь и девяносто три","splitType":"manual","split":[{"participantId":"P1","amount":"0.07"},{"participantId":"P2","amount":"0.93"}]}`
  3. `POST /api/groups/{G1}/expenses`
     `{"payerId":"P1","amount":"100.00","currency":"RUB","category":"other","description":"три трети","splitType":"percent","split":[{"participantId":"P1","percent":"33.33"},{"participantId":"P2","percent":"33.33"},{"participantId":"P3","percent":"33.34"}]}`
- **Ожидаемый результат:**
  Шаг 1 — `201`: `10 + 20 = 30` копеек ровно. `P1` — `10` / `"0.10"`, `P2` — `20` / `"0.20"`,
  итог `30` = `"0.30"`.
  Шаг 2 — `201`: `7 + 93 = 100` копеек ровно. `P1` — `7` / `"0.07"`, `P2` — `93` / `"0.93"`,
  итог `100` = `"1.00"`.
  Шаг 3 — `201`: сумма процентов `33.33 + 33.33 + 33.34 = 100.00` ровно, принимается
  (`SP-066`). Начисления: `10000 × 33.33 ÷ 100 = 3333` (дробной части нет),
  `3333`, `10000 × 33.34 ÷ 100 = 3334`. Остатка нет. `P1` — `3333` / `"33.33"`,
  `P2` — `3333` / `"33.33"`, `P3` — `3334` / `"33.34"`, итог `10000` = `"100.00"`.
  Отсекается ровно то, что даёт арифметика в `double`: `0.1 + 0.2 = 0.30000000000000004`,
  `0.07 + 0.93 = 1.0000000000000002`, `33.33 + 33.33 + 33.34 = 100.00000000000001` — при
  сравнении с `0.3`, `1` и `100` без приведения к целым все три валидных запроса будут
  **ошибочно отклонены** с `VALIDATION_ERROR`. Это внешняя, не заглядывающая в код проверка
  `SP-010`.
- **Статус возможной находки:** **расхождение с оракулом** — хранение и счёт в целых копейках
  требует `SP-010`; заказ говорит лишь «данные в JSON-файле».
- **Результат прогона:** `не прогнано — сессия прогона`

### A-16 · Проценты 33 / 33 / 34 на 100,00
- **Требования:** SP-065, SP-066, SP-067, SP-068, SP-076
- **Уровень:** API

  и вручную» сказано в `ORDER.md` дословно. Если поддержаны, но числа иные — **расхождение
  с оракулом**.
- **Результат прогона:** `не прогнано — сессия прогона`

### A-17 · Те же проценты 33 / 33 / 34 на сумму, которая на них не делится
- **Требования:** SP-067, SP-068, SP-076
- **Уровень:** API
- **Предусловие:** Ф1, порядок `P1` → `P2` → `P3`.
- **Шаги:**
  1. `POST /api/groups/{G1}/expenses`
     `{"payerId":"P1","amount":"0.07","currency":"RUB","category":"food","description":"семь копеек по процентам","splitType":"percent","split":[{"participantId":"P1","percent":"33"},{"participantId":"P2","percent":"33"},{"participantId":"P3","percent":"34"}]}`
- **Ожидаемый результат:**
  `201`. Расчёт по методу наибольшего остатка (`SP-067`):
  `7 × 33 ÷ 100 = 2.31` → целая часть `2`, дробная `0.31`;
  `7 × 33 ÷ 100 = 2.31` → `2`, дробная `0.31`;
  `7 × 34 ÷ 100 = 2.38` → `2`, дробная `0.38`.
  Сумма целых частей `6`, остаток `1` копейка. Наибольшая дробная часть — `0.38` у `P3`.
  Начисления: `P1` — `2` / `"0.02"`, `P2` — `2` / `"0.02"`, `P3` — `3` / `"0.03"`.
  Итог `7` = `"0.07"` (`SP-068`).
  Отсекается: наивное округление до ближайшего (`2 + 2 + 2 = 6` — потеря копейки, итог `"0.06"`);
  округление вверх (`3 + 3 + 3 = 9`, итог `"0.09"`); выдача остатка первому добавленному
  (`0.03/0.02/0.02`) — здесь метод наибольшего остатка и порядок добавления дают **разный**
  ответ, и кейс их различает.
- **Статус возможной находки:** **расхождение с оракулом** — метод наибольшего остатка задан
  только `SP-067`.
- **Результат прогона:** `не прогнано — сессия прогона`

  и нетерпимость к сотой доле процента заданы только `SP-066`.
- **Результат прогона:** `не прогнано — сессия прогона`

### A-21 · Формат и диапазон отдельного процента
- **Требования:** SP-065, SP-066
- **Уровень:** API
- **Предусловие:** Ф1, число расходов `N` зафиксировано.
- **Шаги:** для каждой строки — отдельный `POST /api/groups/{G1}/expenses`, тело
  `{"payerId":"P1","amount":"100.00","currency":"RUB","category":"other","description":"формат процента","splitType":"percent","split":<состав>}`.

  | № | Состав | Почему отказ |
  |---|---|---|
  | 1 | `[{"participantId":"P1","percent":"33,33"},{"participantId":"P2","percent":"33.33"},{"participantId":"P3","percent":"33.34"}]` | запятая, SP-065 (формат сумм, SP-014) |
  | 2 | `[{"participantId":"P1","percent":"33.333"},{"participantId":"P2","percent":"33.333"},{"participantId":"P3","percent":"33.334"}]` | три знака, SP-065 |
  | 3 | `[{"participantId":"P1","percent":"100.00"},{"participantId":"P2","percent":"0.00"},{"participantId":"P3","percent":"0.00"}]` | процент ниже `"0.01"`, SP-065 |
  | 4 | `[{"participantId":"P1","percent":"-10.00"},{"participantId":"P2","percent":"60.00"},{"participantId":"P3","percent":"50.00"}]` | отрицательный процент, SP-065 |
  | 5 | `[{"participantId":"P1","percent":33.33},{"participantId":"P2","percent":33.33},{"participantId":"P3","percent":33.34}]` | число вместо строки, SP-065 |

  Затем шаг 6: `POST /api/groups/{G1}/expenses`
  `{"payerId":"P1","amount":"100.00","currency":"RUB","category":"other","description":"весь процент одному","splitType":"percent","split":[{"participantId":"P1","percent":"100.00"}]}`
- **Ожидаемый результат:**
  Строки 1–5 — `400`, `VALIDATION_ERROR`, сообщение называет процент или участника, у которого
  он неверен. Шаг 6 — `201`: состав из одного участника допустим (`SP-052` требует лишь
  непустоты), `P1` — `10000` / `"100.00"`, итог `10000`.
  Отсекается: приём `"33,33"` как `33.33`; приём трёх знаков с округлением; приём нулевого
  процента (`SP-065` задаёт нижнюю границу `"0.01"`, а не `"0.00"`); приём отрицательного
  процента с компенсацией у других (сумма-то `100.00`!) — строка 4 специально сделана суммой
  ровно `100.00`, чтобы проверка суммы её не поймала и отказ шёл именно по диапазону;
  падение на нестроковом значении.
- **Статус возможной находки:** **расхождение с оракулом** — формат и диапазон процента
  заданы только `SP-065`.
- **Результат прогона:** `не прогнано — сессия прогона`

# IV. Ручное распределение

### A-22 · Ручное распределение, сумма частей совпадает
- **Требования:** SP-069, SP-071, SP-076, SP-020
- **Уровень:** API
- **Предусловие:** Ф1.
- **Шаги:**
  1. `POST /api/groups/{G1}/expenses`
     `{"payerId":"P2","amount":"100.00","currency":"RUB","category":"housing","description":"вручную 50/30/20","splitType":"manual","split":[{"participantId":"P1","amount":"50.00"},{"participantId":"P2","amount":"30.00"},{"participantId":"P3","amount":"20.00"}]}`
- **Ожидаемый результат:**
  `201`. `5000 + 3000 + 2000 = 10000` — совпадает с суммой расхода (`SP-071`).
  Начисления: `P1` — `5000` / `"50.00"` / `"RUB"`, `P2` — `3000` / `"30.00"` / `"RUB"`,
  `P3` — `2000` / `"20.00"` / `"RUB"`. `amountMinor: 10000`, `amountFormatted: "100.00"`.
  Отсекается: перераспределение заданных вручную сумм поровну; сортировка состава,
  меняющая привязку сумм к участникам (например `P1` получает `20.00`); `amountFormatted`
  без двух знаков.
- **Статус возможной находки:** если `splitType: "manual"` не поддержан вовсе — **дефект
  против заказа** («и вручную» сказано дословно). Если поддержан, но числа привязаны к другим
  участникам — **расхождение с оракулом**.
- **Результат прогона:** `не прогнано — сессия прогона`

### A-23 · Ручное распределение с остатком: сумма частей ≠ сумме расхода
- **Требования:** SP-071, SP-076
- **Уровень:** API
- **Предусловие:** Ф1, число расходов `N` зафиксировано.
- **Шаги:**
  1. `POST /api/groups/{G1}/expenses`
     `{"payerId":"P1","amount":"100.00","currency":"RUB","category":"other","description":"недобор копейки","splitType":"manual","split":[{"participantId":"P1","amount":"33.33"},{"participantId":"P2","amount":"33.33"},{"participantId":"P3","amount":"33.33"}]}`
  2. `POST /api/groups/{G1}/expenses`
     `{"payerId":"P1","amount":"100.00","currency":"RUB","category":"other","description":"перебор копейки","splitType":"manual","split":[{"participantId":"P1","amount":"33.34"},{"participantId":"P2","amount":"33.33"},{"participantId":"P3","amount":"33.34"}]}`
  3. `POST /api/groups/{G1}/expenses`
     `{"payerId":"P1","amount":"100.00","currency":"RUB","category":"other","description":"крупный недобор","splitType":"manual","split":[{"participantId":"P1","amount":"50.00"},{"participantId":"P2","amount":"20.00"}]}`
  4. `GET /api/groups/{G1}/expenses`
- **Ожидаемый результат:**
  Шаг 1 — `400`, `VALIDATION_ERROR`: `3333 × 3 = 9999 ≠ 10000`, недобор ровно **одна
  минимальная единица** — этого достаточно для отказа (`SP-071`).
  Шаг 2 — `400`, `VALIDATION_ERROR`: `3334 + 3333 + 3334 = 10001 ≠ 10000`, перебор одна копейка.
  Шаг 3 — `400`, `VALIDATION_ERROR`: `5000 + 2000 = 7000 ≠ 10000`.
  Шаг 4 — расходов `N`, ни один из трёх не создан.
  Отсекается: «дораспределение» остатка последнему/первому (`201` с `33.33/33.33/33.34`);
  подтягивание суммы расхода под сумму частей (`201` с `amountFormatted: "99.99"` или
  `"70.00"`); приём с молчаливой потерей копейки; допуск «погрешности» в одну копейку;
  `409` вместо `400` (`SP-103` требует `VALIDATION_ERROR`/`400`).
- **Статус возможной находки:** **расхождение с оракулом** — правило «сумма распределения
  совпадает с суммой расхода» есть в постановке заказчика, но в `ORDER.md` не передано.
- **Результат прогона:** `не прогнано — сессия прогона`

### A-24 · Ручное распределение: ноль допускается
- **Требования:** SP-070, SP-071
- **Уровень:** API
- **Предусловие:** Ф1.
- **Шаги:**
  1. `POST /api/groups/{G1}/expenses`
     `{"payerId":"P1","amount":"100.00","currency":"RUB","category":"other","description":"всё на одного","splitType":"manual","split":[{"participantId":"P1","amount":"100.00"},{"participantId":"P2","amount":"0.00"},{"participantId":"P3","amount":"0.00"}]}`
- **Ожидаемый результат:**
  `201`. `10000 + 0 + 0 = 10000` (`SP-071`). Состав — **три** записи, нулевые не выброшены:
  `P1` — `10000` / `"100.00"`, `P2` — `0` / `"0.00"`, `P3` — `0` / `"0.00"`.
  Отсекается: `400` на нулевой части (правило `SP-016` про сумму расхода ошибочно
  перенесённое на части распределения — самое вероятное неверное поведение); выбрасывание
  нулевых участников из состава; `amountFormatted: "0"` вместо `"0.00"`.
- **Статус возможной находки:** **расхождение с оракулом** — что ноль в ручном распределении
  допустим, сказано только в `SP-070`.
- **Результат прогона:** `не прогнано — сессия прогона`

### A-25 · Ручное распределение: отрицательная часть при верной общей сумме
- **Требования:** SP-070
- **Уровень:** API
- **Предусловие:** Ф1, число расходов `N` зафиксировано.
- **Шаги:**
  1. `POST /api/groups/{G1}/expenses`
     `{"payerId":"P1","amount":"100.00","currency":"RUB","category":"other","description":"минус десять","splitType":"manual","split":[{"participantId":"P1","amount":"110.00"},{"participantId":"P2","amount":"-10.00"},{"participantId":"P3","amount":"0.00"}]}`
  2. `GET /api/groups/{G1}/expenses`
- **Ожидаемый результат:**
  Шаг 1 — `400`, `VALIDATION_ERROR`, сообщение называет участника `P2` или отрицательную
  часть. Шаг 2 — расходов `N`.
  Ключ кейса: общая сумма частей `11000 − 1000 + 0 = 10000` **совпадает** с суммой расхода,
  поэтому проверка `SP-071` эту ситуацию не ловит — отказ обязан идти именно по `SP-070`.
  Отсекается: реализация, проверяющая только итог (вернёт `201` с начислением `−10.00`);
  взятие модуля (`110.00/10.00/0.00`, итог `120.00`).
- **Статус возможной находки:** **расхождение с оракулом** — запрет отрицательной части
  задан только `SP-070`.
- **Результат прогона:** `не прогнано — сессия прогона`

### A-26 · Ручное распределение: формат части
- **Требования:** SP-069
- **Уровень:** API
- **Предусловие:** Ф1, число расходов `N` зафиксировано.
- **Шаги:** отдельный `POST /api/groups/{G1}/expenses` на каждую строку, тело
  `{"payerId":"P1","amount":"100.00","currency":"RUB","category":"other","description":"формат части","splitType":"manual","split":<состав>}`.

  | № | Состав | Почему отказ |
  |---|---|---|
  | 1 | `[{"participantId":"P1","amount":"33.333"},{"participantId":"P2","amount":"33.333"},{"participantId":"P3","amount":"33.334"}]` | три знака, SP-069 → SP-012 |
  | 2 | `[{"participantId":"P1","amount":"50,00"},{"participantId":"P2","amount":"30.00"},{"participantId":"P3","amount":"20.00"}]` | запятая, SP-069 → SP-014 |
  | 3 | `[{"participantId":"P1","amount":50},{"participantId":"P2","amount":30},{"participantId":"P3","amount":20}]` | число вместо строки, SP-069 → SP-011 |

- **Ожидаемый результат:**
  Все три — `400`, `VALIDATION_ERROR`, сообщение называет часть распределения или участника.
  `GET` в конце — расходов `N`.
  Строка 1 отдельно ценна: `33.333 + 33.333 + 33.334 = 100.000`, то есть общая сумма сходится,
  и отказ обязан идти по формату части, а не по `SP-071`.
  Отсекается: округление трёх знаков до двух с приёмом (`33.33/33.33/33.33` — и молчаливой
  потерей копейки); приём числовых значений; падение процесса.
- **Статус возможной находки:** **расхождение с оракулом** — «в том же формате, что и сумма
  расхода» задано `SP-069`, в заказе формата нет.
- **Результат прогона:** `не прогнано — сессия прогона`

# V. Валюта

### A-27 · Расход в валюте, отличной от валюты группы
- **Требования:** SP-026
- **Уровень:** API
- **Предусловие:** Ф1 (`G1`, валюта `RUB`) и Ф2 (`G2`, валюта `USD`), обе группы у
  `qa-agent-a`. Число расходов в `G1` — `N`, в `G2` — `M`.
- **Шаги:**
  1. `POST /api/groups/{G1}/expenses`
     `{"payerId":"P1","amount":"100.00","currency":"USD","category":"food","description":"доллары в рублёвой группе","splitType":"equal","splitWith":["P1","P2","P3"]}`
  2. `POST /api/groups/{G2}/expenses`
     `{"payerId":"Q1","amount":"100.00","currency":"RUB","category":"food","description":"рубли в долларовой группе","splitType":"equal","splitWith":["Q1","Q2"]}`
  3. `GET /api/groups/{G1}/expenses` и `GET /api/groups/{G2}/expenses`
- **Ожидаемый результат:**
  Шаги 1 и 2 — `400`, `VALIDATION_ERROR`, сообщение называет валюту и несовпадение с валютой
  группы. Шаг 3 — в `G1` расходов `N`, в `G2` — `M`.
  Отсекается: `201` с сохранением `currency: "USD"` в рублёвой группе (мультивалютная группа —
  прямо вне рамок, `SPEC.md` часть III); `201` с конвертацией по какому бы то ни было курсу
  (любое `amountMinor ≠ 10000` при `201` — отдельная, более тяжёлая находка: обращение к курсам
  означало бы сеть, что запрещено заказом); `201` с молчаливой заменой валюты расхода на
  валюту группы (`currency: "RUB"`, `amountMinor: 10000`) — это тоже провал: `SP-026`
  требует **отказа**, а не подмены; `409` вместо `400`.
- **Статус возможной находки:** **расхождение с оракулом** — заказ говорит «у расхода есть
  валюта» и молчит о связи с валютой группы; запрет конвертации задан `SP-026` и частью III.
  Если же обнаружится обращение в сеть за курсом — это уже **дефект против заказа**
  («интернета нет», «только встроенные модули»).
- **Результат прогона:** `не прогнано — сессия прогона`

### A-28 · Валюта по умолчанию: у группы и у расхода
- **Требования:** SP-024, SP-027, SP-025, SP-026
- **Уровень:** API
- **Предусловие:** Ф3 — группа `G3` создана телом **без поля** `currency`:
  `POST /api/groups` `{"name":"Без валюты"}`; участники `Дима` (`R1`), `Егор` (`R2`).
- **Шаги:**
  1. `GET /api/groups/{G3}` — прочитать валюту группы.
  2. `POST /api/groups/{G3}/expenses` **без поля** `currency`:
     `{"payerId":"R1","amount":"10.00","category":"food","description":"без валюты","splitType":"equal","splitWith":["R1","R2"]}`
  3. `POST /api/groups/{G3}/expenses`
     `{"payerId":"R1","amount":"10.00","currency":"USD","category":"food","description":"доллары","splitType":"equal","splitWith":["R1","R2"]}`
- **Ожидаемый результат:**
  Шаг 1 — `200`, валюта группы `"RUB"` (подставлена по `SP-024`), не `null`, не пусто,
  не `"USD"`.
  Шаг 2 — `201`, у расхода поле валюты присутствует (`SP-025`) и равно `"RUB"` — валюте группы
  (`SP-027`). `amountMinor: 1000`, `amountFormatted: "10.00"`, начисления
  `R1` — `500` / `"5.00"` / `"RUB"`, `R2` — `500` / `"5.00"` / `"RUB"`, итог `1000`.
  Шаг 3 — `400`, `VALIDATION_ERROR`: валюта группы `RUB`, `USD` не совпадает (`SP-026`).
  Отсекается: отказ при создании группы без валюты; валюта группы `null`/`""`/`"USD"`;
  расход без поля валюты вовсе (`SP-025`); отказ на расходе без `currency` («поле обязательно»)
  — `SP-027` требует подстановки, а не отказа; приём `USD` в группе, чья валюта подставлена
  по умолчанию.
- **Статус возможной находки:** отсутствие поля валюты у расхода — **дефект против заказа**
  («у расхода есть сумма, валюта, …» сказано дословно). Значение по умолчанию `RUB` и отказ
  по `USD` — **расхождение с оракулом**.
- **Результат прогона:** `не прогнано — сессия прогона`

### A-30 · Код валюты при каждой денежной величине ответа
- **Требования:** SP-028, SP-025, SP-020, SP-021, SP-062
- **Уровень:** API

# VI. Расход: состав, участники, жизненный цикл

### A-31 · Плательщик — участник другой группы
- **Требования:** SP-051
- **Уровень:** API
- **Предусловие:** Ф1 (`G1`, участники `P1`–`P3`) и Ф2 (`G2`, участники `Q1` `Ann`, `Q2` `Bob`).

### A-46 · UI: адресуемость элементов ролью и видимым текстом
- **Требования:** SP-131 (все действия по расходу), примечание спеки 1.2 к `SP-134`/`SP-135`
- **Уровень:** UI
- **Предусловие:** страница `/` открыта, пользователь указан, группа с тремя участниками есть.
- **Шаги:** для каждого элемента ниже выполнить ровно один запрос по роли или тексту
  и зафиксировать, найден ли он.

  | № | Элемент | Запрос |
  |---|---|---|
  | 1 | поле суммы расхода | `getByRole('textbox'\|'spinbutton', { name: /сумма|amount/i })` |
  | 2 | выбор валюты расхода | `getByRole('combobox'\|'radio', { name: /валют|currency/i })` |
  | 3 | выбор плательщика | `getByRole('combobox'\|'radio', { name: /плат|payer/i })` |
  | 4 | выбор категории | `getByRole('combobox'\|'radio', { name: /категор|category/i })` |
  | 5 | выбор способа распределения | `getByRole('combobox'\|'radio', { name: /поровну|процент|вручн|split/i })` |
  | 6 | выбор участников распределения | `getByRole('checkbox', { name: /Аня|Борис|Вера/ })` |
  | 7 | поля процентов / ручных сумм | `getByRole('textbox', { name: /Аня|Борис|Вера/ })` |
  | 8 | кнопка добавления расхода | `getByRole('button', { name: /добав|созда|add/i })` |
  | 9 | кнопка изменения расхода | `getByRole('button', { name: /измен|редакт|edit/i })` |
  | 10 | текст сообщения об ошибке | `getByText(/.+/)` внутри области ошибки |

- **Ожидаемый результат:**
  Каждый из десяти запросов находит **ровно один** элемент. Кейс считается проваленным
  за каждый ненайденный или неоднозначный элемент, и каждый такой случай оформляется
  отдельной находкой «дефект доступности интерфейса» с указанием, что именно нельзя
  адресовать: элемент без доступного имени (`input` без `label`), кликабельный `div`
  вместо `button`, выпадающий список, собранный из `div`-ов, сообщение об ошибке,
  выводимое `alert`-ом и не остающееся в DOM.
  Обход через `data-testid` или через CSS-селекторы по классам **запрещён**: он подменил бы
  объект проверки. Ненайденный элемент фиксируется, а не обходится.
- **Статус возможной находки:** **расхождение с оракулом** — заказ говорит «простая
  HTML-страница» и требований к доступности не содержит; требование адресуемости ролью
  и текстом введено решением заказчика в версии 1.2 спеки.
- **Результат прогона:** `не прогнано — сессия прогона`

# XI. Спорные трактовки спеки (фиксируются до прогона)

1. **Имена полей запроса и ответа не заданы.** `SP-050` перечисляет состав полей расхода,
   но не их идентификаторы; `SP-020` фиксирует только суффиксы `Minor`/`Formatted`,
   `SP-028` — имя `currency`. Соглашение С-1 — рабочее, а не нормативное: несовпадение имён
   находкой не считается, находкой считается поведение.

2. **Код отказа для участника не из этой группы не определён.** `SP-051` и `SP-052` требуют
   «отклонить», но не говорят чем: `400`/`VALIDATION_ERROR` (нарушено правило состава)
   или `404`/`NOT_FOUND` (в этой группе такого участника нет). В A-31 и A-32 первичным
   ожиданием взят `400`, `404` помечен как допустимая альтернатива; жёстко проверяется
   несоздание расхода и отсутствие утечки данных соседней группы.

3. **Регистр значений перечислимых полей.** Для валюты требование верхнего регистра явное
   (`SP-022`), для `category` и `splitType` — нет. `"Food"` и `"EQUAL"` формально «вне
   набора» (`SP-073`, `SP-060`), но столь же формально это тот же элемент набора в другом
   регистре. Кейсов на это нет намеренно.

4. **Верхняя граница суммы для частей распределения.** `SP-018` ограничивает сумму расхода
   `"10000000.00"`. Распространяется ли предел на отдельную часть ручного распределения,
   спека не говорит; при верной общей сумме (`SP-071`) часть больше предела невозможна,
   так что практического зазора почти нет — но формально вопрос открыт.

5. **Нижняя граница процента и нулевая доля.** `SP-065` задаёт минимум `"0.01"`, значит
   участника с нулевым процентом в составе быть не может — его нужно исключить из состава.
   При этом `SP-064` требует сохранять нулевые доли при `equal`, а `SP-070` разрешает ноль
   при `manual`. Три способа ведут себя по-разному, и это, судя по формулировкам, намеренно;
   в A-21 (строка 3) отказ на `"0.00"` ожидается именно поэтому.

6. **Формат денежной величины на странице.** `SP-133` требует «два знака и код валюты»,
   но не задаёт ни порядок (`100.00 RUB` или `RUB 100.00`), ни разделитель. В UI-кейсах
   проверяется наличие обоих элементов рядом с суммой, а не их взаимное расположение.
