# SplitPay QA — набор проверок и отчёт о прогоне

Домашнее задание №2. Роль — **QA**, работа соло, 25–28 августа 2026.

**Репозиторий — не приложение, а набор проверок и доказательств прогона.**
Приложение здесь объект тестирования, а не результат работы. Результат
работы QA — набор проверок, который прогоняется одной командой и даёт
результат, плюс отчёт о прогоне.

Быстрый старт — раздел [«Как запустить проверки»](#как-запустить-проверки).
Отчёт о прогоне в PDF — `run-report.pdf` в корне.

## Что за проект и почему свой, а не вариант из приложения к заданию

**SplitPay** — веб-приложение для совместного учёта общих расходов: группы,
расходы с разными способами деления, автоматический расчёт долгов, отметка
долга оплаченным, история операций.

Приложение написал **отдельный субагент с чистым контекстом**, по короткому
заказу `ORDER.md`. Он не видел `SPEC.md` и не участвовал в обсуждении проверок.

Свой сценарий взят ровно ради этого. Он единственный, в котором удаётся
развести автора и проверяющего по разным контекстам: приложение пишется под
мой заказ, но без доступа к моим проверкам. Готовые варианты из приложения
к заданию такой развязки не дают — там объект либо уже существует и известен,
либо описывается тем же контекстом, который его потом проверяет. А если автор
и проверяющий — один контекст, проверки подтверждают не поведение приложения,
а собственные предположения о нём.

Отсюда правило, действующее всю работу:

> **SplitPay тестируется как чужое приложение. Код не читаем и не правим.**
> Все выводы — по наблюдаемому поведению: через API и через интерфейс.
> Найденные дефекты фиксируются в отчёте, а не исправляются.

## Как поднять приложение

Нужен только Node.js (проверялось на `v22.22.2` и `v22.23.2`). Внешних
зависимостей нет, `npm install` не нужен ни для приложения, ни для проверок.

```
node app/server.js
```

Затем открыть http://127.0.0.1:3000

Необязательные переменные окружения: `PORT` (по умолчанию 3000), `HOST`
(по умолчанию 127.0.0.1), `SPLITPAY_DATA` (путь к файлу данных). Данные
лежат в JSON-файле, он создаётся сам при первом запуске.

**Для прогона проверок приложение поднимать не нужно.** Оснастка сама
поднимает свой экземпляр на свободном порту, со своим файлом данных
во временном каталоге, и сама его гасит.

## Как запустить проверки

### API-набор — одной командой

```
node --test "tests/api/*.test.mjs"
```

Предварительных шагов нет. Каждый файл проверок поднимает **свой** процесс
приложения на **своём** порту и со **своим** файлом данных — `node --test`
исполняет файлы параллельно, общее состояние тут недопустимо. Каталог
`app/` при этом не трогается: файл данных уводится штатной переменной
`SPLITPAY_DATA`, объявленной в `app/README.md`.

Время прогона — около 25 секунд. Код возврата будет **ненулевым**: набор
красный по существу, см. [«Намеренно красные тесты»](#намеренно-красные-тесты).

### UI-слой — отдельно, и только там, где есть Playwright

```
npm link playwright && node --test "tests/ui/*.spec.mjs"
```

**Оговорка, без которой команда не сработает.** Playwright есть только
в облачном контейнере, где он предустановлен глобально вместе с Chromium.
На локальной машине его нет и поставить нельзя: реестр npm закрыт исходящим
прокси (`E403`) из обеих сред — вывод в `evidence/env-check.md`. Поэтому
`npm link` вместо `npm install`: он подключает уже установленный глобально
пакет, не ходя в сеть.

Локально воспроизводится только API-часть набора. Это ограничение окружения,
и оно названо вслух, а не спрятано за зелёным прогоном.

### Регрессионный прогон целиком

```
workflow/qa-regress run          # изменения от тега → зоны → прогон → задание агенту
workflow/qa-regress finish       # отчёт → тег
```

Процедура прогоняет только те зоны, которых коснулись изменения, и оставляет
файл-доказательство на каждом шаге. Подробно — `workflow/README.md`.

## Намеренно красные тесты

**Красный тест в этом наборе — не поломка набора, а зафиксированная находка.**

Набор написан по оракулу `SPEC.md`, который автору приложения не передавался.
Каждое ожидание выведено из требования и записано **до** прогона. Когда
приложение ведёт себя иначе, чем требует оракул, тест краснеет и остаётся
красным.

Что из этого следует для читающего:

- **`xfail`, `skip` и «ожидаемые падения» не используются.** Пометить находку
  «ожидаемой» — значит перевести её из отчёта в конфигурацию набора: она
  перестанет быть видна и в следующем прогоне никого ни о чём не предупредит.
- **Приложение не правится.** Работа QA заканчивается отчётом (запрет 2
  в `sessions/STATE.md`). Ни одна находка не закрыта правкой в `app/`.
- **Зелёный прогон целиком не является целью.** Целью является прогон,
  в котором каждый красный тест объяснён: какое требование нарушено, каким
  наблюдаемым поведением, какой у находки статус.
- **Тест, красный из-за собственной ошибки оснастки, — это брак, а не
  находка.** Такие чинятся. В прогоне 27 августа таких было три (`B-33`,
  `B-34`, `B-35`); оснастка исправлена, после чего `B-34` позеленел,
  а `B-33` и `B-35` остались красными уже по существу. См. раздел
  «Правка оснастки» в `REPORT.md`.

### Почему красных так много

67 красных — это **не 67 разных дефектов**. Одно расхождение обычно валит
несколько проверок: зоны перекрываются по построению веера. Крупнейшие группы:

1. **Форма тела ошибки.** `SP-101` требует
   `{"error":{"code":"…","message":"…"}}`, приложение отвечает плоским
   `{"error":"текст"}` — кода ошибки нет вовсе, а с ним нет и набора `SP-102`.
   В зоне C это расхождение проверяется **ровно один раз** (`C-25`,
   соглашение С-C2), чтобы одна находка не покрасила собой три десятка
   тестов. В зоне A по той же причине выделен `A-20-NAMES`.
2. **Коды успешных ответов.** `SP-109` требует `201` на создание и `204`
   на удаление; приложение отвечает `200` на всё. Вердикт даёт `C-29`,
   задевает `A-37`, `C-10`, `C-14`, `C-19`.
3. **Модель участника.** Оракул описывает участника как сущность с именем
   внутри группы, приложение отождествляет его с зарегистрированной учётной
   записью. Отсюда пять красных: нет уникальности имён (`C-16`, `C-17`),
   нет предела в 20 участников (`C-18`), нет верхней границы длины имени
   (`C-15`), идентификатор переиспользуется после удаления и повторного
   добавления (`C-32`).
4. **Отказ по чужой группе.** `SP-116` требует `403 FORBIDDEN`, приложение
   отвечает `404` на чужую группу и на несуществующую одинаково
   (`C-01`…`C-05`). Это **осознанное решение автора**, объявленное
   в `app/README.md`: «запрос чужой группы возвращает 404, чтобы нельзя было
   даже узнать о её существовании». Оно безопаснее требования оракула.
   Расхождение зафиксировано, дефектом не названо.
5. **История операций.** `SP-180`–`SP-181` требуют список расходов
   и погашений, где у записи есть тип, момент, сумма, валюта и стороны.
   Приложение отдаёт `activity` — журнал строками вида «Аня добавил(а)
   расход «Бензин» на 300.00 RUB»: сумма, валюта и стороны существуют только
   внутри текста, полями их нет. Отсюда `C-23`, `C-34`, `C-38`, а также
   `C-36` (удалённый расход остаётся в журнале двумя записями).
6. **Валидация верхних границ.** Ни у названия группы (60), ни у имени (40),
   ни у описания расхода (140), ни у суммы (10 000 000.00) верхней границы
   нет: `C-11`, `C-15`, `A-34`, `A-13`.

### Статус находки: два разных вида, смешивать нельзя

- **Дефект против заказа** — нарушено то, что автору было сказано дословно
  в `ORDER.md`.
- **Расхождение с оракулом** — в заказе этого не было, автор решил иначе.

Доктрина отнесения — соглашение С-3 плана A, принятое как единственное для
всех трёх зон (разбор `D-35` в `evidence/audit-resolution.md`): дефект против
заказа — только там, где отсутствует или неработоспособна функция, названная
в заказе дословно; всякая характеристика её результата — расхождение
с оракулом. Условная переклассификация допустима, когда условие
сформулировано через текст заказа, и запрещена, когда через тяжесть
последствий.

### Объявленные неоднозначности

Спека их не решает, кейса они не проваливают, в набор входят как наблюдения
(разбор — `evidence/audit-resolution.md`, § 3):

- **Н-3-А** — величина у записи долга со статусом `paid`: остаток `0.00`
  либо погашенная сумма.
- **Н-3-Б** — `Content-Type` у ответов `204`: у ответа нет тела, заголовок
  спорен.
- **Н-3-В** — статус успеха на отметке оплаты: `200` либо `201`.

## Что осталось за рамками итерации

Названо вслух, а не умолчано. Полный разбор с причинами — раздел
«Что не сделано и почему» в `REPORT.md`.

| Что | Почему |
|---|---|
| Dashboard и фильтрация истории | Решение заказчика, подтверждено явно. Не сокращение объёма агентом |
| Независимая проверка чужого набора («ломатель») | Требует отдельного агента с чистым контекстом; лимиты среды в финальной сессии исчерпаны |
| Проверка на инъекцию в промпт на двух моделях | То же основание. Осталось непроверенным: устойчивость набора и процедуры к тексту, приходящему из данных приложения |
| Последовательный замер против параллельного | Решение заказчика: цена второго полного прогона веера под лимитами среды неприемлема. Следствие: 2,09 — измеренная параллельность, не измеренное ускорение |
| `SP-152` | Щель между зонами, найденная аудитом (`D-01`). Покрытие набора — 132 требования из 138 полноценно |
| Установка сторонних инструментов | Реестр npm закрыт из обеих сред. Разбор — `TOOLS.md` |

## Ограничения окружения

Проверены до начала работы, полный вывод — `evidence/env-check.md`.

- **Реестр npm недоступен** (`E403` через исходящий прокси) — ни на локальной
  машине, ни в облачном контейнере. Ни один шаг не зависит от `npm install`.
- **Выход в сеть закрыт** — `curl` получает `HTTP code 403 from proxy after
  CONNECT`. Разбор границ песочницы — раздел «Изоляция» в `REPORT.md`.
- **Playwright доступен только в облачном контейнере** (1.56.0, Chromium
  предустановлен).
- **Git на локальной машине работает без права удалять файлы** — среда
  возвращает `Operation not permitted`. Обход и его цена — риск Р-1
  в `REPORT.md`.
