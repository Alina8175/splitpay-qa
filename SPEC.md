# ЧАСТЬ 0. ПОСТАНОВКА ЗАКАЗЧИКА И ТРАССИРОВКА

## 0.1. Постановка дословно

**Функционал**

1. **Dashboard:** общий баланс пользователя, сколько ему должны, сколько должен он,
   последние операции.
2. **Groups:** создание группы, добавление и удаление участников, просмотр расходов группы.
3. **Добавление расхода.** Поля: сумма, валюта, кто заплатил, категория, участники,
   способ распределения — поровну / по процентам / вручную.
4. **Debts:** кто кому и сколько должен, статусы Pending / Paid, возможность отметить
   долг оплаченным.
5. **Transactions:** история всех расходов и погашений с фильтрацией.

**Бизнес-правила**

- сумма распределения должна совпадать с суммой расхода;
- округление обрабатывается корректно;
- нельзя создать расход с нулевой или отрицательной суммой;
- нельзя повторно оплатить уже оплаченный долг;
- после удаления или изменения расхода долги пересчитываются;
- пользователь не должен видеть данные чужих групп.

# ЧАСТЬ I. ЗАКАЗ

## Что за приложение

**SplitPay** — веб-приложение для совместного учёта общих расходов.

Задача, которую оно решает: несколько человек тратят деньги на общее — поездка, аренда,
совместные покупки. Платит каждый раз кто-то один, а польза достаётся всем или части
группы. Нужно понять, кто кому сколько должен, отмечать погашения и видеть историю.

Пользователь заводит группу, добавляет участников, записывает расходы (сумма, валюта,
плательщик, категория, участники, способ распределения) и получает две сводки: **балансы** —
кто в плюсе, кто в минусе, и **долги** — конкретный список «кто кому сколько», который
можно отмечать оплаченным. Все операции складываются в **историю**.

## Технические рамки

Рамки продиктованы окружением, а не вкусом. Реестр пакетов недоступен: `npm ping`
возвращает `E403`, исходящий трафик закрыт прокси. Установить зависимость невозможно.

- **Node.js**, версия 20 или новее. Проверено на `v22.23.2`.
- **Только стандартная библиотека.** Ни одной внешней зависимости. `package.json`, если
  он есть, обязан иметь пустой или отсутствующий раздел `dependencies`. Команда
  `npm install` не должна требоваться ни на одном шаге.
- **Никаких обращений в сеть** во время работы: ни CDN, ни шрифтов, ни аналитики.
- **Один процесс.** Запускается одной командой, без сборки.
- **Хранилище — файл.** JSON-файл на диске. База данных не используется.

## Как запускается

```
node app/server.js
```

- Порт по умолчанию — **3000**, переопределяется переменной окружения `PORT`.
- При старте процесс обязан напечатать в stdout строку с адресом, на котором слушает.
- Файл данных создаётся при первом запуске автоматически.
- Файл данных располагается в `app/data/` — каталог внесён в `.gitignore`.

## Что входит в поставку

| Путь | Что это |
|---|---|
| `app/server.js` | Точка входа. HTTP-сервер, API и отдача страницы |
| `app/public/index.html` | Интерфейс: одна страница |
| `app/data/` | Файл данных, создаётся при первом запуске |

Внутреннее устройство — на усмотрение автора: число модулей, имена функций, организация
кода не проверяются.

# ЧАСТЬ II. ТРЕБОВАНИЯ К ПОВЕДЕНИЮ

## 1. Модель данных

**SP-001.** Группа обязана иметь: идентификатор, название, валюту, владельца, список
участников, момент создания.

**SP-002.** Валюта группы обязана задаваться при создании и обязана быть неизменяемой
после создания. Набор допустимых валют — `SP-022`.

**SP-003.** Участник обязан иметь идентификатор и имя. Участник принадлежит ровно одной
группе.

**SP-004.** Расход обязан иметь: идентификатор, группу, плательщика, сумму, валюту,
категорию, описание, способ распределения, состав распределения, момент создания.

**SP-005.** Идентификаторы обязаны быть строками, уникальными в пределах своего вида,
и обязаны не совпадать с идентификаторами, выданными ранее в этом же запуске.

**SP-006.** Порядок участников в группе обязан совпадать с порядком их добавления
и обязан не меняться при добавлении расходов.

**SP-007.** Данные обязаны переживать перезапуск процесса: после остановки и повторного
запуска все группы, участники, расходы и погашения обязаны остаться теми же.

## 2. Деньги

**SP-010.** Все денежные величины обязаны храниться и вычисляться в **целых копейках**
(минимальных единицах валюты). Хранение сумм числами с плавающей точкой не допускается.

**SP-011.** На входе API сумма передаётся **строкой** с точкой в качестве разделителя:
`"100"`, `"100.5"`, `"100.50"`.

**SP-012.** Сумма обязана приниматься с числом знаков после точки **не более двух**.
`"100.005"` обязана отклоняться.

**SP-013.** Крайние пробелы в строке суммы обязаны отбрасываться: `" 100.00 "`
эквивалентно `"100.00"`.

**SP-014.** Запятая в качестве разделителя обязана отклоняться: `"100,00"` — ошибка.

**SP-015.** Экспоненциальная запись обязана отклоняться: `"1e3"` — ошибка.

**SP-016.** Сумма расхода обязана быть строго больше нуля. `"0"` и `"0.00"` — ошибка.

**SP-017.** Отрицательная сумма обязана отклоняться: `"-1.00"` — ошибка.

**SP-018.** Сумма обязана быть не больше `"10000000.00"`. Превышение — ошибка.

**SP-019.** Минимальная допустимая сумма расхода — `"0.01"`. Она обязана приниматься.

**SP-020.** В ответах API каждая денежная величина обязана присутствовать в двух видах:
целое число минимальных единиц в поле с суффиксом `Minor` и строка с ровно двумя знаками
после точки в поле с суффиксом `Formatted`. Пример: `amountMinor: 10000`,
`amountFormatted: "100.00"`.

**SP-021.** Строковое представление обязано содержать ровно два знака после точки всегда:
`100` копеек → `"1.00"`, не `"1"` и не `"1.0"`.

### Валюта

**SP-022.** Валюта обязана задаваться кодом из фиксированного набора: `RUB`, `USD`, `EUR`.
Код обязан приниматься только в верхнем регистре.

**SP-023.** Код валюты вне набора обязан отклоняться с `VALIDATION_ERROR`. Это касается
и заведомо существующих валют вне набора, например `GBP`.

**SP-024.** При создании группы валюта обязана приниматься; при её отсутствии в запросе
обязана подставляться `RUB`.

**SP-025.** Расход обязан иметь поле валюты.

**SP-026.** Валюта расхода обязана совпадать с валютой группы. Расход в валюте, отличной
от валюты группы, обязан отклоняться с `VALIDATION_ERROR`: конвертация не выполняется.

**SP-027.** При отсутствии поля валюты в запросе на создание расхода обязана подставляться
валюта группы.

**SP-028.** Каждая денежная величина в ответах API обязана сопровождаться кодом валюты
в поле `currency`.

## 3. Группы

**SP-030.** Создание группы обязано принимать название и возвращать созданную группу
с пустым списком участников.

**SP-031.** Название группы обязано иметь длину от 1 до 60 символов после отбрасывания
крайних пробелов.

**SP-032.** Название из одних пробелов обязано отклоняться.

**SP-033.** Название обязано сохраняться с отброшенными крайними пробелами.

**SP-034.** Запрос несуществующей группы обязан возвращать ошибку «не найдено».

**SP-035.** Список групп обязан возвращать группы, принадлежащие обратившемуся
пользователю. Ограничение — `SP-144`.

## 4. Участники

**SP-040.** Добавление участника обязано принимать имя и возвращать созданного участника.

**SP-041.** Имя участника обязано иметь длину от 1 до 40 символов после отбрасывания
крайних пробелов.

**SP-042.** Имена участников обязаны быть уникальны в пределах группы **без учёта регистра
и крайних пробелов**: при наличии `Аня` добавление `аня` и ` Аня ` обязано отклоняться.

**SP-043.** Группа обязана вмещать не более 20 участников. Добавление двадцать первого —
ошибка.

**SP-044.** Участник обязан удаляться, если он не участвует ни в одном расходе и ни в одном
погашении.

**SP-045.** Удаление участника, который является плательщиком, входит в состав
распределения хотя бы одного расхода либо является стороной хотя бы одного погашения,
обязано отклоняться с ошибкой конфликта.

**SP-046.** Добавление участника в несуществующую группу обязано возвращать «не найдено».

**SP-047.** Удаление несуществующего участника обязано возвращать «не найдено».

## 5. Расходы

**SP-050.** Добавление расхода обязано принимать: плательщика, сумму, валюту, категорию,
описание, способ распределения и состав распределения.

**SP-051.** Плательщик обязан быть участником той же группы. Идентификатор участника
другой группы обязан отклоняться.

**SP-052.** Состав распределения обязан быть непустым и обязан состоять только из
участников этой группы.

**SP-053.** Повторение одного участника в составе распределения обязано отклоняться.

**SP-054.** Описание расхода обязано иметь длину не более 140 символов. Пустое описание
допускается.

**SP-055.** Плательщик не обязан входить в состав распределения: допустима ситуация, когда
один заплатил за других и на него самого ничего не начисляется.

**SP-056.** Список расходов группы обязан возвращать расходы в порядке добавления,
от старых к новым.

**SP-057.** Удаление расхода обязано удалять его из группы и обязано отражаться
в балансах и долгах немедленно.

**SP-058.** Повторное удаление уже удалённого расхода обязано возвращать «не найдено».

**SP-059.** Добавление расхода в несуществующую группу обязано возвращать «не найдено».

## 6. Способы распределения

**SP-060.** Приложение обязано поддерживать три способа распределения: `equal` — поровну,
`percent` — по процентам, `manual` — вручную. Иной способ обязан отклоняться.

### Поровну (`equal`)

**SP-061.** Сумма обязана распределяться поровну между участниками состава распределения.

**SP-062.** При неделимом остатке лишние минимальные единицы обязаны раздаваться
по одной участникам **в порядке их добавления в группу**, начиная с первого.

**SP-063.** Сумма начислений обязана в точности равняться сумме расхода. Пример:
`"100.00"` на троих → `33.34`, `33.33`, `33.33`.

**SP-064.** Расход в одну копейку на троих обязан начислить `0.01`, `0.00`, `0.00`.

### По процентам (`percent`)

**SP-065.** Проценты обязаны задаваться строкой в том же формате, что и суммы: не более
двух знаков после точки, от `"0.01"` до `"100.00"`.

**SP-066.** Сумма процентов по всем участникам состава распределения обязана равняться
ровно `"100.00"`. Расхождение хотя бы в сотую долю процента обязано отклоняться
с `VALIDATION_ERROR`.

**SP-067.** Начисление обязано считаться методом наибольшего остатка: каждому — целая
часть от `сумма × процент ÷ 100`, затем оставшиеся минимальные единицы раздаются по одной
участникам с наибольшей дробной частью; при равных дробных частях — в порядке добавления
участников.

**SP-068.** Сумма начислений обязана в точности равняться сумме расхода.

### Вручную (`manual`)

**SP-069.** Каждому участнику состава распределения обязана задаваться точная сумма
в том же формате, что и сумма расхода.

**SP-070.** Заданная вручную сумма обязана быть не меньше нуля. Ноль допускается,
отрицательная — ошибка.

**SP-071.** Сумма заданных вручную сумм обязана в точности равняться сумме расхода.
Расхождение хотя бы в одну минимальную единицу обязано отклоняться с ошибкой.

### Категория

**SP-072.** Расход обязан иметь категорию из фиксированного набора: `food`, `transport`,
`housing`, `entertainment`, `other`.

**SP-073.** Категория вне набора обязана отклоняться с `VALIDATION_ERROR`.

**SP-074.** При отсутствии поля категории обязана подставляться `other`.

**SP-075.** Категория обязана возвращаться в составе расхода при чтении.

### Общее правило распределения

**SP-076.** При любом способе распределения сумма начислений по участникам обязана
в точности равняться сумме расхода. Требование действует независимо от способа и является
общим случаем `SP-063`, `SP-068` и `SP-071`.

## 7. Балансы

**SP-080.** Баланс участника обязан считаться как: сколько он заплатил, плюс сколько
он отдал погашениями, минус сколько на него начислено, минус сколько он получил
погашениями.

**SP-081.** Сумма балансов всех участников группы обязана быть равна нулю **всегда**,
при любом наборе расходов, любом способе распределения и любом числе погашений.

**SP-082.** Балансы обязаны возвращаться для всех участников группы, включая тех, у кого
баланс нулевой.

**SP-083.** Группа без расходов обязана возвращать нулевые балансы для всех участников,
а не пустой список.

**SP-084.** Балансы обязаны пересчитываться на момент запроса и обязаны отражать все
добавления, изменения и удаления расходов, а также все погашения.

## 8. Долги

**SP-090.** Приложение обязано возвращать список долгов, гасящих все балансы в ноль.

**SP-091.** Каждый долг обязан содержать: от кого, кому, сумму, валюту, статус.

**SP-092.** Сумма каждого долга со статусом `pending` обязана быть строго больше нуля.

**SP-093.** Число долгов со статусом `pending` обязано быть не больше, чем число
участников с ненулевым балансом, минус один.

**SP-094.** Применение всех долгов к балансам обязано обнулять их полностью, без остатка
в минимальных единицах.

**SP-095.** Долг, где отправитель и получатель совпадают, обязан отсутствовать.

**SP-096.** Группа с нулевыми балансами обязана возвращать пустой список долгов
со статусом `pending`.

## 9. Протокол и ошибки

**SP-100.** Все ответы API обязаны иметь `Content-Type: application/json; charset=utf-8`.

**SP-101.** Тело ошибки обязано иметь вид `{"error": {"code": "...", "message": "..."}}`.

**SP-102.** Коды ошибок обязаны быть из фиксированного набора: `VALIDATION_ERROR`,
`NOT_FOUND`, `CONFLICT`, `MALFORMED_JSON`, `METHOD_NOT_ALLOWED`, `UNAUTHORIZED`,
`FORBIDDEN`.

**SP-103.** Ошибка проверки данных обязана возвращать статус `400` и код
`VALIDATION_ERROR`.

**SP-104.** Отсутствующая сущность обязана возвращать статус `404` и код `NOT_FOUND`.

**SP-105.** Конфликт состояния обязан возвращать статус `409` и код `CONFLICT`.

**SP-106.** Тело запроса, не являющееся корректным JSON, обязано возвращать статус `400`
и код `MALFORMED_JSON`, а не приводить к падению процесса.

**SP-107.** Обращение к существующему пути неподдерживаемым методом обязано возвращать
статус `405` и код `METHOD_NOT_ALLOWED`.

**SP-108.** Сообщение об ошибке обязано называть конкретное поле или причину. Сообщение
вида «ошибка» без уточнения требованию не удовлетворяет.

**SP-109.** Успешное создание обязано возвращать статус `201`, успешное чтение — `200`,
успешное изменение — `200`, успешное удаление — `204` с пустым телом.

**SP-110.** Неизвестное поле в теле запроса обязано игнорироваться, а не приводить
к ошибке.

**SP-111.** Отсутствие обязательного поля обязано возвращать `VALIDATION_ERROR`,
а не приводить к падению процесса.

**SP-112.** Значение неверного типа — число вместо строки, строка вместо массива —
обязано возвращать `VALIDATION_ERROR`, а не приводить к падению процесса.

**SP-113.** Процесс обязан оставаться работоспособным после любого некорректного запроса:
следующий корректный запрос обязан обслуживаться нормально.

**SP-114.** `GET /api/health` обязан возвращать статус `200` и не обязан требовать
идентификации.

**SP-115.** Запрос без идентификатора пользователя обязан возвращать статус `401` и код
`UNAUTHORIZED`.

**SP-116.** Обращение к группе, владельцем которой является другой пользователь, обязано
возвращать статус `403` и код `FORBIDDEN`.

**SP-117.** Тело отказа по `SP-116` обязано не раскрывать содержимое чужой группы:
ни названия, ни имён участников, ни сумм.

## 10. Идентификация и доступ

Полноценной авторизации в этой итерации нет: ни паролей, ни сессий, ни регистрации.
Есть минимальная идентификация, достаточная для того, чтобы разграничить группы.

**SP-140.** Каждый запрос к `/api/`, кроме `GET /api/health`, обязан нести идентификатор
пользователя в заголовке `X-User-Id`.

**SP-141.** Отсутствующий заголовок `X-User-Id` обязан приводить к `SP-115`.

**SP-142.** Пустой заголовок либо заголовок из одних пробелов обязан приводить к `SP-115`.

**SP-143.** Группа обязана принадлежать пользователю, создавшему её. Владелец фиксируется
в момент создания и обязан быть неизменяемым.

**SP-144.** Список групп обязан возвращать только группы, принадлежащие обратившемуся
пользователю. Чужая группа обязана в списке отсутствовать.

**SP-145.** Обращение к чужой группе по прямому идентификатору обязано приводить
к `SP-116`, а не возвращать данные.

**SP-146.** Проверка владения обязана применяться ко **всем** вложенным путям группы:
участники, расходы, балансы, долги, погашения, история. Ни один из них не обязан быть
исключением.

**SP-147.** Ранее не встречавшийся идентификатор пользователя обязан обслуживаться как
обычный: регистрации нет, у такого пользователя просто нет групп.

**SP-148.** Идентификатор участника и идентификатор пользователя — разные сущности.
Передача идентификатора участника в `X-User-Id` не обязана давать доступ к группе.

## 11. Изменение расхода

**SP-150.** Расход обязан изменяться по своему пути методом `PUT`.

**SP-151.** Изменению обязаны подлежать все поля расхода, кроме идентификатора и группы.

**SP-152.** К изменяемому расходу обязаны применяться те же правила проверки, что
и при создании: сумма, валюта, категория, состав распределения, способ распределения.

**SP-153.** Изменение расхода обязано немедленно отражаться в балансах и долгах.

**SP-154.** Изменение несуществующего расхода обязано возвращать `NOT_FOUND`.

**SP-155.** Изменение расхода обязано сохранять его идентификатор и его позицию в порядке
добавления.

**SP-156.** Отклонённое изменение обязано не менять расход: после ошибки расход обязан
остаться в том виде, в каком был до запроса.

## 12. Погашения

**SP-160.** Долг обязан адресоваться парой «должник, кредитор» в пределах группы.

**SP-161.** Долг обязан вычисляться из балансов с учётом всех ранее проведённых погашений.

**SP-162.** Список долгов обязан включать как долги со статусом `pending`, так и долги
со статусом `paid`.

**SP-163.** Статус долга обязан быть `pending`, если остаток по паре больше нуля,
и `paid`, если остаток равен нулю и по этой паре было проведено хотя бы одно погашение.

**SP-164.** Пара, по которой никогда не было ни задолженности, ни погашения, обязана
в списке долгов отсутствовать.

**SP-165.** Отметка долга оплаченным обязана выполняться отдельным вызовом и обязана
создавать погашение на полную сумму текущего остатка.

**SP-166.** Повторная отметка уже оплаченного долга обязана отклоняться со статусом `409`
и кодом `CONFLICT`.

**SP-167.** Отметка оплаченным по паре, у которой нет задолженности, обязана возвращать
`NOT_FOUND`.

**SP-168.** После отметки оплаченным остаток по паре обязан стать нулевым, а балансы обеих
сторон обязаны измениться ровно на сумму погашения.

**SP-169.** Сумма балансов обязана оставаться равной нулю после любого числа погашений.

**SP-170.** Погашение обязано быть необратимым в рамках этой итерации: отмены погашения
не предусмотрено.

**SP-171.** После удаления расхода долги обязаны пересчитаться. Ранее проведённые
погашения обязаны сохраниться и обязаны продолжать учитываться в расчёте.

**SP-172.** После изменения расхода долги обязаны пересчитаться. Ранее проведённые
погашения обязаны сохраниться и обязаны продолжать учитываться в расчёте.

**SP-173.** Если после пересчёта задолженность по паре сменила направление, она обязана
появиться как долг противоположного направления со статусом `pending`.

## 13. История операций

**SP-180.** Приложение обязано возвращать историю операций группы: расходы и погашения
в одном списке.

**SP-181.** Каждая запись истории обязана иметь: тип (`expense` либо `settlement`), момент,
сумму, валюту и стороны операции.

**SP-182.** История обязана возвращаться в порядке от новых к старым.

**SP-183.** Удалённый расход обязан исчезать из истории.

**SP-184.** Фильтрация истории в этой итерации не предусмотрена. Параметры фильтрации,
если они переданы, обязаны игнорироваться по правилу `SP-110`, а не приводить к ошибке.

# ЧАСТЬ III. ВНЕ РАМОК

## Отложено решением заказчика

Подтверждено явно. Это не упущение и не сокращение объёма проверки — это граница итерации.

- **Dashboard:** общий баланс пользователя, сводка «сколько мне должны / сколько должен я»,
  последние операции.
- **Фильтрация истории операций** по датам, категориям, участникам, типу.

## Не входит в продукт

- Полноценная авторизация: пароли, сессии, регистрация, восстановление доступа.
  Минимальная идентификация описана в разделе 10.
- Конвертация валют, курсы, мультивалютные группы. Валюта фиксируется на группе.
- Загрузка файлов, чеки, изображения.
- Уведомления, почта, экспорт.
- Повторяющиеся и запланированные расходы.
- Отмена погашения, история изменений, откат действия.
- Мобильная вёрстка, оформление, анимация. Интерфейс должен быть работающим,
  а не красивым.
- Любые внешние библиотеки, шрифты, стили и скрипты, загружаемые из сети.

# ЧАСТЬ IV. ПРИЁМКА

Приложение считается принятым, когда выполнены все условия:

1. `node app/server.js` запускается на чистой машине без единой предварительной команды,
   и в stdout появляется адрес прослушивания.
2. `GET /api/health` отвечает `200`.
3. Страница `/` открывается и позволяет пройти путь целиком: указать пользователя →
   создать группу → добавить трёх участников → добавить расход → увидеть балансы
   и долги → отметить долг оплаченным → увидеть операцию в истории.
4. В поставке нет внешних зависимостей: `npm install` нигде не требуется, обращений
   в сеть при работе нет.
5. Все пути из `SP-120` отвечают — хотя бы кодом ошибки в формате `SP-101`, а не разрывом
   соединения.

**Приёмка не означает отсутствия дефектов.** Она означает, что объект пригоден для
проверки. Соответствие требованиям проверяется отдельно, найденные расхождения фиксируются
в отчёте, а не исправляются.
