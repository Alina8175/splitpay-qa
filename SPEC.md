# Как устроен этот документ

Документ выполняет две роли одновременно.

**Часть I — заказ.** Что строим, в каких технических рамках, как это запускается.
Самодостаточна: её можно передать автору приложения как есть.

**Часть II — требования к поведению.** Пронумерованные требования вида `SP-NNN`.
Каждое сформулировано так, чтобы его можно было проверить снаружи, не заглядывая в код.
Это основание для проверок: каждая проверка ссылается на номер требования.

**Часть III — вне рамок.** Чего в приложении быть не должно.

**Часть IV — приёмка.** Условия, при которых приложение считается принятым.

Формулировки: **обязан** — требование, нарушение считается дефектом; **не обязан** —
поведение на усмотрение автора, проверке не подлежит.

# ЧАСТЬ I. ЗАКАЗ

## Что за приложение

**SplitPay** — веб-приложение для совместного учёта общих расходов.

Задача, которую оно решает: несколько человек тратят деньги на общее — поездка, аренда,
совместные покупки. Платит каждый раз кто-то один, а польза достаётся всем или части
группы. В конце нужно понять, кто кому сколько должен, и погасить это минимальным числом
переводов.

Пользователь заводит группу, добавляет участников, записывает расходы (кто заплатил,
сколько, за кого) и получает две сводки: **балансы** — сколько каждый в плюсе или минусе,
и **переводы** — конкретный список «кто кому сколько переводит», чтобы всё обнулить.

## Технические рамки

Рамки продиктованы окружением, а не вкусом. Реестр пакетов недоступен: `npm ping`
возвращает `E403`, исходящий трафик закрыт прокси. Установить зависимость невозможно.

- **Node.js**, версия 20 или новее. Проверено на `v22.23.2`.
- **Только стандартная библиотека.** Ни одной внешней зависимости. `package.json`, если
  он есть, обязан иметь пустой или отсутствующий раздел `dependencies`. Команда
  `npm install` не должна требоваться ни на одном шаге.
- **Никаких обращений в сеть** во время работы: ни CDN, ни шрифтов, ни аналитики.
  Страница обязана полностью работать без внешних запросов.
- **Один процесс.** Запускается одной командой, без сборки и без предварительных шагов.
- **Хранилище — файл.** JSON-файл на диске. База данных не используется.

## Как запускается

```
node app/server.js
```

- Порт по умолчанию — **3000**, переопределяется переменной окружения `PORT`.
- При старте процесс обязан напечатать в stdout строку, содержащую адрес, на котором
  он слушает.
- Файл данных создаётся при первом запуске автоматически, отдельного шага инициализации
  быть не должно.
- Файл данных располагается в `app/data/` — этот каталог внесён в `.gitignore` и в сдачу
  не попадает.

## Что входит в поставку

| Путь | Что это |
|---|---|
| `app/server.js` | Точка входа. HTTP-сервер, API и отдача страницы |
| `app/public/index.html` | Интерфейс: одна страница |
| `app/data/` | Файл данных, создаётся при первом запуске |

Внутреннее устройство — на усмотрение автора: число модулей, имена функций, организация
кода не проверяются и требованиями не ограничены.

# ЧАСТЬ II. ТРЕБОВАНИЯ К ПОВЕДЕНИЮ

## 1. Модель данных

**SP-001.** Группа обязана иметь: идентификатор, название, валюту, список участников,
момент создания.

**SP-002.** Валюта группы обязана быть `RUB` и обязана быть неизменяемой после создания.

**SP-003.** Участник обязан иметь идентификатор и имя. Участник принадлежит ровно одной
группе.

**SP-004.** Расход обязан иметь: идентификатор, группу, плательщика, сумму, описание,
способ деления, состав деления, момент создания.

**SP-005.** Идентификаторы обязаны быть строками, уникальными в пределах своего вида,
и обязаны не совпадать с идентификаторами, выданными ранее в этом же запуске.

**SP-006.** Порядок участников в группе обязан совпадать с порядком их добавления
и обязан не меняться при добавлении расходов.

**SP-007.** Данные обязаны переживать перезапуск процесса: после остановки и повторного
запуска все группы, участники и расходы обязаны остаться теми же.

## 2. Деньги

**SP-010.** Все денежные величины обязаны храниться и вычисляться в **целых копейках**.
Хранение сумм числами с плавающей точкой не допускается.

**SP-011.** На входе API сумма передаётся **строкой в рублях** с точкой в качестве
разделителя: `"100"`, `"100.5"`, `"100.50"`.

**SP-012.** Сумма обязана приниматься с числом знаков после точки **не более двух**.
`"100.005"` обязана отклоняться.

**SP-013.** Крайние пробелы в строке суммы обязаны отбрасываться: `" 100.00 "`
эквивалентно `"100.00"`.

**SP-014.** Запятая в качестве разделителя обязана отклоняться: `"100,00"` — ошибка.

**SP-015.** Экспоненциальная запись обязана отклоняться: `"1e3"` — ошибка.

**SP-016.** Сумма обязана быть строго больше нуля. `"0"` и `"0.00"` — ошибка.

**SP-017.** Отрицательная сумма обязана отклоняться: `"-1.00"` — ошибка.

**SP-018.** Сумма обязана быть не больше `"10000000.00"` (десять миллионов рублей).
Превышение — ошибка.

**SP-019.** Минимальная допустимая сумма — `"0.01"`, одна копейка. Она обязана приниматься.

**SP-020.** В ответах API каждая денежная величина обязана присутствовать в двух видах:
целое число копеек в поле с суффиксом `Minor` и строка рублей с ровно двумя знаками
после точки в поле с суффиксом `Formatted`. Пример: `amountMinor: 10000`,
`amountFormatted: "100.00"`.

**SP-021.** Строковое представление обязано содержать ровно два знака после точки всегда,
включая целые суммы: `100` копеек → `"1.00"`, не `"1"` и не `"1.0"`.

## 3. Группы

**SP-030.** Создание группы обязано принимать название и возвращать созданную группу
с пустым списком участников.

**SP-031.** Название группы обязано иметь длину от 1 до 60 символов после отбрасывания
крайних пробелов.

**SP-032.** Название из одних пробелов обязано отклоняться.

**SP-033.** Название обязано сохраняться с отброшенными крайними пробелами.

**SP-034.** Запрос несуществующей группы обязан возвращать ошибку «не найдено».

**SP-035.** Список групп обязан возвращать все созданные группы.

## 4. Участники

**SP-040.** Добавление участника обязано принимать имя и возвращать созданного участника.

**SP-041.** Имя участника обязано иметь длину от 1 до 40 символов после отбрасывания
крайних пробелов.

**SP-042.** Имена участников обязаны быть уникальны в пределах группы **без учёта регистра
и крайних пробелов**: при наличии `Аня` добавление `аня` и ` Аня ` обязано отклоняться.

**SP-043.** Группа обязана вмещать не более 20 участников. Добавление двадцать первого —
ошибка.

**SP-044.** Участник обязан удаляться, если он не участвует ни в одном расходе.

**SP-045.** Удаление участника, который является плательщиком или входит в состав деления
хотя бы одного расхода, обязано отклоняться с ошибкой конфликта.

**SP-046.** Добавление участника в несуществующую группу обязано возвращать «не найдено».

**SP-047.** Удаление несуществующего участника обязано возвращать «не найдено».

## 5. Расходы

**SP-050.** Добавление расхода обязано принимать: плательщика, сумму, описание, способ
деления и состав деления.

**SP-051.** Плательщик обязан быть участником той же группы. Идентификатор участника
другой группы обязан отклоняться.

**SP-052.** Состав деления обязан быть непустым и обязан состоять только из участников
этой группы.

**SP-053.** Повторение одного участника в составе деления обязано отклоняться.

**SP-054.** Описание расхода обязано иметь длину не более 140 символов. Пустое описание
допускается.

**SP-055.** Плательщик не обязан входить в состав деления: допустима ситуация, когда один
заплатил за других и на него самого ничего не начисляется.

**SP-056.** Список расходов группы обязан возвращать расходы в порядке добавления.

**SP-057.** Удаление расхода обязано удалять его из группы и обязано отражаться
в балансах немедленно.

**SP-058.** Повторное удаление уже удалённого расхода обязано возвращать «не найдено».

**SP-059.** Добавление расхода в несуществующую группу обязано возвращать «не найдено».

## 6. Способы деления

**SP-060.** Приложение обязано поддерживать три способа деления: `equal` — поровну,
`shares` — по долям, `exact` — точными суммами. Иной способ обязан отклоняться.

### Поровну (`equal`)

**SP-061.** Сумма обязана делиться поровну между участниками состава деления.

**SP-062.** При неделимом остатке лишние копейки обязаны раздаваться по одной копейке
участникам **в порядке их добавления в группу**, начиная с первого.

**SP-063.** Сумма начислений обязана в точности равняться сумме расхода. Пример:
`"100.00"` на троих → `33.34`, `33.33`, `33.33`.

**SP-064.** Расход в одну копейку на троих обязан начислить `0.01`, `0.00`, `0.00`.

### По долям (`shares`)

**SP-065.** Доли обязаны задаваться целыми числами от 1 до 1000 включительно.

**SP-066.** Доля, равная нулю, отрицательная или дробная, обязана отклоняться.

**SP-067.** Начисление обязано считаться методом наибольшего остатка: каждому — целая
часть от `сумма × доля ÷ сумма_долей`, затем оставшиеся копейки раздаются по одной
участникам с наибольшей дробной частью; при равных дробных частях — в порядке добавления
участников.

**SP-068.** Сумма начислений обязана в точности равняться сумме расхода.

### Точными суммами (`exact`)

**SP-069.** Каждому участнику состава деления обязана задаваться точная сумма в том же
формате, что и сумма расхода.

**SP-070.** Точная сумма обязана быть не меньше нуля. Ноль допускается, отрицательная —
ошибка.

**SP-071.** Сумма точных сумм обязана в точности равняться сумме расхода. Расхождение
хотя бы в одну копейку обязано отклоняться с ошибкой.

## 7. Балансы

**SP-080.** Баланс участника обязан считаться как: сколько он заплатил, минус сколько
на него начислено.

**SP-081.** Сумма балансов всех участников группы обязана быть равна нулю **всегда**,
при любом наборе расходов и любом способе деления.

**SP-082.** Балансы обязаны возвращаться для всех участников группы, включая тех, у кого
баланс нулевой.

**SP-083.** Группа без расходов обязана возвращать нулевые балансы для всех участников,
а не пустой список.

**SP-084.** Балансы обязаны пересчитываться на момент запроса и обязаны отражать все
добавления и удаления расходов.

## 8. Переводы

**SP-090.** Приложение обязано возвращать список переводов, гасящих все балансы в ноль.

**SP-091.** Каждый перевод обязан содержать: от кого, кому, сумму.

**SP-092.** Сумма каждого перевода обязана быть строго больше нуля. Переводы на ноль
в список не входят.

**SP-093.** Число переводов обязано быть не больше, чем число участников с ненулевым
балансом, минус один.

**SP-094.** Применение всех переводов к балансам обязано обнулять их полностью, без
остатка в копейках.

**SP-095.** Участник не обязан переводить сам себе: перевод, где отправитель и получатель
совпадают, обязан отсутствовать.

**SP-096.** Группа с нулевыми балансами обязана возвращать пустой список переводов.

## 9. Протокол и ошибки

**SP-100.** Все ответы API обязаны иметь `Content-Type: application/json; charset=utf-8`.

**SP-101.** Тело ошибки обязано иметь вид `{"error": {"code": "...", "message": "..."}}`.

**SP-102.** Коды ошибок обязаны быть из фиксированного набора: `VALIDATION_ERROR`,
`NOT_FOUND`, `CONFLICT`, `MALFORMED_JSON`, `METHOD_NOT_ALLOWED`.

**SP-103.** Ошибка проверки данных обязана возвращать статус `400` и код
`VALIDATION_ERROR`.

**SP-104.** Отсутствующая сущность обязана возвращать статус `404` и код `NOT_FOUND`.

**SP-105.** Конфликт состояния — например, удаление участника с расходами — обязан
возвращать статус `409` и код `CONFLICT`.

**SP-106.** Тело запроса, не являющееся корректным JSON, обязано возвращать статус `400`
и код `MALFORMED_JSON`, а не приводить к падению процесса.

**SP-107.** Обращение к существующему пути неподдерживаемым методом обязано возвращать
статус `405` и код `METHOD_NOT_ALLOWED`.

**SP-108.** Сообщение об ошибке обязано называть конкретное поле или причину. Сообщение
вида «ошибка» без уточнения требованию не удовлетворяет.

**SP-109.** Успешное создание обязано возвращать статус `201`, успешное чтение — `200`,
успешное удаление — `204` с пустым телом.

**SP-110.** Неизвестное поле в теле запроса обязано игнорироваться, а не приводить
к ошибке.

**SP-111.** Отсутствие обязательного поля обязано возвращать `VALIDATION_ERROR`,
а не приводить к падению процесса.

**SP-112.** Значение неверного типа — число вместо строки, строка вместо массива —
обязано возвращать `VALIDATION_ERROR`, а не приводить к падению процесса.

**SP-113.** Процесс обязан оставаться работоспособным после любого некорректного запроса:
следующий корректный запрос обязан обслуживаться нормально.

**SP-114.** `GET /api/health` обязан возвращать статус `200`.

## 11. Интерфейс

**SP-130.** Страница обязана отдаваться по адресу `/` и обязана работать без обращений
в сеть.

**SP-131.** Страница обязана позволять: создать группу, добавить участника, добавить
расход, увидеть список расходов, увидеть балансы, увидеть переводы.

**SP-132.** Страница обязана показывать ошибку, вернувшуюся от API, текстом, а не молча
игнорировать её.

**SP-133.** Денежные величины на странице обязаны отображаться с двумя знаками после точки.

значениями:

заполнен ли соответствующий блок данными.

# ЧАСТЬ III. ВНЕ РАМОК

Ниже — то, чего в приложении быть **не должно**. Наличие этого не улучшает результат,
а расширяет поверхность проверки без пользы.

- Регистрация, вход, пароли, сессии, права доступа.
- Несколько валют, курсы, конвертация.
- Загрузка файлов, чеки, изображения.
- Уведомления, почта, экспорт.
- Редактирование расхода после создания — расход удаляется и создаётся заново.
- Повторяющиеся и запланированные расходы.
- История изменений, отмена действия.
- Мобильная вёрстка, оформление, анимация. Интерфейс должен быть работающим, а не красивым.
- Любые внешние библиотеки, шрифты, стили и скрипты, загружаемые из сети.

# ЧАСТЬ IV. ПРИЁМКА

Приложение считается принятым, когда выполнены все условия:

1. `node app/server.js` запускается на чистой машине без единой предварительной команды,
   и в stdout появляется адрес прослушивания.
2. `GET /api/health` отвечает `200`.
3. Страница `/` открывается и позволяет пройти путь целиком: создать группу → добавить
   трёх участников → добавить расход → увидеть балансы и переводы.
4. В поставке нет внешних зависимостей: `npm install` нигде не требуется, обращений
   в сеть при работе нет.
5. Все пути из `SP-120` отвечают — хотя бы кодом ошибки в формате `SP-101`, а не разрывом
   соединения.

**Приёмка не означает отсутствия дефектов.** Она означает, что объект пригоден для
проверки. Соответствие требованиям `SP-001`–`SP-135` проверяется отдельно, и найденные
расхождения фиксируются в отчёте, а не исправляются.
