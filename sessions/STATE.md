# 1. Что это за работа

Репозиторий — **не приложение, а набор проверок и доказательств прогона**.
По условию задания результат для направления QA — работающий набор проверок, который
прогоняется и даёт результат, плюс отчёт о прогоне.

**Объект тестирования** — веб-приложение **SplitPay** для совместного учёта общих расходов.
Приложение пишет **отдельный субагент с чистым контекстом**. Он не участвует в обсуждении
проверок. Смысл разделения: объект тестирования должен быть написан независимо от того,
чем его будут проверять, иначе автор и проверяющий — один контекст, и проверки подтверждают
собственные предположения, а не поведение приложения.

# 2. Роли и запреты

| Роль | Кто | Что делает | Чего не делает |
|---|---|---|---|
| Заказчик и QA | владелец репозитория | спецификация, проверки, прогон, отчёт | не пишет код приложения |
| Автор приложения | отдельный субагент, чистый контекст | пишет SplitPay по заказу | не видит проверок, не участвует в их обсуждении |
| Независимый проверяющий | отдельный агент, отдельная сессия | ломает чужие чек-листы, ищет дыры | не проверяет собственную работу |

**Запреты, действующие на всю работу:**

1. **Код приложения не читаем и не правим.** SplitPay тестируется как чужое. Все выводы —
   по наблюдаемому поведению: через API и через интерфейс. Заглядывание в исходники, чтобы
   понять «как оно там устроено», обесценивает проверку.
2. **Найденные дефекты фиксируются, а не исправляются.** Работа QA заканчивается отчётом.
3. **Автор не проверяет себя.** Любая независимая проверка — отдельная сессия, отдельный
   агент.
4. **Файлов-заготовок с плейсхолдерами не создаём.** Либо файл заполнен, либо его нет.
   `.gitkeep` в пустых каталогах — тоже заготовка, не создаём; каталог попадает в историю
   вместе с первым реальным содержимым.
5. **Материалы курса в сдачу не попадают** — внесены в `.gitignore`, проверено
   через `git check-ignore`.
6. **Промпт фиксируется в журнале до выполнения.** Не записан — действие не выполняется.
7. **Варианты подаются без рекомендации** — плюсы и минусы, решение за владельцем.
8. **Документ, определяющий предмет работы, не создаётся из догадок.** Нет постановки —
   либо запросить её, либо пометить прямо в документе, какие разделы являются
   предположением агента. Проверочный вопрос: на какое сообщение заказчика опирается
   каждый раздел? Нет ответа — это домысел, и он обязан быть помечен. Объём документа
   не является признаком его обоснованности. Основание — случай Н-1 в `REPORT.md`.
9. **Механизм проверяется на отказ, а не на согласие.** Защита, которая не была
   продемонстрирована отказом, считается неработающей. Основание — случай Н-2
   в `REPORT.md`: первая версия pre-commit хука молча пропускала материалы курса
   и выглядела рабочей.

# 6. Известные риски, обходы и ограничения

Полные разборы — в `REPORT.md`. Здесь то, что должна знать следующая сессия, чтобы
не наступить.

## Р-1. Git работает без права на удаление файлов

Оболочка на локальной машине не может удалять файлы: `rm` внутри подключённой папки
возвращает `Operation not permitted`. Git из-за этого оставляет за собой мёртвые
`*.lock` (`index.lock`, `HEAD.lock`, `objects/maintenance.lock`), и следующая операция
падает с `Unable to create ... File exists`.

**Механика.** Операция, кончающаяся записью, **переименовывает** замок в целевой файл —
переименование разрешено, такие команды проходят. Операция, кончающаяся без записи
(например `git status`), должна замок **удалить** — вот здесь отказ.

**Обход.** Перед каждой git-операцией оставшиеся `*.lock` переносятся в `.git/_trash/`,
туда же складываются недоудалённые `.git/objects/**/tmp_obj_*`.

**Почему это риск.** Замок защищает индекс от одновременного доступа. Снимая его,
мы снимаем защиту. Пока процесс один — все замки заведомо мёртвые, последствий нет.
Как только процессов больше одного, предположение ломается.

**Штатное решение недоступно:** инструмента запроса права на удаление
(`device_request_delete_permission`) в этой сборке нет; поиск по имени и по описанию
возвращает только `device_request_folder_access`, который прав на удаление не даёт.

**Четыре согласованных правила работы под обходом:**

1. В репозитории в каждый момент времени работает **ровно один** процесс.
2. Перед снятием замка проверить, не идёт ли операция в другом worktree. Идёт — ждать.
3. На worktrees и merge замки снимаются **поштучно и осознанно**, по имени файла,
   а не пакетным `find`.
4. После каждого коммита подтверждать целостность: `git status --short` (пусто = чисто),
   `git log --oneline`, `git show --stat`.

## О-1. Ограничение для сессии с worktrees: git-операции не выполняются параллельно

Прямое следствие Р-1 и отдельная договорённость на будущее.

В сессии с worktrees три агента будут писать тесты параллельно. **Писать файлы
параллельно — можно. Выполнять git-операции одновременно — нельзя.**

Допустимые схемы, любая на выбор:

- **Коммитит один.** Агенты только пишут файлы в своих worktree; все `git add`
  и `git commit` делает главная сессия, последовательно, после того как агент отчитался.
- **По очереди с ожиданием.** Агент, которому нужна git-операция, дожидается, пока
  освободится очередь, и только потом выполняет свою команду. Одновременных вызовов
  быть не должно.

Причина: worktrees делят общий каталог `.git`. Замок, снятый вслепую, может относиться
к живой операции соседнего worktree, а не к мёртвой. Цена — повреждённый индекс:
объекты обычно целы, но история шага теряется.

Уборка worktrees обязательна (`git worktree remove`, `git worktree prune`) — на курсе
приводился случай, когда на одном проекте накопилось 250 ГБ.

## Н-3 / Н-4. Побочные эффекты, о которых должна знать следующая сессия

**Файлы, которые нельзя удалить.** На диске остались и не удаляются средой:

**Хук срабатывает на журнале сессий.** `sessions/session-1.md` содержит дословный промпт
заказчика со строкой-образцом присваивания ключа. Хук на неё честно срабатывает.
Решение: журнал коммитится отдельным коммитом с `git commit --no-verify`, с объяснением
в сообщении коммита. **Общим режимом работы без проверок это не становится.**
Ослаблять образец в хуке и вносить журнал в исключения запрещено: журнал промптов —
как раз то место, куда реальный ключ и попадёт.

## О-3. Утверждение «внесено в .gitignore» без проверки — не факт

`STATE.md` три сессии утверждал, что рабочие остатки «внесены в `.gitignore`,
в репозиторий не входят». Сплошная проверка 28 августа показала, что внесены
были только `_transfer/` и `evidence/hook-demo.txt`; `_pending/`
и `_do-git-steps.sh` не игнорировались и уехали бы в репозиторий с первым
`git add -A`.

Вторая находка того же прохода: защита материалов курса и в `.gitignore`,
и в `pre-commit` держалась на точном совпадении разделителя `·` (U+00B7).
Промах на один символ отключил бы оба правила молча — тем же способом,
которым первая версия хука уже один раз пропустила материалы (Н-2).

**Закрыто:** в `.gitignore` добавлены `_pending/`, `_do-git-steps.sh`,
`_to_delete/`; в оба места добавлены широкие маски `04 *` / `05 *`.

**Правило.** Строка в `.gitignore` — не доказательство. Доказательство —
вывод `git check-ignore -v` по конкретному файлу. Это применение правила 9
к тому, чей результат — отсутствие чего-то. Разбор — `evidence/secrets-scan.md`.

## Р-3. Лимит сессии убивает субагентов на полном ходу

Обнаружено в сессии 2. Среда обрывает работу ответом
`You've hit your session limit · resets HH:MM (UTC)`. Обрыв приходит без предупреждения
и убивает **всех параллельных агентов разом**.

**Два разных исхода, и они не равноценны:**

1. Обрыв до записи файла — работа агента потеряна целиком. Первая попытка запуска
   веера: три агента, 73 тыс. токенов только у одного из них, ноль файлов.
2. Обрыв после записи файла, но до финального отчёта — **файл цел, отчёт потерян**.
   Так оборвало агента B. Файл на 120 КБ был полон, но собственный финишный `date -u`
   агент вернуть не успел, и доказательство времени пришлось восстанавливать снаружи
   по времени модификации файла и длительности вызова.

**Следствия для следующих сессий:**

- Оборванного агента можно **переспросить через `SendMessage` по его идентификатору**
  уже после обрыва: контекст жив, агент отвечает. Так был подтверждён старт агента B.
  Это дешевле, чем перезапускать агента заново.
- Агент, чей результат — файл, обязан **писать файл, а не копить его в ответе**.
  Файл переживает обрыв, ответ — нет.
- Всё, что нужно для доказательства (времена, счётчики), агент обязан снимать
  **в файл по ходу работы**, а не возвращать в финальном сообщении. Показание,
  существующее только в ответе агента, — это показание, которого может не быть.
- Планировать веер так, чтобы потеря одного агента не рушила остальных: зоны
  независимы, файлы раздельны, никакой агент не ждёт результата соседнего.

## Р-1, дополнение: замки переживают архивацию и переезд

Обход Р-1 написан для работающей сессии на одной машине: перед git-операцией
снять мёртвые `*.lock`. Перенос репозитория git-операцией не является и под
правило не попадал. В сессии 3 архиватор упаковал `.git` вместе с замками,
и первый же коммит на новой машине упёрся в замок от процесса, которого
на этой машине никогда не было.

**Правило:** снятие замков — часть операции переноса. Проверять `.git/*.lock`
и `.git/objects/**/tmp_obj_*` **перед архивацией** и **первым действием после
распаковки**. Полный разбор — случай Н-6 в `REPORT.md`.

## О-2. `git worktree prune` не убирает заблокированные записи

Заблокированную запись (`.git/worktrees/<имя>/locked`) `prune` пропускает
намеренно: блокировка существует для worktree на съёмном носителе, который
сейчас недоступен. Снаружи это выглядит как отказ уборки — каталога нет,
`git worktree list` запись показывает, `prune` отрабатывает без ошибки
и без эффекта.

Снимается `git worktree unlock <путь>` с последующим `prune`, либо
`git worktree remove --force`, либо удалением каталога записи вручную.

**Правило:** уборка подтверждается состоянием, а не кодом возврата. После
`git worktree prune` выполнять `git worktree list` и убеждаться, что записи
нет. Это применение правила 9 («механизм проверяется на отказ») к командам,
чей результат — отсутствие чего-то. Полный разбор — случай Н-7 в `REPORT.md`.
