# Workflow: повторяемая процедура регрессионного прогона

В этом проекте workflow существует в **двух форматах**, и они закрывают разные
случаи. Это не дублирование — это разделение по признаку «кто нажимает кнопку».

| Формат | Файл | Кто запускает | Можно ли обойти |
|---|---|---|---|
| Процедура прогона | `workflow/qa-regress` | владелец репозитория, вручную | да — просто не запустить |
| Защита коммита | `.githooks/pre-commit` | никто, срабатывает сам на `git commit` | нет: это не правило, а механизм |

Хук описан в `REPORT.md` (случаи Н-2 и Н-4), доказательство его отказа —
`evidence/hook-refusal.txt`. Здесь — про `qa-regress`.

---

## Что делает `qa-regress`

Шесть шагов. Каждый оставляет после себя файл в `evidence/run-<дата>/`.
Файла нет — шаг не выполнен: то же правило, по которому в этом проекте живёт
весь набор проверок.

| Шаг | Что происходит | Файл-доказательство |
|---|---|---|
| 0 | Контекст: HEAD, версии, снятые замки, наличие Playwright | `00-context.txt` |
| 1 | Изменения от тега `last-qa-run` | `01-base.txt`, `01-changed-files.txt` |
| 2 | Сопоставление изменений с зонами A/B/C по `workflow/zones.map` | `02-zone-map.txt` |
| 3 | Прогон только затронутых зон, API и UI | `03-run-api.txt`, `03-run-ui.txt`, `03-counts.tsv` |
| 4 | Задание независимому агенту и его вердикт «заявлено / фактически» | `04-audit-task.md`, `04-audit-verdict.md` |
| 5 | Сборка отчёта из файлов каталога | `05-report.md` |
| 6 | Перестановка тега `last-qa-run` на текущий HEAD | `06-tag.txt` |

## Как вызывать

```
workflow/qa-regress run          # шаги 0–4: прогон и подготовка задания агенту
                                 # ... здесь работает независимый агент ...
workflow/qa-regress finish       # шаги 5–6: отчёт и тег
```

Ключи:

```
workflow/qa-regress run --base <ref>   # сравнивать не с тегом, а с указанной точкой
workflow/qa-regress run --all          # прогнать все зоны, минуя сопоставление
workflow/qa-regress run --no-ui        # пропустить UI-слой
```

## Почему процедура разорвана на два вызова

Шаг 4 — независимая сверка. Между `run` и `finish` работает **отдельный агент
с чистым контекстом**: он получает `04-audit-task.md`, читает только
перечисленные там файлы и кладёт рядом `04-audit-verdict.md`.

Разрыв сделан намеренно. Агент, проверяющий отчёт, написанный в том же
контексте, проверяет собственные предположения — это запрет 3 в
`sessions/STATE.md`. Без вердикта `finish` не собирает отчёт и отказывается
работать: шаг 4 не украшение, а условие продолжения.

Задание агенту генерируется процедурой, а не пишется руками, — иначе
формулировка вопроса подстраивается под уже известный ответ.

## Как работает сопоставление с зонами

Правила лежат в `workflow/zones.map` — текстовая таблица, а не логика внутри
скрипта, чтобы её можно было прочитать и оспорить.

- **Правки в `app/` перепрогоняют все три зоны.** Приложение тестируется как
  чужое, код не читаем (запрет 1) — значит, определить, какую зону задела
  правка, нельзя в принципе. Прогнать лишнее дешевле, чем пропустить.
- **Правки в `tests/` перепрогоняют только свою зону.**
- **Правки в `SPEC.md` разбираются по разделам:** процедура берёт заголовки
  ханков `git diff` и переводит номер раздела в зону по той же таблице.
- **Документация и журналы зон не задевают** — помечены `-`.
- **Ключа в таблице нет — берутся все три зоны.** Умолчание намеренно широкое.

## Живой прогон

Процедура прогнана целиком, от первого шага до тега. Вывод — в
`evidence/run-2026-08-27/`. Итог: 47 изменённых файлов от корневого коммита,
все три зоны, 135 тестов, 68 зелёных, 67 красных, вердикт независимой
сверки — «ЧИСТО».

`07-tag-check.txt` — повторный вызов сразу после первого: изменений от тега
ноль, прогон не запускался. Процедура различает «нечего прогонять»
и «прогон не сделан», и это разные файлы с разным выводом.

## Ограничения, о которых нужно знать

- **UI-слой прогоняется только там, где есть Playwright** — в облачном
  контейнере. На локальной машине реестр npm закрыт (`E403`, риск Р-2),
  и шаг 3 честно пишет об этом в `03-run-ui.txt` вместо того, чтобы
  промолчать или соврать зелёным.
- **Тег локальный.** На сервер он уезжает отдельной командой владельца:
  `git push --force origin last-qa-run`.
- **Перед git-операциями процедура уводит мёртвые `*.lock` в `.git/_trash/`**
  переименованием — на машине владельца среда запрещает удаление файлов
  (риск Р-1). Это обход, а не решение; разбор в `REPORT.md`.
