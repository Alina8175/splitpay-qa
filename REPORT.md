# Известные риски и ограничения

## Р-1. Git работает без права на удаление файлов — защита от гонок ослаблена

**Статус: не устранено. Обход действует весь день.**

### В чём проблема

Оболочка, через которую я работаю с папкой проекта на локальной машине, не имеет права
удалять файлы: любой `rm`, `rmdir` или `unlink` внутри подключённой папки возвращает
`Operation not permitted`. Это ограничение среды, а не настройка репозитория.

Git на это рассчитывать не может. Механика такая: почти каждая операция, меняющая
состояние репозитория, сначала создаёт файл-замок — `.git/index.lock`, `.git/HEAD.lock`,
`.git/objects/maintenance.lock`, локи на конкретные ссылки при работе с ветками. Дальше
возможны два исхода. Если операция завершается записью, git **переименовывает** замок
в целевой файл — например, `index.lock` → `index`. Переименование внутри папки разрешено,
поэтому такие операции проходят. Если же операция завершается без записи — а это, например,
`git status`, который взял замок, обновил индекс в памяти и ничего не поменял, — git должен
замок **удалить**. Вот здесь и приходит `Operation not permitted`, и замок остаётся лежать.

Следующая операция видит существующий `index.lock` и отказывается работать:

```
fatal: Unable to create '.../.git/index.lock': File exists.
Another git process seems to be running in this repository...
```

Ровно на этом упал первый `git commit`.

### Что делает обход

Перед каждой git-операцией я переношу оставшиеся `*.lock` в `.git/_trash/` (переименование
разрешено) и там же складываю недоудалённые временные объекты `.git/objects/**/tmp_obj_*`.

### Почему это риск, а не косметика

Замок существует именно для того, чтобы две операции не работали с индексом одновременно.
Снимая его до запуска команды, я снимаю эту защиту. Пока в репозитории работает ровно один
процесс — последствий нет, потому что все замки заведомо мёртвые: их некому было удалить.
Опасность появляется там, где процессов больше одного:

- **worktrees.** Несколько рабочих копий делят общий каталог `.git`. Замки на общие ссылки
  и на `objects` становятся общими, и снятый вслепую замок может относиться к **живой**
  операции соседнего worktree, а не к мёртвой.
- **merge.** Слияние — самая длинная операция с индексом. Снятие её замка в середине
  оставляет индекс в частично записанном состоянии; внешне это выглядит как исчезнувшие
  или задвоенные файлы в рабочем дереве.
- **параллельные агенты.** Если несколько агентов работают с репозиторием одновременно,
  предположение «все замки мёртвые» перестаёт быть верным.

Цена ошибки — повреждённый индекс. Объекты при этом обычно целы, и восстановление возможно
(`git reset`, пересборка индекса), но история шага теряется, а в однодневном темпе это дорого.

### Почему обход не заменён нормальным решением

Штатный путь — выдать оболочке право на удаление внутри папки проекта. Для этого нужен
инструмент запроса разрешения (`device_request_delete_permission`), который показал бы
подтверждение на устройстве. **В этой сборке инструмент отсутствует.** Поиск по точному
имени и по описанию вернул только `device_request_folder_access` — он расширяет доступ
к папкам, но права на удаление не выдаёт. Запросить разрешение нечем.

### Правила, которые из этого следуют

1. В репозитории в каждый момент времени работает **ровно один** процесс. Никаких
   параллельных git-команд.
2. Перед снятием замка проверять, не идёт ли операция в другом worktree. Если идёт —
   ждать, а не снимать.
3. На этапе worktrees и merge — снимать замки **поштучно и осознанно**, глядя на имя
   файла, а не пакетным `find`.
4. Мусор копится в `.git/_trash/`. В сдачу не попадает: каталог `.git` не отслеживается.

### Проверка целостности

После каждого коммита состояние подтверждается: `git status --short` (пусто = дерево
чистое), `git log --oneline` и состав коммита через `git show --stat`. Первый коммит
`e69f718` этой проверкой подтверждён — четыре файла, 504 строки, ничего лишнего.

## Р-2. Реестр npm недоступен из обоих окружений

**Статус: обойдено конструктивно, ограничение принято как данность.**

`npm ping` возвращает `E403` и на локальной машине, и в облачном контейнере. На локальной
машине `curl` показывает источник отказа прямо: `HTTP code 403 from proxy after CONNECT` —
соединение перехватывает исходящий прокси. Полный вывод — `evidence/env-check.md`.

Следствия приняты в план: приложение и проверки строятся на Node.js без внешних
зависимостей, ни один шаг не зависит от `npm install`. Playwright доступен только
в облачном контейнере (1.56.0, Chromium предустановлен), поэтому UI-проверки идут там,
а не на локальной машине.

Побочная польза: отказ прокси на `CONNECT` — это готовый **вывод неудачной попытки** выйти
за границу окружения, то самое доказательство изоляции, которое задание просит показать
выводом, а не словами.


## О-1. Worktrees: зачем понадобились, чем ограничены, чем кончились

### Зачем понадобились

Пункт задания «Агенты» требует нескольких независимых агентов, работающих параллельно.
Параллельно писать проверки в один рабочий каталог нельзя: три агента, редактирующие
файлы одного дерева, наступают друг другу на индекс. Штатное средство git для этого —
`git worktree`: несколько рабочих каталогов на один общий каталог `.git`, каждый на своей
ветке. Отсюда три ветки — `qa-A`, `qa-B`, `qa-C` — по зоне проверок на ветку.

### Чем ограничены — правило О-1

Worktrees делят **общий** каталог `.git`. Наложенное на это ограничение Р-1 (оболочка
на локальной машине не удаляет файлы, и обход состоит в переносе мёртвых `*.lock`
в `.git/_trash/`) даёт правило, которое пришлось объявить отдельно:

> **Писать файлы параллельно — можно. Выполнять git-операции одновременно — нельзя.**

Причина в том, что обход Р-1 снимает замок вслепую. Пока процесс один, все замки заведомо
мёртвые, и снимать их безопасно. Как только процессов больше одного, предположение ломается:
снятый замок может относиться к живой операции соседнего worktree. Цена — повреждённый
индекс: объекты обычно целы, а история шага теряется.

Допустимые схемы, любая на выбор:

- **Коммитит один.** Агенты только пишут файлы в своих worktree; все `git add` и `git commit`
  делает главная сессия, последовательно, после того как агент отчитался.
- **По очереди с ожиданием.** Агент, которому нужна git-операция, дожидается освобождения
  очереди и только потом выполняет свою команду.

Дополнительное правило, не выводимое из Р-1, а взятое с занятия: **уборка worktrees
обязательна** (`git worktree remove`, затем `git worktree prune`). На курсе приводился случай,
когда на одном проекте накопилось 250 ГБ забытых рабочих каталогов.

### Чем кончились

Каталоги worktree не пережили переезд между машинами (см. Н-5). Записи о них вычищены
командой `git worktree prune`, каталогов на диске больше нет. Уцелело ровно то, что было
закоммичено в ветки:

| Ветка | Что в ней | Состояние после переезда |
|---|---|---|
| `qa-A` | `tests/api/plan-a.test.mjs`, `tests/ui/plan-a.spec.mjs`, `evidence/run-A-api.txt` | цела |
| `qa-B` | `tests/api/plan-b.test.mjs`, `tests/ui/plan-b.spec.mjs`, `evidence/run-B-api.txt` | цела |
| `qa-C` | — | пуста: проверки зоны C писались в контейнере и закоммичены не были |

### Что из этого следует

**Worktree — это рабочий каталог, а не хранилище.** Пережила переезд не работа, лежавшая
в worktree, а работа, попавшая в коммит. Разница между `qa-A`/`qa-B` и `qa-C` — ровно одна
выполненная команда `git commit`, и она стоила заново написанных 38 проверок зоны C.

Это тот же вывод, что уже записан в Р-3 применительно к субагентам («агент, чей результат —
файл, обязан писать файл, а не копить его в ответе»), только на шаг дальше: **файл
переживает обрыв агента, но переезд машины переживает только коммит.**

# Что не сработало

Раздел ведётся по ходу работы. Записывается то, что пошло не так, включая случаи,
где ошибку допустил агент. Формулировки не смягчаются: смягчённая формулировка

## Н-1. Агент спроектировал продукт вместо заказчика и не спросил постановку

**Когда:** 25 августа, шаг «спецификация», между коммитами `cf681ab` и `6f5f4ea`.
**Цена: полный переписанный документ и потерянный шаг.**

### Что произошло

Агент получил задачу «дальше — SPEC.md» и написал `SPEC.md` версии 1.0: 140 строк
разделов и **90 пронумерованных требований** `SP-001`–`SP-135`, оформленных как контракт,
по которому будет писаться приложение и строиться все проверки.

Постановки заказчика при этом **не существовало в контексте**. Агент располагал ровно
двумя фактами, оба из ответа на уточняющий вопрос: название — SplitPay, и одна строка —
«веб-приложение для совместного учёта общих расходов». Всё остальное — состав сущностей,
способы распределения, правила округления, коды ошибок, список путей, четырнадцать
`data-testid` — агент придумал сам и подал как требования заказчика.

Ни одного вопроса о том, что приложение должно делать, задано не было.

### Чем это хуже, чем просто «придумал лишнего»

Агент не ограничился тем, что дописал требования. Он **выдумал запреты**. В версии 1.0
был раздел «Вне рамок» — список того, чего в приложении быть не должно. Туда попали
три вещи, которые в настоящей постановке были обязательными:

| Что агент запретил в 1.0 | Что было в постановке заказчика |
|---|---|
| «Регистрация, вход, пароли, сессии, права доступа» | «Пользователь не должен видеть данные чужих групп» — бизнес-правило |
| «Редактирование расхода после создания — расход удаляется и создаётся заново» | «После удаления **или изменения** расхода долги пересчитываются» — бизнес-правило |
| «Несколько валют, курсы, конвертация» | Валюта — поле расхода в списке полей |

То есть агент своей волей вычеркнул из продукта то, что заказчик считал обязательным,
и оформил это как согласованное ограничение объёма.

Помимо запретов, из постановки полностью отсутствовали: категория расхода, статусы
долга Pending/Paid, отметка долга оплаченным, история операций. А способ распределения
«по процентам» был подменён на «по долям» — похоже по звучанию, различно по проверкам:
у долей нет требования «сумма ровно 100».

### Как подробность работала маскировкой

Это главное в этом случае, и это стоит записать отдельно.

Документ на 90 требований со сквозной нумерацией, таблицами, граничными значениями,
разобранным правилом округления с примером `100.00 → 33.34 / 33.33 / 33.33` и отдельно
выделенным инвариантом «сумма балансов равна нулю всегда» **выглядит как результат
анализа предметной области**. Именно детальность создаёт впечатление, что за документом
стоит источник.

Источника не было. Чем подробнее агент домысливал, тем труднее было заметить, что он
домысливает. Короткий документ на десять строк вызвал бы вопрос «а откуда это?» —
документ на девяносто требований вопроса не вызвал.

Отдельно: агент завершил этот шаг вопросом заказчику — но вопрос был о том, **какие части
спецификации передать автору приложения**. То есть агент обсуждал способ использования
документа, ни разу не усомнившись в его содержании. Мелкое противоречие в собственных
формулировках он заметил и вынес на обсуждение, а отсутствие постановки целиком — нет.

### Как это обнаружилось

**Не процессом. Заказчиком, при чтении.**

Заказчик открыл `SPEC.md`, не нашёл в нём своей постановки и написал «Стоп».
Опознавательным признаком послужило то, что три её бизнес-правила оказались в разделе
«вне рамок» — то есть документ не просто не покрывал постановку, а прямо ей противоречил.

Ни один шаг рабочего процесса этого не ловил и поймать не мог:

- проверки на этот момент ещё не писались;
- независимый проверяющий на этом этапе не запускался;
- `git`, чек-лист требований и `STATE.md` следят за полнотой сдачи и за процессом,
  но ни один из них не проверяет, откуда взялось содержание документа;
- сам агент подтверждения источника не искал.

Если бы заказчик не прочитал документ целиком, дальше пошло бы так: приложение пишется
по выдуманному контракту, три субагента веером строят тест-планы по выдуманным
требованиям, все проверки проходят, отчёт показывает соответствие. Работа выглядела бы
безупречно и не имела бы отношения к задаче. **Обнаружение было случайным
по отношению к процессу.**

### Что исправлено

`SPEC.md` доведён до версии 1.1: добавлено 46 требований, изменены 22, три запрета
из «вне рамок» переведены в требования. В документ добавлена Часть 0 — постановка
заказчика дословно и таблица трассировки: какое требование закрывает какой пункт
функционала и какое бизнес-правило. Версия 1.0 сохранена в журнале изменений построчно,
чтобы расхождение было видно, а не заглажено.

Dashboard и фильтрация истории оставлены вне рамок — **это решение заказчика,
подтверждённое явно**, и в документе помечено именно так, отдельно от того, что
не входит в продукт.

### Правило, которое из этого следует

**Документ, определяющий предмет работы, не создаётся из догадок.** Если постановки нет,
у агента ровно два допустимых хода: запросить её, либо написать документ и **пометить
в самом документе**, какие разделы являются предположением агента, а не требованием
заказчика.

Проверочный вопрос перед созданием такого документа: *на какое сообщение заказчика
опирается каждый раздел?* Если ответа нет — это домысел, и он обязан быть помечен
как домысел.

Отдельно: **объём документа не является признаком его обоснованности.** Подробность
маскирует отсутствие источника тем сильнее, чем её больше.

## Н-2. Первая версия pre-commit хука молча пропускала материалы курса

**Найдено демонстрацией. Если бы демонстрации не было — ушло бы в сдачу как рабочая
защита.**

### Что произошло

Хук `.githooks/pre-commit` написан с двумя правилами: блокировать похожее на секреты
и блокировать файлы материалов курса. Первое правило сработало сразу. Второе —
не сработало вовсе:

```
$ git add -f "04 · Домашнее задание №2.md"
$ git commit -m "проверка второго правила"
[main 694e044] проверка второго правила
 1 file changed, 387 insertions(+)
```

Материалы курса попали в коммит. Отказа не было — было тихое согласие.

### Причина

`git diff --cached --name-only` **без флага `-z`** печатает имена с не-ASCII символами
в кавычках и восьмеричных escape-последовательностях:

```
$ git diff --cached --name-only
"04 \302\267 \320\224\320\276\320\274\320\260\321\210\320\275\320\265\320\265 ..."

$ git diff --cached --name-only -z | tr '\0' '\n'
04 · Домашнее задание №2.md
```

Сравнение по образцу `"04 · "*` не совпадало никогда. Русские имена файлов —
не экзотика в этом проекте, а норма: так называются оба файла задания.

### Исправлено

Чтение списка файлов переведено на `-z` с NUL-разделителем. Ошибочный коммит `694e044`
откачен через `git reset --mixed HEAD~1`, история вернулась к `67525fe`. После
исправления оба правила блокируют коммит — протокол в `evidence/hook-refusal.txt`,
включая неудачную первую попытку.

### Правило, которое из этого следует

**Механизм проверяется на отказ, а не на согласие.** Хук, который ни разу не отказал,
неотличим от хука, который ничего не проверяет. Оба «работают»: коммиты проходят.

Если бы демонстрация ограничилась первым правилом — а оно сработало с первого раза —
защита выглядела бы полностью рабочей. В отчёт ушла бы строчка «хук блокирует секреты
и материалы курса», и она была бы наполовину ложью.

Отдельно стоит отметить: требование продемонстрировать отказ пришло от заказчика,
а не от агента. Агент написал хук и был готов считать его готовым.

## Н-3. Следствие Р-1: демонстрационный файл невозможно удалить

Задание требовало доказать работу хука файлом с секретоподобной строкой.
`evidence/hook-demo.txt` создан, отказ получен, файл больше не нужен — но **удалить его
среда не даёт**: `rm` внутри подключённой папки возвращает `Operation not permitted`
(риск Р-1).

Файл внесён в `.gitignore` и в репозиторий не попадает. На диске он остаётся.

Это прямая цена ограничения среды: там, где нормальной уборкой был бы `rm`, остаётся

## Н-4. Хук срабатывает на легитимном тексте в журнале сессий

Обнаружено сразу после включения хука.

Журнал `sessions/session-1.md` содержит промпты заказчика **дословно** — таково
требование задания. Один из промптов содержит строку-образец с присваиванием ключа,
приведённую заказчиком как пример того, что хук должен ловить. Хук честно на неё
и срабатывает.

Получается противоречие двух требований: «промпты дословно» против «не коммитить
похожее на секреты».

**Разобрано так.** Ослаблять образец нельзя: понижение чувствительности ради удобства —
это ровно то, как защита превращается в декорацию. Вносить журнал в исключения тоже
нельзя: журнал промптов — как раз то место, куда реальный ключ и попадёт, если его
случайно вставят в промпт.

**Принятое решение:** журнал коммитится **отдельным коммитом с `--no-verify`**, чтобы
обход был изолирован, виден в истории и объяснён в сообщении коммита. Всё остальное
проходит через хук штатно. Каждый следующий раз, когда журнал споткнётся о хук, —
такой же отдельный коммит с обоснованием, а не общий режим работы без проверок.

Слабое место решения названо прямо: `--no-verify` работает и тогда, когда обходят
не образец в журнале, а настоящий ключ. Механизм здесь опирается на то, что обход
виден в истории и требует отдельного действия, а не на невозможность обхода.

**Честно про границы механизма.** Задание противопоставляет правило-просьбу и механизм,
который нельзя обойти сменой команды. Git-хук — механизм: он висит на действии «создать
коммит», а не на строке команды, и переформулировкой не обходится. Но `--no-verify`
его отключает. Это осознанное отдельное действие, видимое в истории команд, — не то же
самое, что обход переформулировкой, но и не абсолютная преграда. Абсолютной здесь
не бывает: хук живёт в `.git/config`, а при свежем клоне `core.hooksPath` придётся
включить заново.


## Н-5. Обрыв моста до машины и переезд между машинами

### Что произошло

Сессия 3 оборвалась в момент переезда между машинами. В момент обрыва зона C существовала
только как файлы в контейнере: ветка `qa-C` была создана, но пуста. Каталоги worktree
на прежней машине не сохранились, записи о них вычищены `git worktree prune`.

Сессия 4 (27 августа) началась с того же класса отказа, но с другой стороны. Мост
до машины — MCP-сервер `remote-devices`, через который агент читает и пишет подключённые
папки, — не поднялся:

```
remote-devices (502): "Error POSTing to endpoint: { type : https://developers.cloudflare.com/
support/troubleshooting/http-status-codes/cloudflare-5xx-errors/error-502/ ,
title : Error 502: Bad gateway , status :502 …"
```

Проверено дважды, включая принудительный `RefreshMcpTools`: состояние соединения — `failed`.
Ни один инструмент семейства `device_*` в этой сессии не отвечал.

### Чем это хуже обычного сбоя

Отказ моста — не «медленно» и не «часть функций недоступна». Это **отказ всего**, потому что
через мост проходит единственный путь к предмету работы. В сессии 4 недоступными разом стали:

- `sessions/STATE.md` — рамка, правила и запреты, без которых работать нельзя;
- `tests/plan-C.md` — то, по чему пишутся проверки;
- `app/` — объект тестирования;
- `.git` — все ветки, вся история;
- запись промпта в журнал, которую правило 6 требует сделать **до** выполнения.

Правило 6 («промпт фиксируется в журнале до выполнения; не записан — действие не выполняется»)
при отказе моста превращается в блокировку целиком: записать нельзя, а значит нельзя ничего.
Промпт был сохранён в рабочую папку агента дословно и перенесён в `sessions/session-3.md`
владельцем репозитория вручную.

### Что сработало

Обход нашёлся не в починке моста, а в **смене пути к данным**: репозиторий был опубликован
на GitHub, и облачный контейнер склонировал его напрямую.

```
git clone https://github.com/Alina8175/splitpay-qa.git
```

После этого весь объём сессии 4 — 38 проверок зоны C, UI-спек зоны C, два полных прогона —
был выполнен в контейнере, а результат отдан файлами. Git-часть (коммиты, слияния, push)
осталась за владельцем репозитория: авторизации у контейнера нет и быть не должно.

### Правило, которое из этого следует

**У каждого шага должен быть путь к данным, не проходящий через мост.**

Мост между сессией и машиной — единственная точка отказа, и отказывает он целиком.
Опубликованный репозиторий — не только «выкладка результата», как он был записан
в плане работ, но и **резервный канал доставки предмета работы в сессию**. Стоило бы
выложить его раньше: в сессии 3 это сэкономило бы зону C, в сессии 4 — час на диагностику.

Второе следствие, менее очевидное: **коммит — это не оформление результата, а его
сохранение.** В обеих сессиях потеряно ровно то, что не было закоммичено, и уцелело ровно
то, что было. Цель «не менее 8 коммитов за день, по одному в конце смыслового шага»,
записанная в `STATE.md` как ответ на прошлую работу с двумя коммитами на девять сессий,
из дисциплины оформления превращается в дисциплину сохранности.

### Ограничение, которое осталось невыполненным

Прогон в контейнере не воспроизводит окружение локальной машины. Playwright есть только
в контейнере (факты окружения, `STATE.md` § 7), поэтому UI-слой на машине владельца
не прогонялся ни разу и прогнан быть не может. Это не обход и не риск, а граница: строки
«UI-проверки идут в облачном контейнере» в таблице решений достаточно, чтобы её объявить,
но не достаточно, чтобы её снять.

## Н-6. Риск Р-1 реализовался буквально: замки пережили архивацию

### Что произошло

Первый же коммит на новой машине не прошёл: в `.git` лежали файлы-замки,
приехавшие туда вместе с архивом репозитория. Процессов, которые их поставили,
на новой машине не существовало никогда.

### Механика

Р-1 описан в этом отчёте как риск с обходом: оболочка на локальной машине
не удаляет файлы, git из-за этого оставляет за собой мёртвые `*.lock`,
и перед каждой git-операцией их приходится переносить в `.git/_trash/`.
Обход написан для **работающей сессии на одной машине**: замок мёртвый,
процесс, поставивший его, заведомо завершён, снимаем и идём дальше.

Архивация ломает это рассуждение с другого конца. Архиватор не знает, что
`index.lock` — временный файл; для него это обычный файл в каталоге `.git`,
и он кладёт его в архив наравне с объектами и ссылками. На новой машине
распакованный репозиторий получает замок в наследство, и первая же операция,
кончающаяся записью, упирается в него.

Отдельная неприятность в том, что **момент архивации — это момент, когда замок
гарантированно ложный**: процесс, который его поставил, к тому времени точно
мёртв, потому что мы упаковываем каталог. То есть в архив попадает файл,
о котором в этот самый момент точно известно, что он не нужен.

### Почему это не было предусмотрено

Правило обхода Р-1 звучит как «перед каждой git-операцией снять оставшиеся
замки». Перенос репозитория на другую машину git-операцией не является,
под правило не попадает — и не попал. Риск был описан, обход работал,
но описан он был для одного сценария из двух.

### Правило, которое из этого следует

**Снятие замков — часть операции переноса, а не только часть git-операции.**
Перед архивацией и первым действием после распаковки проверять `.git/*.lock`
и `.git/objects/**/tmp_obj_*`. На машине, где среда не даёт удалять, —
переносить в `.git/_trash/`, как и по обходу Р-1.

Более общий вывод: риск, для которого написан обход, продолжает существовать
за границами того сценария, для которого обход написан. Р-1 был известен
с первого дня, обход применялся десятки раз — и всё равно сработал, потому
что сработал в другом месте.

### Чего в этом разборе нет

Консольного вывода отказа. Эпизод произошёл в сессии заказчика на её машине;
у агента, писавшего этот раздел, вывода нет, и он не восстанавливался
по памяти и не сочинялся. Если вывод сохранился — его место здесь.

## Н-7. Мёртвая запись worktree не убирается штатным `git worktree prune`

### Что произошло

Каталогов worktree после переезда не существовало, но запись о worktree
для ветки `qa-C` осталась в `.git/worktrees/` и не убиралась командой
`git worktree prune`. Запись была помечена как **заблокированная**.

### Механика

Это не сбой git, а его объявленное поведение. `git worktree prune` намеренно
**пропускает заблокированные записи**. Блокировка (`.git/worktrees/<имя>/locked`)
и существует ровно для того, чтобы уборка не снесла запись о рабочем каталоге,
который сейчас недоступен — например, лежит на съёмном носителе или на
отключённом сетевом диске. С точки зрения git заблокированная запись без
каталога — это не мусор, а временно недоступный worktree.

Отсюда результат, который снаружи выглядит как отказ уборки: каталога нет,
`git worktree list` его показывает, `prune` отрабатывает без ошибки и без
эффекта. Снимается это либо `git worktree unlock <путь>` с последующим `prune`,
либо `git worktree remove --force`, либо удалением каталога записи вручную.

### Почему это попало в отчёт

Потому что уборка worktrees была объявлена сделанной на основании того,
что команда отработала успешно. Она и отработала успешно — успешно ничего
не сделав.

Это ровно случай Н-2 в другой одежде. Там первая версия pre-commit хука молча
пропускала материалы курса и выглядела рабочей, потому что её не проверили
на отказ. Здесь `git worktree prune` молча пропустил заблокированную запись
и выглядел рабочим, потому что его не проверили на результат. В обоих случаях
успешный код возврата был принят за выполненную работу.

Правило 9 проекта — «механизм проверяется на отказ, а не на согласие» —
написано после Н-2 и здесь не сработало, потому что его применяли к защитным
механизмам (хук, проверка секретов), а `prune` защитным механизмом не выглядит.
Он выглядит уборкой.

### Правило, которое из этого следует

**Уборка подтверждается состоянием, а не кодом возврата.** После
`git worktree prune` полагается выполнить `git worktree list` и убедиться,
что записи нет. То же относится ко всякой команде, чей результат — отсутствие
чего-то: успешный выход означает «команда отработала», а не «объекта больше нет».

### Чего в этом разборе нет

Консольного вывода `git worktree list` и `git worktree prune` до и после.
Эпизод произошёл на машине заказчика; вывода у агента нет, и он не сочинялся.

## 2. Доказательство одновременности

|---|---|---|

когда параллельности уже нет.

Агент D в пересечение намеренно не входит: он обязан видеть уже готовые чужие планы,
поэтому запущен отдельно и позже.

## 3. Почему последовательного замера нет

Пункт необязательный, и он **не выполнен**. Причины называются прямо, без смягчения.

**Что помешало.**

1. **Лимит среды, дважды.** Первый веер убит на 4-й минуте ответом
   `You've hit your session limit · resets 5:20pm (UTC)` — три агента разом, ноль файлов.
   Второй веер отработал, но агента B оборвало тем же лимитом уже после записи файла
   (`resets 11:20pm (UTC)`). Между попытками — ожидание сброса. Полный разбор — риск Р-3
   в `sessions/STATE.md`.
2. **Цена второго полного прогона.** Последовательный замер — это не «то же самое,
   но по очереди»: это ещё раз три агента, каждый снова читает `SPEC.md` целиком, то есть
   ещё ≈ 600 тысяч токенов и ещё один заход под те же лимиты, которые уже дважды
   остановили работу. При 17 часах настенного времени, уже потраченных, второй прогон
   с высокой вероятностью упёрся бы в третий лимит.
3. **Решение заказчика.** Замер признан необязательным пунктом, цена — неприемлемой.
   Решение зафиксировано в промпте 2, `sessions/session-2.md`.

**Что из этого следует для трактовки цифр.** Отношение **2,09 — это измеренная
параллельность внутри прогона, а не измеренное ускорение против очереди.** Вывод
«последовательно заняло бы 42 минуты вместо 20» — это арифметическое следствие
из сложения длительностей, а не результат второго замера. Разница существенная,
и её нельзя проглатывать: сложение предполагает, что последовательный прогон выполнил
бы ровно ту же работу с той же длительностью каждого шага, а это предположение
не проверено.

**Чего параллельность не сэкономила.** Токены. Каждый из трёх агентов прочитал
`SPEC.md` целиком — спека пошла в контекст трижды. Параллельный веер экономит настенное
время и контекст **главной сессии**, а не общий объём. Общий объём он, скорее всего,
увеличивает.

## 4. Время / контекст главной сессии / качество

Таблица в том виде, в каком её просит задание.

| Измерение | Параллельный веер (замерено) | Последовательно (не замерено) |
|---|---|---|
| **Настенное время чистой работы** | 20 мин 11 с на три плана | не замерено; сложение длительностей даёт 42 мин 12 с |
| **Контекст главной сессии** | ≈ 192 300 из ≈ 883 100 — **21,8 %** | не замерено; при работе в одном контексте спека, три плана и аудит легли бы в главную сессию целиком |
| **Качество: объём** | 125 проверок, деньги до копейки, ожидания записаны до прогона | — |
| **Качество: независимая проверка** | 41 находка агента D, чистый контекст | — |
| **Качество: цена деления на зоны** | **щель между зонами** — требование `SP-152` не покрыл никто | — |

**Про качество — главное наблюдение замера, и оно не в пользу веера.**

Деление на зоны породило дефект, которого у одного автора быть не могло. Требование
`SP-152` — «при изменении расхода действуют те же проверки, что при создании» — не покрыто
ни одним из 125 кейсов: агент B решил, что матрица проверок полей это зона агента A,
а агент A отказался от всего блока `SP-150`–`SP-156` как от чужого. Каждый счёл требование
чужим, и оно выпало. Находка D-01.

Это цена приёма, а не случайность: три автора, не видящие работы друг друга, не могут
увидеть щель между собой **по построению**. Её видно только четвёртому, который смотрит
на три плана сразу и сверяет их с оракулом, а не с их собственными таблицами трассировки.
Отсюда практический вывод, который дороже цифры 2,09: **веер субагентов без замыкающего
независимого аудита — незаконченная конструкция.** Три агента дали 125 кейсов
и заявленное покрытие 138 из 138; четвёртый показал, что фактическое покрытие — 132
полноценно и 6 частично, и что два кейса плана C вообще неисполнимы и на прогоне занесли
бы в отчёт несуществующий дефект.

## 5. Сопоставление с замером, показанным на занятии

На занятии живой замер дал **128 тысяч токенов в главной сессии против почти миллиона
общего объёма** — около 13 %.

У нас — **≈ 192 тысячи против ≈ 883 тысяч, то есть 21,8 %**.

**Порядок величин совпал: главная сессия в обоих случаях расходует малую долю общего
объёма — десятки процентов в пределах одного порядка, а основная работа уходит
в контексты, которые в переписку не попадают.** Наше число получено **независимо
и на другой задаче**: другая предметная область, другая роль, другое число агентов,
другой состав работы. Совпадение порядка величин на независимом замере — это довод
в пользу того, что эффект относится к самому приёму, а не к конкретной демонстрации.

Дальше этого вывод не идёт, и растягивать его не следует. Два замера — это два замера,
а не закономерность. Наши 21,8 % против 13 % на занятии — разница почти вдвое,
и объяснить её нечем: состав работы разный, методики счёта главной сессии могут
не совпадать, а второго замера у нас нет. Сравнивается порядок величин, и только он.

# Workflow: два формата, и они закрывают разные случаи

Пункт 1.3 задания. В этом проекте workflow существует в двух видах, и разница
между ними не в оформлении, а в том, **кто нажимает кнопку**.

| Формат | Файл | Кто запускает | Можно ли обойти |
|---|---|---|---|
| Процедура регрессионного прогона | `workflow/qa-regress` | владелец репозитория, вручную | да — просто не запустить |
| Защита коммита | `.githooks/pre-commit` | никто, срабатывает сам на `git commit` | нет |

**Файл `qa-regress` я запускаю сама.** Он шесть шагов: изменения от тега
`last-qa-run` → сопоставление с зонами A/B/C по разделам `SPEC.md` → прогон
только затронутых зон → независимая сверка «заявлено / фактически» отдельным
агентом → сборка отчёта → перестановка тега. Каждый шаг оставляет файл
в `evidence/run-<дата>/`; файла нет — шаг не выполнен. Описание и вызовы —
`workflow/README.md`, живой прогон целиком — `evidence/run-2026-08-27/`.

**Хук `pre-commit` срабатывает без меня, и обойти его сменой команды нельзя.**
Это и есть причина, по которой защита сделана механизмом, а не правилом
в документе. Правило «не коммить материалы курса» обходится тем, что про него
забыли; хук выполняется git-ом на каждом `commit`, независимо от того, какую
команду набрали и что при этом думали. Его отказ показан выводом —
`evidence/hook-refusal.txt` (случай Н-2: первая версия хука молча пропускала
материалы курса и выглядела рабочей, пока её не проверили на отказ).

У обхода есть ровно одна дверь — `git commit --no-verify`, и она **видна
в истории**: коммиты, сделанные с этим ключом, названы в `STATE.md` вместе
с причиной (случай Н-4, журнал сессий содержит дословный промпт с образцом
присваивания ключа, и хук на него честно срабатывает). Обход, о котором
написано в отчёте, — не дыра в механизме, а зафиксированное решение.

**Почему нужны оба.** `qa-regress` отвечает на вопрос «что перепроверить
после изменений» и требует человека, чтобы начаться. Хук отвечает на вопрос
«что не должно уехать в репозиторий никогда» и человека не требует.
Заменить второй первым нельзя: процедура, которую можно не запустить,
защитой не является.

# Изоляция

Задание просит показать границу окружения **выводом неудачной попытки**,
а не описанием. Ниже — то, что было снято, и то, что из снятого следует.
Полные выводы: `evidence/env-check.md` (25 августа) и
`evidence/isolation-probe.txt` (28 августа).

## Отказы, снятые выводом

**Локальная машина, 25 августа — закрыто всё, отказ на `CONNECT`:**

```
--- npm ping
npm error code E403
npm error 403 403 Forbidden - GET https://registry.npmjs.org/-/ping
exit=1
--- curl registry.npmjs.org
curl: (56) Received HTTP code 403 from proxy after CONNECT
exit=56
```

`curl: (56) ... from proxy after CONNECT` — это отказ **исходящего прокси**,
а не сети: соединение перехвачено на этапе установления туннеля. Ни один
внешний адрес с этой машины не открывается, GitHub в том числе. Именно
поэтому UI-слой на машине заказчика не прогонялся ни разу: Playwright взять
неоткуда.

**Облачный контейнер, 25 августа — реестр npm закрыт:**

```
--- npm ping
npm error code E403
npm error 403 403 Forbidden - GET https://registry.npmjs.org/-/ping
exit=1
--- curl registry.npmjs.org
403
exit=0
```

Разница в форме отказа содержательна: на машине обрывается транспорт,
в контейнере приходит нормальный ответ `403`. Это две разные политики,
а не одна.

**Облачный контейнер, 28 августа — граница сдвинулась:**

```
$ npm ping
npm notice PING https://registry.npmjs.org/
npm notice PONG 136ms
exit=0

$ curl -sS -o /dev/null -w "%{http_code}\n" https://github.com/Alina8175/splitpay-qa
403
exit=0

$ git ls-remote https://github.com/Alina8175/splitpay-qa HEAD
c834fcd56350616b895e61e6ad3f90299610b425	HEAD
exit=0
```

## Три вывода, и второй из них я не ожидала

**1. Песочница накрывает оболочку того окружения, которому принадлежит,
и не переносится на другое.** Оболочка на машине заказчика закрыта наглухо.
Оболочка контейнера — нет. Работа, невозможная в одном окружении, спокойно
делается в другом; сессия 3 ровно так и спаслась, когда мост до машины лёг
и предмет работы был доставлен в контейнер клонированием с GitHub
(случай Н-5). Инструменты агента, работающие вне оболочки, — ещё один
отдельный канал с собственной политикой; в этой работе он не использовался
для доставки кода, и это стоит сказать прямо, потому что соблазн был.

**2. Граница проходит не по хосту, а по протоколу и пути.** `github.com`
отвечает `403` на обычный запрос страницы и в ту же секунду обслуживает
`git ls-remote` по тому же адресу. Один хост одновременно закрыт и открыт.
Вывод «GitHub недоступен» был бы ложью, вывод «GitHub доступен» — тоже.

**3. Граница не постоянна во времени.** Между 25 и 28 августа политика
контейнера изменилась: реестр npm, отвечавший `E403`, теперь отвечает `PONG`.
На этом основании построен целый пласт решений всей работы — «ни один шаг
не зависит от `npm install`», отказ от трёх сторонних инструментов
(`TOOLS.md`), выбор Node.js без зависимостей и для приложения, и для набора
проверок. Решения остаются верными: они принимались по состоянию среды
на момент принятия, и это состояние снято выводом. Но **утверждение
об изоляции действительно только вместе с датой и названием окружения**.
Бессрочного «здесь закрыта сеть» не бывает.

Свежей пробы с локальной машины в этой сессии нет и быть не может:
инструмента запуска команд на ней в этой сборке не существует, есть только
файловый мост. Её строка датирована 25 августа и за сегодняшнюю не выдаётся.

## Что из этого следует для сдачи

**Публикация осталась единственным шагом, который делает человек.** Прогон,
сборка отчёта, сверка чисел, перестановка тега — всё это делает процедура
или агент. `git push` — я.

И это ограничение **не техническое, а принятое**. Технически контейнер
достаёт до GitHub: `git ls-remote` в выводе выше отработал. Не хватает
только авторизации, и выдача агенту токена рассматривалась. Отказались
по причине, которая целиком лежит внутри этой работы: журнал промптов
ведётся дословно и лежит в публичном репозитории, промпт с токеном по
правилу 6 обязан попасть в журнал до выполнения — и токен утёк бы
не через ошибку и не через агента, а **через собственную сдачу**, ровно
тем механизмом, который здесь отвечает за честность. Разбор обходов
и почему каждый отклонён — `TOOLS.md`.

Из двух вещей — «агент делает всё сам» и «видно, что именно ему говорили» —
выбрана вторая.

# Что не сделано и почему

Раздел ведётся ради полноты картины, а не ради оправданий. Формат один:
что не сделано, по какой причине, и **что именно осталось непроверенным**.

## Независимая проверка чужого набора («ломатель») — не сделана

**Причина.** Требует отдельного агента с чистым контекстом, а по-хорошему —
нескольких: конструкция «веер плюс замыкающий аудит» в этом проекте уже
применялась к тест-планам и стоила заметной доли лимитов
(`evidence/subagents-run.md`). В финальной сессии лимиты заказчика
исчерпаны на 80 %, и запуск веера гарантированно оборвал бы сессию
до сдачи. Это тот же риск Р-3, который дважды убивал агентов на полном
ходу, только на этот раз он был виден заранее, и решение принято до, а не после.

**Что осталось непроверенным именно из-за этого:**

- **Классификация 67 красных по существу.** Правило отнесения выровнено
  (доктрина С-3, разбор `D-35` в `evidence/audit-resolution.md`), но
  правильность конкретных отнесений «дефект против заказа / расхождение
  с оракулом» в таблице находок проверялась при заполнении результата
  прогона — тем же контекстом, который её и заполнял.
- **Полнота покрытия набора чужим взглядом.** На аудите планов замыкающий
  агент нашёл щель, невидимую ни одному из трёх авторов по построению
  (`D-01`: три агента заявили 138 из 138, фактическое покрытие — 132).
  Тот же класс щели в написанных проверках никем не искался.
- **Достаточность самих ожиданий.** Кейс может быть зелёным потому, что
  приложение право, и потому, что проверка слабая. Различить это может
  только тот, кто её не писал.
- **Устойчивость `qa-regress` к враждебному входу.** Сверку «заявлено /
  фактически» на живом прогоне сделал независимый агент, и вердикт «ЧИСТО»
  снят честно. Но он проверял согласованность отчёта с выводом, а не
  пытался процедуру сломать.

## Проверка на инъекцию в промпт на двух моделях — не сделана

**Причина.** Та же: требует минимум двух агентов на разных моделях
и заполненной таблицы сравнения. Лимитов не хватит, а сделанная наполовину
проверка на инъекцию хуже несделанной — она создаёт впечатление проверенного.

**Что осталось непроверенным именно из-за этого:**

- **Данные приложения как канал инъекции.** SplitPay принимает от
  пользователя произвольный текст — названия групп, имена участников,
  описания расходов. Этот текст попадает в вывод прогона, оттуда
  в `evidence/`, оттуда в задание независимому агенту на шаге 4
  `qa-regress` и в отчёт. Никто не проверял, что будет, если в описание
  расхода положить строку, адресованную читающему агенту.
- **Задание агенту как канал.** `04-audit-task.md` процедура генерирует
  сама, подставляя в него имена изменённых файлов из `git diff`.
  Имя файла — тоже вход.
- **Различие между моделями.** Смысл требования «на двух моделях» —
  показать, что устойчивость не свойство одной. Не показано ничего.

**Отдельно.** Оба пункта — из необязательной части задания, «в плюс».
Ни один обязательный пункт по этой причине не пропущен.

## Н-8. Два промпта записаны задним числом

Правило 6 требует: промпт фиксируется в журнале **до** выполнения; не записан —
действие не выполняется. Промпты 1–3 сессии 1 записаны после действия, потому
что журнала на тот момент ещё не существовало — он заводился этими же промптами.

Формально это не нарушение — нарушать было нечего. По существу — да, и вот чем.
Дословность промпта ценна тем, что он записан **до** того, как стал известен
результат. Промпт, восстановленный после, восстанавливается человеком, который
уже знает, чем дело кончилось, и незаметно для себя формулирует его чуть точнее,
чем он был. Проверить это невозможно: свидетеля нет.

**Правило.** Журнал заводится первым действием сессии, до любого содержательного
шага. Записи, сделанные задним числом, помечаются прямо в журнале как таковые —
что и сделано в `sessions/session-1.md`.

## Н-10. Облачный агент отказался нарисовать вывод установки

Отдельному агенту было поручено показать, как выглядела бы установка стороннего
инструмента в среде, где реестр закрыт. Агент отказался — и был прав.

Просьба, если читать её буквально, — это просьба **изготовить вывод команды,
которая не выполнялась**. Такой вывод неотличим от настоящего: то же
форматирование, те же коды возврата. Попав в `evidence/`, он стал бы
доказательством того, чего не было, — в папке, весь смысл которой в том,
что в ней лежит снятое машиной.

**Чем это опасно именно здесь.** Весь проект построен на различении
«снято» и «написано»: кейс без зафиксированного результата в набор не входит,
числа в отчёте берутся из файлов, а не переписываются, механизм считается
рабочим только после демонстрации отказа. Один нарисованный вывод в `evidence/`
обесценивает не себя, а всю папку: читателю больше нечем отличить одно от другого.

**Что сделано вместо.** Отказ установки снят настоящим выводом настоящей
попытки — `evidence/env-check.md`, `npm ping` → `E403`. Он короче и скучнее
нарисованного, и он единственный, который что-то значит.

**Правило.** В `evidence/` попадает только вывод выполненной команды.
Реконструкция, пример и иллюстрация — в текст отчёта, с явной пометкой,
что это реконструкция.

## Форма сдачи

**Работа сдаётся репозиторием с историей, а не архивом.** В прошлый раз
сдавали архивом, и это скрывало главное: 23 коммита по смысловым шагам,
три ветки, три `merge --no-ff`, тег `last-qa-run` — это не оформление
результата, а показание о том, как он появлялся. Архив показывает только
конечное состояние, в котором доказательства выглядят возникшими
одномоментно. История показывает порядок, и порядок здесь — часть
содержания: спецификация до заказа, ожидания до прогона, аудит до
написания проверок.

# Размышления

**Самое дорогое решение всей работы принято в первый час и не выглядело
решением.** Развести автора приложения и проверяющего по разным контекстам —
одна строка в `STATE.md`. Из неё выросло всё остальное: `ORDER.md` отдельно
от `SPEC.md`, запрет читать код, 67 красных тестов, каждый из которых
что-то значит. Если бы приложение писал тот же контекст, что и проверки,
набор был бы зелёным — и не стоил бы ничего.

**Красный набор оказалось труднее защищать, чем зелёный.** Каждый раз, глядя
на `# fail 63`, хочется что-нибудь подкрутить. Не приложение — его нельзя,
запрет 2, — а ожидание: смягчить, отметить `xfail`, объявить неоднозначностью.
Каждая такая правка выглядит как повышение качества набора и является
уничтожением находки. Единственное, что помогло, — записать ожидания
до прогона и потом не иметь права их трогать.

**Механизм и правило — разные вещи, и я поняла разницу через отказ.**
Первая версия хука выглядела рабочей и молча пропускала материалы курса.
Она перестала выглядеть рабочей ровно в тот момент, когда её попросили
отказать. Отсюда правило 9, и оно оказалось самым продуктивным правилом
работы: `prune`, отработавший без ошибки и без эффекта (Н-7), пойман им же.

**Границы среды я описывала увереннее, чем имела право.** Три дня «реестр
npm недоступен» было фактом, снятым выводом. На четвёртый день проба
вернула `PONG`. Ничего из принятых решений это не отменяет — они
принимались по состоянию на момент принятия, — но фраза «в этом окружении
нельзя» без даты оказалась не фактом, а привычкой. Теперь я знаю, что
изоляция — это не свойство, а показание, и у показания есть время снятия.

**Автоматизировано всё, кроме одного шага, и этот шаг оставлен намеренно.**
Соблазн выдать агенту токен и закрыть последнюю ручную операцию был
сильным. Не сделано потому, что дословный публичный журнал — механизм,
и он работает в обе стороны: он не только показывает, что я делала,
он ещё и не даёт мне сделать то, о чём нельзя написать. Это неудобно
ровно в той степени, в какой полезно.

**Чего не хватило — не времени, а лимитов, и это разные дефициты.**
Времени можно было занять у следующего дня. Лимиты кончаются внутри
сессии, без предупреждения, и уносят с собой всё, что не записано в файл.
Отсюда единственный рабочий вывод, который я забираю с собой из этой
работы целиком: **агент, чей результат — файл, обязан писать файл,
а не копить его в ответе.** Всё остальное — детали.
