# Известные риски и ограничения

## Р-1. Git работает без права на удаление файлов — защита от гонок ослаблена

**Статус: не устранено. Обход действует весь день.**

### В чём проблема

Оболочка, через которую я работаю с папкой проекта на локальной машине, не имеет права
удалять файлы: любой `rm`, `rmdir` или `unlink` внутри подключённой папки возвращает
`Operation not permitted`. Это ограничение среды, а не настройка репозитория.

Git на это рассчитывать не может. Механика такая: почти каждая операция, меняющая
состояние репозитория, сначала создаёт файл-замок — `.git/index.lock`, `.git/HEAD.lock`,
`.git/objects/maintenance.lock`, локи на конкретные ссылки при работе с ветками. Дальше
возможны два исхода. Если операция завершается записью, git **переименовывает** замок
в целевой файл — например, `index.lock` → `index`. Переименование внутри папки разрешено,
поэтому такие операции проходят. Если же операция завершается без записи — а это, например,
`git status`, который взял замок, обновил индекс в памяти и ничего не поменял, — git должен
замок **удалить**. Вот здесь и приходит `Operation not permitted`, и замок остаётся лежать.

Следующая операция видит существующий `index.lock` и отказывается работать:

```
fatal: Unable to create '.../.git/index.lock': File exists.
Another git process seems to be running in this repository...
```

Ровно на этом упал первый `git commit`.

### Что делает обход

Перед каждой git-операцией я переношу оставшиеся `*.lock` в `.git/_trash/` (переименование
разрешено) и там же складываю недоудалённые временные объекты `.git/objects/**/tmp_obj_*`.

### Почему это риск, а не косметика

Замок существует именно для того, чтобы две операции не работали с индексом одновременно.
Снимая его до запуска команды, я снимаю эту защиту. Пока в репозитории работает ровно один
процесс — последствий нет, потому что все замки заведомо мёртвые: их некому было удалить.
Опасность появляется там, где процессов больше одного:

- **worktrees.** Несколько рабочих копий делят общий каталог `.git`. Замки на общие ссылки
  и на `objects` становятся общими, и снятый вслепую замок может относиться к **живой**
  операции соседнего worktree, а не к мёртвой.
- **merge.** Слияние — самая длинная операция с индексом. Снятие её замка в середине
  оставляет индекс в частично записанном состоянии; внешне это выглядит как исчезнувшие
  или задвоенные файлы в рабочем дереве.
- **параллельные агенты.** Если несколько агентов работают с репозиторием одновременно,
  предположение «все замки мёртвые» перестаёт быть верным.

Цена ошибки — повреждённый индекс. Объекты при этом обычно целы, и восстановление возможно
(`git reset`, пересборка индекса), но история шага теряется, а в однодневном темпе это дорого.

### Почему обход не заменён нормальным решением

Штатный путь — выдать оболочке право на удаление внутри папки проекта. Для этого нужен
инструмент запроса разрешения (`device_request_delete_permission`), который показал бы
подтверждение на устройстве. **В этой сборке инструмент отсутствует.** Поиск по точному
имени и по описанию вернул только `device_request_folder_access` — он расширяет доступ
к папкам, но права на удаление не выдаёт. Запросить разрешение нечем.

### Правила, которые из этого следуют

1. В репозитории в каждый момент времени работает **ровно один** процесс. Никаких
   параллельных git-команд.
2. Перед снятием замка проверять, не идёт ли операция в другом worktree. Если идёт —
   ждать, а не снимать.
3. На этапе worktrees и merge — снимать замки **поштучно и осознанно**, глядя на имя
   файла, а не пакетным `find`.
4. Мусор копится в `.git/_trash/`. В сдачу не попадает: каталог `.git` не отслеживается.

### Проверка целостности

После каждого коммита состояние подтверждается: `git status --short` (пусто = дерево
чистое), `git log --oneline` и состав коммита через `git show --stat`. Первый коммит
`e69f718` этой проверкой подтверждён — четыре файла, 504 строки, ничего лишнего.

## Р-2. Реестр npm недоступен из обоих окружений

**Статус: обойдено конструктивно, ограничение принято как данность.**

`npm ping` возвращает `E403` и на локальной машине, и в облачном контейнере. На локальной
машине `curl` показывает источник отказа прямо: `HTTP code 403 from proxy after CONNECT` —
соединение перехватывает исходящий прокси. Полный вывод — `evidence/env-check.md`.

Следствия приняты в план: приложение и проверки строятся на Node.js без внешних
зависимостей, ни один шаг не зависит от `npm install`. Playwright доступен только
в облачном контейнере (1.56.0, Chromium предустановлен), поэтому UI-проверки идут там,
а не на локальной машине.

Побочная польза: отказ прокси на `CONNECT` — это готовый **вывод неудачной попытки** выйти
за границу окружения, то самое доказательство изоляции, которое задание просит показать
выводом, а не словами.
